# Poeticus AI development conventions

These requirements apply to all AI-generated code changes and GitHub operations in this repository.

## Development entry and PR closeout

- **Actually read current guidance before substantive work:** open the [teaching and development collaboration manual](https://github.com/montricwang/chatgpt-vault/blob/main/GPT%20%E7%BA%A6%E6%9D%9F/%E6%95%99%E5%AD%A6%E4%B8%8E%E5%BC%80%E5%8F%91%E5%8D%8F%E4%BD%9C%E6%89%8B%E5%86%8C.md) and the [六花 manual index](https://github.com/montricwang/chatgpt-vault/blob/main/%E5%85%AD%E8%8A%B1/%E8%AF%A6%E7%BB%86%E6%93%8D%E4%BD%9C%E6%89%8B%E5%86%8C/README.md) plus only the relevant submanuals. Restore the related Issues, PRs, code, and previous decisions before designing or implementing. Recheck the relevant sections at major architecture, merge, and release milestones; do not claim a review was completed if the sources were inaccessible. Keep this lightweight for small, deterministic edits.
- **Clean up at PR closeout:** after a PR is merged or closed, inspect its worktree for tracked, untracked, and ignored private files, active processes, and independent commits. Archive needed data, then remove the unused worktree without `--force`. Preserve branches or worktrees that still serve a real purpose, and report anything left for follow-up. Opening a PR alone does not trigger worktree removal.

- **Commits (including squash-merge commits): English Conventional Commits**, with **type and subject required, scope optional**: `type: subject` or `type(scope): subject`. Examples: `ci: update GitHub workflows` and `fix(retrieval): reject empty tokens`. Use English for commit body and footer. Include a scope when it usefully identifies an affected module, but never invent one to satisfy formatting. Breaking changes may use `type!: subject` or `type(scope)!: subject`.
- Allowed types: `build, chore, ci, docs, feat, fix, perf, refactor, revert, style, test`.
- **PR title and PR description: Chinese** (technical names, commands, paths, and identifiers may remain English). Issue title and body: Chinese.
- **Check the wording when writing or editing an Issue/PR:** before publishing the title or body, read the current [中文表达](https://github.com/montricwang/chatgpt-vault/blob/main/GPT%20%E7%BA%A6%E6%9D%9F/%E6%A0%B8%E5%BF%83%E8%A7%84%E8%8C%83/%E4%B8%AD%E6%96%87%E8%A1%A8%E8%BE%BE.md) rules. Write natural Chinese that clearly states the current problem, what changed or remains to be done, and the evidence. Remove invented terms, abstract noun clusters, repeated history, and template filler; retain necessary technical identifiers, constraints, and precise acceptance criteria. Re-read the actual draft before creating or updating the GitHub item. Reading `AGENTS.md` at session start does not replace this final wording check.
- **Squash and Merge:** never reuse the Chinese PR title as the Git commit title. Supply an explicit English `type: subject` or `type(scope): subject` and English commit body using GitHub's `commit_title` / `commit_message` arguments, or `gh pr merge --squash --subject ... --body ...`. Validate the final message before merge.
- The repository enforces commit formatting using `commitlint.config.mjs` and PR language using `.github/workflows/pr-language.yml`. A local opt-in commit hook lives in `.githooks/commit-msg`. GitHub administrators must separately enable required checks and commit-metadata Rulesets to prevent bypass by direct push or incorrect squash titles.
- Write PR titles and descriptions in Chinese even when all code comments or commit messages are in English.
- **GitHub Issues:** Search existing open and closed issues/PRs before creating one. Prefer updating an existing task when its goal and acceptance are shared; preserve one source of truth rather than opening separate learning-only or overlapping tickets. Use native sub-issues for independently verifiable work under a larger goal, dependencies only for real blocking relationships, and checklists only for steps within one task. If the integration cannot create native sub-issue links, say so and use explicit references instead; never imply that a Markdown link is a native parent-child relationship.
- **Issue closure:** Check completion evidence (PR/code/tests and real interaction acceptance where applicable). Resolve each unchecked item as done, deferred to a linked issue, or explicitly out of scope; never bulk-check historical boxes merely because an issue was closed. For obsolete work, record the replacement or reason and close with the appropriate state. Keep issue current status concise and leave historical decisions traceable.

## Implementation and verification

- **Keep changes focused:** Prefer the simplest solution compatible with existing architecture and stated acceptance criteria. Do not add speculative abstractions, compatibility layers, retries, fallbacks, or redundant state. Preserve necessary security, input validation, and error handling.
- **Test according to risk:** Prioritize tests that catch realistic failures. For bug fixes, add a focused regression test when it provides lasting value; for core algorithms, APIs, and data changes, use relevant unit or integration tests. Purely visual changes generally do not need new unit tests; inspect the affected UI in a browser instead. Avoid duplicate or low-value test cases.
- **Verify proportionately:** Start with affected checks and tests. Run full test suites, builds, or E2E checks when the scope or risk warrants them, such as cross-module changes and release preparation. Do not repeat successful checks unless relevant code or assumptions changed.
- **Stop when done:** Once the requested behavior and appropriate verification are complete, finish the task. Do not expand CI, testing infrastructure, documentation, or unrelated code without a concrete need. Record optional follow-up improvements rather than implementing them unrequested.

- Frontend verification commands (from `frontend/`): `npm run lint`, `npm run format:check`, `npm run build`, and `npm run test:e2e`. Select relevant checks for the change; run the full set for release preparation or when the change warrants broad regression coverage. Playwright exercises Chromium at desktop and mobile viewports; visually assess layout and animation changes in the browser. Tailwind v4 class canonicalization is warned about in ESLint and Tailwind IntelliSense. Do not automatically rewrite or reorder established Tailwind class strings across the whole project; `npm run format:tailwind` is an explicit, opt-in migration command.
- Dependency updates arrive weekly through Dependabot; keep its PRs small. Audit Python requirements with the `Python dependency security` workflow; do not auto-fix security upgrades without tests.
