# EPUB 作品导入 SOP

本文件记录 Poeticus 从 EPUB 导入作品数据时的标准检查流程，以及已经发现或需要主动排查的风险。它不是某一册书的解析说明，而是以后处理任何半结构化文献数据时都要遵守的最低检查清单。

对应实施 Issue：#48。

## 1. 核心原则

1. **先认识数据，再写规则。** 不根据一两个样本推断整本 EPUB 都使用同一种 XHTML 结构。
2. **提取阶段优先保留信息。** 不静默改字、不擅自统一异文、不删除暂时看不懂的符号或节点。
3. **规范化与原始值分开。** 例如保留 `heading_raw`，再生成 `cipai`、`subtitle` 等规范化字段。
4. **程序成功运行不等于数据正确。** 数据工程最危险的问题往往是没有报错但悄悄丢失内容。
5. **不确定就进入 warning / review。** 不让启发式规则把猜测伪装成确定事实。
6. **原始资料可追溯。** 任何规范化结果都应能够回到原 EPUB 中对应的文件、锚点或上下文。
7. **私有原始资料与公开代码分离。** 商业 EPUB、完整现代注释和评论不提交到公开仓库。

## 2. 标准流程

```text
Raw EPUB
  ↓
Profiling / 数据探查
  ↓
Extraction / 提取
  ↓
Extraction Validation / 提取校验
  ↓
Normalization / 规范化
  ↓
Normalization Validation / 规范化校验
  ↓
Review / 人工抽查
  ↓
Curated Output / 可发布数据
  ↓
Enrichment / 知识增强（后续）
```

每进入下一阶段以前，先完成上一阶段对应的最低检查。不要为了尽快得到“漂亮 JSON”跳过中间校验。

## 3. Profiling：先认识 EPUB

处理一个新 EPUB、作者卷或明显不同的章节结构时，先回答这些问题：

- [ ] EPUB 的目录、spine 与实际 XHTML 文件怎样对应？
- [ ] 是“一首作品一个 HTML”，还是“整卷/整册共用一个 HTML + anchor”？
- [ ] 标题主要使用哪些标签：`h1`、`h2`、`p`、`div` 或其他？
- [ ] 正文是否只在 `p` 中？是否大量使用 `br`、`span`、`ruby`、`a`、`aside` 等内联或脚注结构？
- [ ] 是否存在 `<img>`？图片位于封面、插图，还是正文字符附近？
- [ ] 是否存在自定义字体、私用区字符、实体或其他特殊编码？
- [ ] 作品标题、题目、序、注释、评论分别如何标记？
- [ ] 同样的视觉结构在不同册、不同作者中是否真的使用同样的 HTML 结构？

探查脚本只负责回答“数据长什么样”，不要在这个阶段加入业务修复规则。

## 4. Extraction：尽量无损地提取

提取阶段的目标是将 EPUB 中已经存在的结构转成程序可处理的候选对象。

当前允许做的事情包括：

- 按已经确认的标题节点切分作品候选；
- 保留正文段落及顺序；
- 根据明确标记将 `◎`、`◆` 等内容暂时分类；
- 保存原始标题、来源文件和必要的定位信息；
- 记录正文附近出现的图片、脚注或其他无法直接归类的节点。

当前不要做：

- 自动纠正正文错字或异文；
- 删除 `◎`、`◆` 等仍然携带结构信息的符号；
- 根据文学知识猜测缺失文字；
- 将“又”“又和……”直接改成上一首词牌而不保留原值；
- 默认忽略 parser 没有识别的元素。

## 5. Extraction Validation：检查有没有悄悄丢东西

每次新增解析规则或处理新的结构类型，至少做以下检查。

### 5.1 自动检查

- [ ] 作品数量是否与目录或人工计数大致一致？
- [ ] 是否出现空标题、空正文或异常短正文？
- [ ] 正文是否混入以 `◎`、`◆` 开头的内容？
- [ ] 是否出现 `□`、`�`、异常问号、私用区字符或其他可疑 Unicode？
- [ ] XHTML 中的 `<img>` 是否全部被统计，并记录所在文件和附近文字？
- [ ] 是否存在当前 parser 没处理但包含大量文字的标签？
- [ ] 是否出现异常重复作品或完全相同正文？
- [ ] 第一首和最后一首是否正常切分，避免边界漏失？

### 5.2 人工抽样

每次较大的 parser 变化至少检查三类样本：

1. **随机样本**：随机挑若干作品，避免只验证已经知道的情况。
2. **边界样本**：复杂标题、生僻字、图片、序文、注释特别多等已知难点。
3. **首尾样本**：每个 HTML 或卷的第一首与最后一首。

检查方式尽量直接：**左边看原 EPUB，右边看抽取 JSON**。逐项核对标题、正文、分阕、序文、注释、评论、图片位置和作品边界。

## 6. Normalization：统一表示，不替代校勘

只有提取层已经可靠，才开始规范化。

可以做：

- 统一字段名与数据类型；
- 保留 `heading_raw`，另生成词牌、题目、副题等字段；
- 处理全角/半角空格和确定性的格式差异；
- 为作者、collection、source 建立稳定表示；
- 将已识别的结构符号从正文内容中分离，同时保留原始值或可追溯信息；
- 为候选作品建立稳定 ID 和审核状态。

需要谨慎或进入 review 的情况：

- “又”“又和……”等依赖上文的标题；
- 词牌与题目直接粘连，且存在多个可能切分；
- 不同底本正文有异文；
- 序文与正文边界不明确；
- `◎`、`◆` 在不同册中语义可能变化；
- 看似错字但可能是异体字、通假字或版本差异。

## 7. Normalization Validation

规范化以后再次检查：

- [ ] `heading_raw` 等原始字段没有丢失；
- [ ] 规范化前后正文字符没有发生未经允许的改变；
- [ ] 词牌/题目拆分失败时有明确 warning，而不是生成看似正确的值；
- [ ] 同一作品的稳定 ID 不会因为重新运行脚本而无故变化；
- [ ] review 状态能够区分 `imported`、`needs_review`、`reviewed`、`disputed`；
- [ ] 规范化规则的适用范围明确，不将局部规律默认为全书规律。

## 8. 当前已知风险登记

| 风险 | 已知情况 | 检查办法 | 默认处理 |
| --- | --- | --- | --- |
| 不同册 XHTML 结构不同 | 已确认存在“一 HTML 多首”和“一 HTML 一首”等差异 | 跨作者、跨册探查 | 不共享未经验证的结构假设 |
| 图片可能承担文字 | EPUB 中可能用图片表示无法直接排出的生僻字 | 扫描全部 `<img>` 及上下文 | warning + 人工确认 |
| 标题依赖上下文 | 存在“又”“又和……”等形式 | 保留前后作品和 `heading_raw` | 后续单独解析 |
| 词牌与题目粘连 | 苏轼等样本存在 | 词牌表最长前缀匹配 + review | 不在提取阶段拆分 |
| 普通段落不一定全是正文 | 可能包含序文、小题记等 | 原 EPUB 对照 | 后续 schema 支持 preface |
| `◎` / `◆` 可能只是粗粒度标记 | `◆` 可包含评论、纪年等不同内容 | 跨册抽样 | 当前只做粗分类 |
| 异常字符 | 已见 `□` 等情况 | Unicode 扫描 | warning，不自动修字 |
| HTML/XML parser 差异 | XHTML 本质是 XML | 对关键样本比较 DOM/文本 | 有实际差异时再调整 parser |
| TOC / spine / 文件顺序可能不同 | 尚待系统验证 | 对比三种顺序 | 以实际阅读顺序和锚点验证 |
| 内联标签可能改变文本边界 | 尚待系统验证 | 检查 `br/span/ruby/a` 等 | 不默认忽略 |
| 重复作品/不同版本 | 后续多来源导入时必然可能出现 | 稳定 ID、首句、正文 hash | 标记来源，不静默去重 |

## 9. 新发现一个坑时怎么处理

以后遇到新的异常，不只修当前数据。依次做四件事：

1. **保存最小复现样本**：记录具体 EPUB 文件、HTML、作品或节点。
2. **判断属于哪一层**：是探查不足、提取错误、规范化错误，还是确实需要人工校勘。
3. **补自动检查或测试**：只要能够机器发现，就不要永远依赖人记得。
4. **更新本表**：写清“现象 → 怎么发现 → 默认处理”。

目标不是提前猜完所有坑，而是让每踩一次坑，流水线以后都多一道护栏。
