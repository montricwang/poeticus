# Poeticus 开发日志｜2026-10-19

> 当日开发记录：Document Corpus / RAG / Reranker 对照，以及并行进行的本地模型推理实验。Document RAG 的代码和数据库只在本地实验，未公开部署。

## 本地模型：从「能装下」到真正跑通 CPU 与 Intel GPU

围绕 Poeticus 未来的离线文学分析与 Critic Refine，初步验证了三款本地 GGUF 模型。模型权重均保存于独立的 `poeticus-data/models/`，运行工具隔离在私人数据目录；未改生产 Agent、LLM API 配置或现有 Retrieval 服务。

先使用 WSL + `llama-cpp-python==0.3.36` 做 CPU Smoke Test。Qwen3.5-4B Q4_K_M 加载约 **4.92 秒**，生成简短的苏轼《定风波》中文解释；DeepSeek-R1-0528-Qwen3-8B Q4_K_M 加载约 **16.33 秒**，能够正常生成，但最初的 **96 Token** 输出额度消耗在 `<think>` 内，尚未拿到完整的最终文学回答。这一阶段只证明离线推理链路可用。

随后检查 Intel Iris Xe：**WSL Vulkan 仅枚举到 `llvmpipe` CPU 软件渲染器**，因此改用 **Windows 原生 llama.cpp b11723 + Vulkan**。`--list-devices` 与运行时日志均确实识别 Intel Iris Xe，并分别通过 `-ngl 0` / `-ngl 99` 测试 CPU / GPU。短 Benchmark（单次，不同模型的 Token 长度也不同）：

| 模型 | GGUF 权重 | Windows CPU 生成 | Intel Iris Xe 生成 |
| --- | ---: | ---: | ---: |
| Qwen3.5-4B Q4_K_M | 2.74 GB | 8.97 Token/s | **12.51 Token/s** |
| DeepSeek-R1-0528-Qwen3-8B Q4_K_M | 5.03 GB | 5.93 Token/s | **8.29 Token/s** |
| Ternary Bonsai 2 27B PTQ1_0 | 5.95 GB | 1.09 Token/s | **2.38 Token/s** |

Bonsai 2 27B 从国内 ModelScope 镜像下载并完成 SHA-256 校验。其 **PTQ1_0（1.75 bpw）** 需要 Prism ML 定制版 llama.cpp；安装相容的 `prism-b10772-e8fd209` Windows Vulkan 发行包后，已在核显上**真正生成完整中文回答**。即使权重仅比 8B 大约 18%，核显生成速度也只有约 2.4 Token/s，提示词处理约 1.42 Token/s。极低位量化节省了存储与模型驻留所需内存，**没有同步消除 27B 规模的推理计算成本**；不能直接据此归因于特定硬件或 Kernel。WSL 4 GiB Swap 曾被占满，后续长文评测要限制并发、检查内存与换页。

**已验证**：普通笔记本可以离线运行 4B / 8B / 27B；Windows 原生 Vulkan 可真实调用 Intel 核显；8B 可作为低速本地实验模型。**尚未验证**：8B 的文献提炼、观点归纳、批评与修订的实际质量、长上下文与长时间稳定性、是否优于单轮云端模型；本轮没有进行 LoRA 微调。

## Document Corpus：四部词学文献落入 PostgreSQL

先从《白雨斋词话》《人间词话》《碧鸡漫志》《乐府指迷》四本维基文库 EPUB 开始。完成原文 XHTML 与私有 JSON 的 **916/916 section 全量对照**，构建独立的 `document_corpus`：4 个 document、4 个 version、938 个 node（含卷/分组）、916 个检索 Chunk。幂等导入、来源键与回读路径经过实际校验；原 `public.poems` 的 3491 首未受影响。PostgreSQL 18 服务端安装 pgvector 0.8.7 后导入 916 条现有 Qwen3-Embedding-0.6B 向量，SQL Top5 向量检索与 numpy 对照同序。

保留“书 → 版本 → 卷/章节 → 原文”层级与 EPUB 锚点，检索索引从结构化原文派生，未来可共用一份文献数据服务 AI 检索和连续阅读。四本来源的 `rights_status` 仍是 `unreviewed`：不得将本地可检索推断为有权向公众提供全文。原文、模型、评测报告均放在私有 `poeticus-data`；本轮没有创建阅读器或部署到 Railway。

## Document RAG：从 BM25 到 Agent 的查询扩展

`scripts/experiments/document_rag_lexical_baseline.py` 在固定 16 道开发题得到 BM25 Hit@5 **9/16**；完成 58 批 Qwen3 向量后，同集 Dense **10/16**、Hybrid **11/16**。独立 `document_rag_answers.py` 比较 LLM Only、Hybrid 和 Agentic Hybrid（真实模型调用）；在 `BAI_06` 中 Agent 补充别称查询找到原 Hybrid 漏掉的《白雨斋词话》评论。对 `CROSS_01`，Agent 扩展虽找到陈廷焯的反驳，却遗漏《乐府指迷》沈义父的原文。这说明“可找到至少一条相关评论”和“支持完整跨书回答”不是同一项指标。

通过 `search_documents` 将 PostgreSQL 向量查询（Top50）与 BM25（Top50）及多查询 RRF 接入本地 LangGraph Agent，返回 Top5 带书名、卷则、EPUB 定位的**候选评论证据**。由 `POETICUS_DOCUMENT_RAG_ENABLED` 显式开启，未安装本机模型或无数据库时不向模型注册该工具；错误返回不会捏造证据。现有 Poem Retrieval 的作品级 RRF、朝代规则和前端行为未改。

## Reranker：跑通推理，也找到了精排的局限

对同一组 **16 道 development/in_corpus 题**冻结 Agent 查询，以旧 Hybrid 每查询 Top5、延后截断 Top16、Top16 后 Qwen3-Reranker 精排三个条件比较。指标分别为：

| 指标 | 原 Hybrid | 延后截断 | + Reranker |
| --- | ---: | ---: | ---: |
| Hit@5 | 93.75% | 68.75% | 81.25% |
| All Gold@5 | 75.00% | 62.50% | 75.00% |
| Macro Recall@5 | 85.42% | 66.67% | 79.17% |
| MRR@5 | 65.62% | 54.37% | **70.83%** |

Reranker 相比“延后截断”改善排序，但未在总体 Recall@5 上超越原 Hybrid。跨书 `CROSS_01` 的两条 Gold 都进入候选池，却被精排至第 9、11 位；另一些题的 Gold 没有被召回，精排无从补救。Windows 本地 llama.cpp + Intel Iris Xe Vulkan 上用 Qwen3-Reranker-0.6B GGUF 运行 `/v1/rerank`，16 条候选平均请求耗时约 **5.58 秒**（不含 Hybrid 和生成）。本地 `CrossEncoder` 依赖已升级并验证；同时保留可复现实验的 CausalLM yes/no 评分脚本。

因此将 Reranker 实现为 **默认关闭的本地可选能力**，错误时回退原 Hybrid；没有将 Windows HTTP Server 接到生产。下一轮可借鉴 Azure AI Search Agentic Retrieval 的 Query Planning → 分组 Hybrid → 可选 Reranker → Evidence Fusion，但需要保持阶段性 A/B，不能将微软架构名称当作效果证据。
