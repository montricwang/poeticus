# Poeticus 开发日志｜2026-10-12

> 今天以 Poeticus v0.4.0 的工具链、现状核对与架构理解为主。实际交付包括移动端对话入口的小修复，以及部署文档的合并；MCP / API 对照、Memory、文学批评人格、高维标签与格律分析主要仍处于调查或设计阶段。下午还尝试了独立代码图谱原型，尚未在完整 Poeticus 仓库完成端到端验收。

## 一、移动端对话入口：#244

[PR #244](https://github.com/montricwang/poeticus/pull/244) 已合并到 `main`（`200eccf`）。通过 Serena 在本地只调整 `frontend/src/App.tsx` 中移动端悬浮「对话／提问」按钮的位置，从 `1rem` 上移到 `3.5rem`，保留 `safe-area-inset-bottom`，没有改变聊天状态或后端。

本地 Playwright 检查过 320／390／430 px 宽度、页面切换、API 响应与控制台；手机浏览器也实际确认按钮上移且当前页面没有遮挡。相关前端 lint、格式和类型检查通过（详见 PR 的具体验收记录）。长篇滚动、软键盘和所有安全区情况未穷尽测试；[#242](https://github.com/montricwang/poeticus/issues/242) 仍有其他 UI 工作，不因此关闭。

## 二、重新审视现有 MCP 和专业资料工具

在已有 Poeticus MCP Server 基础上，继续比较 Tavily、Firecrawl、DDGS 等搜索能力，以及 Wikidata、古籍平台、诗词资料与 OCR 的候选接入方式。重点从「还能接什么工具」转向「这是否能补足现有 Evidence / Retrieval 的实际缺口」；三种搜索工具的试用不等于它们已成为 Poeticus 生产 Agent 的默认工具。

Poeticus 现有 [PR #229](https://github.com/montricwang/poeticus/pull/229) 提供只读 MCP Server；它与 LangGraph 入口复用 `EvidenceService` 业务逻辑，不能把 MCP 化误认为检索或模型质量天然提高。真实 CNKGraph 授权与跨环境接入仍需按场景验收。

## 三、恢复长期产品方向，但暂不扩张实现

查阅 README、Roadmap、早期 Issue 和 Dev Log，校正了「当前功能」与「远景构想」的边界，并更新相关讨论：

- [#40](https://github.com/montricwang/poeticus/issues/40)、[#41](https://github.com/montricwang/poeticus/issues/41)、[#45](https://github.com/montricwang/poeticus/issues/45)：浏览器 `localStorage` 已保存单设备 Conversation；服务端会话持久化、跨会话用户记忆与 Agent 运行时上下文是不同层次。
- [#148](https://github.com/montricwang/poeticus/issues/148)：长期 Critic Persona / Constitution、按任务使用的 Skills、外部 Library 与可审阅的批评 Notebook；产品自身审美记忆不得与某位用户的私人记忆混在一起。
- [#156](https://github.com/montricwang/poeticus/issues/156)、[#157](https://github.com/montricwang/poeticus/issues/157)：讨论让 LLM 离线为大量诗词生成开放式、可解释的文学特征标签，再以稀疏匹配／语义检索发现跨作品的「意外近邻」。标签归一化、一致性、证据与相似度仍待小样本验证；当天没有全量打标或建立索引。
- [#225](https://github.com/montricwang/poeticus/issues/225)：CNKGraph 词律网页、正式 API、以及「词谱 + LLM 辅助核查」作为不同候选方案；具体接口的可调用性、格律歧义和授权尚未确认。

这里记录的是调查成果和待试验的技术路线，不是已经交付的功能。

## 四、开始以本地代码为依据理解 v0.4.0

接入 Serena、Poeticus Checks 和浏览器工具后，确认可以直接读取本地工作树、按符号定位函数和调用者、运行已有静态检查。代表性的代码追踪包括 `savePoemConversation()` 到 `use-conversation-persistence.ts`、`EvidenceService` 同时被 `backend/ai/graph.py` 与 `backend/mcp/server.py` 引用，以及 `graph.py` 中 LangGraph 节点组织。

另做了一个独立的 **Poeticus Code Atlas** 原型，尝试展示模块、文件、函数、静态调用关系和源码预览；进行了原型级交互与样例检查，但**没有在完整 Poeticus 仓库验证整个分析结果**，也没有将原型合入主项目。不能据此宣称 v0.4.0 的全部代码已讲通或完成重构。

个人学习方向由全天持续推功能，调整为「半天理解、半天有界实践」；下一轮先弄清已有调用链及必要的工程原理，再决定是否引入新框架。

## 五、部署文档合并及仍待验收事项

[PR #232](https://github.com/montricwang/poeticus/pull/232) 于 10 月 12 日合并，更新 README、部署说明、开发指南和检索架构文档，明确 `poeticus.app → Cloudflare → Railway` 与 `retrieval.poeticus.app → Cloudflare Tunnel → Windows cloudflared → WSL Retrieval` 两条链路，并重申 Issue／PR 用中文、Git Commit 用英文的约定。

主站和命名 Tunnel 的历史连通性不代表最后一次线上 Agent → Retrieval 请求已完整验收；实际带 Token 的检索 POST、错误降级等仍按 [#180](https://github.com/montricwang/poeticus/issues/180) 的用例检查。后来发现这次 Squash Merge 最终提交标题被 GitHub 自动取为中文，原先只检查 PR 内提交的 Action 未覆盖合并后的 `main`；该 CI 漏洞留作后续修正。

**当天小结**：有可核对的 UI 小修、部署说明合并、MCP 实际试用和代码工具验证；Memory、Poeticus 长期人格、文学标签系统与格律分析均未落地。接下来优先把现有项目理解清楚，而不是再扩大功能范围。
