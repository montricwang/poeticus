## 二、值得记住的问题与解决过程

### 1. 三分类工作流把“理解用户意图”变成了固定关卡

**现象：** 昨日的设计先将问题归入细读、查证或澄清，再执行对应分支。实际用户却会提出“先查询「三星当户」的典故，再根据结果解释这句词”一类复合任务。固定分支不便于在一次请求中自然组合检索、阅读证据和文学解释，也限制了模型根据中间结果调整下一步行动。

**原因与调整：** 最初把“希望助手理解问题并恰当地使用工具”这个产品需求，过早落实为“必须先做三分类”这一实现方案，开发前没有用复合任务检验架构。今天改为 ReAct 式循环：Agent 可以直接回答，也可以产生 `tool_calls`；工具结果以 `tool` 消息返回消息历史，Agent 再次决定继续检索还是完成回答。每次请求的实际工具调用数量设有上限。[初次迁移](https://github.com/montricwang/poeticus/commit/51e75be2fecf04e0075ef77271f6bd3689efc4f0)、[迭代工具调用与流式支持](https://github.com/montricwang/poeticus/commit/701d16332d36b9d592244f08726c48483839bd07)。

**经验：** 意图理解是 Agent 的能力，不必总是一个互斥的前置分类节点。设计架构时应先写出典型任务和跨能力任务，再比较固定工作流与自主工具调用的取舍。三分类并非普遍错误，只是不符合当前 Poeticus 的开放式阅读场景。

### 2. 工具调用前的英文预告语混入正式回答（#6）

**现象：** 复现问题为“请先查询「三星当户」的典故，再根据检索结果解释这句词”。模型有时先输出 `I'll look up the allusion for ...`，再发起 `lookup_allusion`，最后生成中文赏析。前端将英文预告语直接展示在正式回答前；早期 API 还会因为把所有流式文字合并后与最终 `reply` 比较，报出“流式内容与工作流结果不一致”。相对简单的“检索一下三星当户”更容易直接产生工具调用，不一定复现。

**定位与阶段处理：** LangSmith 中能够看到工具调用、检索结果及最终回答，问题主要发生在模型流式片段经 Graph custom 事件转发为 SSE 的边界：在收到后续 `tool_calls` 之前，程序已把先到达的 `content` 发给浏览器。API 随后区分工具调用前的文字与最终回答，仅对最近一轮正式回答做完整性校验，并以空行分隔不同阶段的文字。[阶段性修改](https://github.com/montricwang/poeticus/commit/cb0abce9811d710ca1092eca3afe8ebe14fcabfb)。

**尚未解决：** 这并没有真正隐藏中间消息；英文预告语仍可能进入用户可见内容。仅靠 Prompt 要求模型不要预告并不可靠，也不能按英文句式做硬编码过滤。正确的长期方向是在输出契约上区分中间 Agent 消息与最终回答，同时权衡流式首字延迟。[#6](https://github.com/montricwang/poeticus/issues/6) 保持开放。

**经验：** 模型消息的 `content` 不必然等于应展示给用户的最终答案。Graph 执行成功、SSE 事件正确传输、前端展示正确，是三个需要分别验证的层次。

### 3. 架构替换很快，旧测试和旧文档不会自动消失

**现象：** 新 Graph 已经只有 `agent` 和 `tools`，仓库中却仍然有 `IntentResult`、引用已删除 `classify_intent` 的评测脚本、未被调用的 `agent_after_tool.md`，以及模拟 `classify_intent`、`direct_answer` 等旧节点事件的 SSE 测试。旧 README 和架构文档也仍在介绍三分类。

**处理：** 先让 Codex 对整个工作区进行只读审计，按“可删除、需要迁移、暂时保留、人工确认”区分遗留资产；随后分批清理确定废弃的类、Prompt 和评测脚本，保留尚未确定用途的兼容代码与历史题库。将 API 层的 Mock SSE 事件迁移为当前 `agent → tools → agent` 流程，最后分别修订 README 和内部架构文档。[测试迁移](https://github.com/montricwang/poeticus/commit/98c357e2e036cc3f2cca9bc8d7728fd3b9c0e2fc)、[遗留清理](https://github.com/montricwang/poeticus/commit/f610e150a13c64c0e4ac0914657f0d2e418dc02e)、[文档迁移](https://github.com/montricwang/poeticus/commit/f4bf0ef067746a8ec4f6b0a493959586aa10dd6a)。

**经验：** AI 可以在短时间内完成一次核心重构，却不会保证所有调用方、测试、评测和文档同步迁移。尤其是模拟过时节点却仍然通过的测试，会带来虚假的安全感。核心架构改动应以“新功能可用＋全仓库影响检查＋关键链路回归”为完成条件。

### 4. 重新生成时临时草稿框突然变得明显（#39）

**现象：** 过去重新生成时主要看到加载状态；真实流式链路接通后，前端会在旧答案下方的临时框中逐步展示 `streamDraft`，成功后再用新答案替换旧答案，临时框随即消失。英文工具预告语也可能先出现在这个框里。

**定位：** 这是前端已有的重新生成交互与新增真实流式输出共同作用的结果，不是 LangGraph 新增了一个可见面板。它与中间消息混入正文是两个独立问题。

**处理决定：** 新建 [#39](https://github.com/montricwang/poeticus/issues/39)，暂不修改：期望重新生成期间保留旧答案，仅显示轻量进度；成功后替换，失败时保留旧答案及可查看的未完成草稿。

**经验：** 后端从一次性返回改为真实流式后，应重新验收所有消费增量数据的前端状态，包括普通回答、重新生成、失败恢复和滚动行为。

## 三、当日决定及留下的边界

- **当前采用 ReAct，不预先引入 Plan-and-Execute。** 先验证直接回答、工具查询、读完结果再回答以及连续工具调用。将来确有跨来源、多阶段研究任务，再用具体失败用例评估是否增加显式规划，避免为了架构完整而提前增加复杂度。
- **区分三种责任。** 产品需求描述用户要完成什么；架构设计决定系统怎样完成；工程验收检查这次变更影响了哪些旧资产。此次问题不仅是三分类选择不合适，还包括最初没有对复合任务做设计反例检验，以及迁移时低估了全仓库影响。提出实现想法不等于必须照单编码，技术建议需要主动指出可能限制产品目标的架构取舍。
- **保留可追溯的迁移边界。** 已清理确定废弃的路由类、Prompt 和失效脚本；旧评测题目及 `main.py` 中潜在兼容用途的独立聊天／证据回答函数暂不贸然删除。当前文件仍叫 `intent_router.py`，不为改名而牵动部署配置。
- **对外 README 与内部架构文档分工。** README 优先说明 Poeticus 是什么、能做什么、怎样本地体验；Graph State、工具循环、SSE 和已知技术限制放入 `docs/architecture/langgraph.md`。文档内容应以已实现的行为为准，不把计划当作产品能力。
- **保留分层测试。** API 契约测试可以 Mock Graph，Agent 单元测试可以 Mock 模型和 Provider，但还需要覆盖 API→真实 Graph→模拟模型／工具的关键路径；旧分类质量评测不能冒充新 Agent 的质量评测。
