## 二、我们怎么从单册原型走到全册？

前一天的基础原型用 `h2` 识别题头、`p` 识别正文，按 `◎/◆` 区分独立注释与评论。这适合先验证 EPUB 能读、JSON 能写，却把**局部能跑**误认为**全书结构已知**。10 月 1 日先以 [PR #50](https://github.com/montricwang/poeticus/pull/50) 扫描 22 册的 DOM/CSS 结构，发现多层标题 `span`、`br`、分册样式差异等信息在单纯 `get_text()` 后会丢失；还定位了 EbookLib 重建 XHTML 导致 CSS 引用丢失及 Windows UTF-8 解码问题。基础代码最终由干净快照 [PR #52](https://github.com/montricwang/poeticus/pull/52) 合并。

今天进一步采用 **先保留源块事实，再给段落赋予语义** 的路径：

```text
本地商业 EPUB → TOC / 原始 XHTML / CSS
      ↓
按文件与源块号保留标签、样式、标题子节点、文本位置
      ↓
有状态分类：作者/词牌/词题/题序/词文/注释/评论/未知项
      ↓
结构审计、未分类阻断、图片字预检 → 人工复核少量来源
      ↓
图片字规范化 → 逐册原始与规范化 JSON → all_normalized.json
```

顺序上的改变很重要：**AI 不应依赖用户先想到 CSS 或 Markdown 报告才会调查结构；用户提议“用 HTML 拆”应被视为候选实现方法，而不是经过审查的问题定义。** 但也不能事后声称一开始就能知道纳兰、周邦彦、贺铸所有文学例外：后者必须回到实际来源核查。

## 三、全量检查怎样推动语义判断？

这一天的显著进步是让**错误集中暴露，而非靠用户偶然读到**。

- **合刊与作者边界：** 温韦、南唐三词人、二晏会共享卷册或 XHTML；目录与文内 `h1`、附作署名共同决定作者。单独的「又」只在同一作者和编辑区域中继承词牌。
- **纳兰附作：** 报告提示 3 个署名待定；沿 `h4 → 短段 → 右对齐署名 → 正文` 复核。短段曾先被解释为题注，用户凭原书截图确认应归于 `prefaces`，于是更新分类和合成回归测试。这是**原始证据纠正已写代码**，而不是简单补一个 CSS 条件。
- **周邦彦评论：** 21 个待分类块实际集中在两首词（19 + 2），后经人工确认属于 `◆` 评论的连续考证/引用；只按确知的 XHTML、作品起始块和段落范围定点分类，不把相同 CSS 推广成普遍语义。
- **作者自注与缺文：** 在正文内部样式异常中识别出 `font1` 注释候选、跨样式的引文以及「以下缺」等编辑标记；`kaiti` 有时只是分页后的词文。故**保留原文及字符位置，记录 `inline_notes`/warning，暂不从阅读正文静默剥离**。
- **图片字：** 图片不必然是插图；缺字的 Unicode 编码、历史异体、版本异文和不同地点名称不是同一个问题。集中生成可读图版与原书上下文，由用户判断 `source_form/display_form`，未证实的 IDS 原样保留。
- **贺铸题头：** 全量 JSON 数量与测试均通过后，用户仍发现《翦朝霞》的寓声名混入词题。最终增加可选 `yusheng`，区分原调、寓声名、作品题目；没有为偶见「亦名」增设通用词牌别名字段。**这是无告警也会有语义错误的反例。**

我们分别检查“结构上哪些段落未处理”和“处理后的文学含义对不对”。前者能够程序化全量覆盖，后者仍需要从**被判为正常的结果**中抽样比较原书。全量候选导出成功，不等于十五册全部完成语义审核。

## 四、哪些问题我们主动停止继续扩展？

- 当前没有独立建模组词、组序、词谱、学术异文关系、全局 `cipai_alias`；字段存在需要明确使用场景，不能见到新知识就扩 Schema。
- 卷次与部分编年信息目前参与抽取而未写进最终中间 Poem；统一来源 XHTML/锚点还未成为作品字段。后续迁移数据库前需特别考虑重新定位与作品 ID 稳定性。
- 作者自注仍可能留在 `content.text`，但有位置证据；中间 JSON 不是面向读者的“纯净词文”。
- 不把异常率、零空正文、187 个合成测试换算成文学准确率；质量提升进入 [Issue #57](https://github.com/montricwang/poeticus/issues/57)。
- 合并完成后停止继续堆 EPUB 特例；贺铸全册的结构审查仍跟踪于 [Issue #60](https://github.com/montricwang/poeticus/issues/60)。

## 五、今天的协作方法，哪些有效，哪些仍有不足？

**有效：** AI 先批量统计分布与异常，生成紧凑 Markdown 和私有详细报告；用户只对少量代表性来源判断语义，AI 再补定位规则、失败阻断和合成回归测试。于是无需用户逐首审阅 3,491 条候选，也不用提前知道所有作者的排版差异。

**不足：** 第一阶段仍明显受到“用 HTML 字符串拆分”的用户方案锚定；AI 有能力主动检查 DOM/CSS 与现有库的读取行为，却没有及早提出。早期还发生了 EPUB 派生报告被提交到旧 PR 历史的安全问题；干净 PR #52 与删除分支不能保证旧 SHA/PR 引用彻底不可达。今天的 140 次小提交说明有高频实现与修正，**没有客观基线能证明这是成本最小的流程**；今后应减少无必要的 CI 触发，把相关代码和测试组合成可审查的逻辑提交。

比较可迁移的原则是：**调查范围可以宽，第一版实现应薄；程序负责把已知异常变成反馈，用户负责关键语义取舍；再从“程序认为正常”的数据中抽样发现未知错误。** 整个过程不应靠用户恰好听说下一个技术名词才能继续。
