# Poeticus 开发日志｜2026-10-10

> 今天集中打磨了 Poeticus 的诗词阅读器：从原文无损分行、字号与光学居中，到双栏伴读、滚动条、分割线、主题和上下首导航。代码在连续几轮视觉试验后收口；与此同时，排版进一步暴露了词集底本的句读、缺文和版本问题。以下按**已合并实现、仍待验收、只建立调查任务**区分记录，避免把设计讨论当成完成的功能。

## 一、从原文分行建立可排版的阅读正文

今天的第一步是把诗文展示与原文契约分开。此前阅读器已经能显示真实语料，但直接对字符串施加视觉换行、标点样式，可能破坏划词引用和复制结果。

- [PR #205](https://github.com/montricwang/poeticus/pull/205) 提取 `PoemBody`，把诗文正文的渲染与选区交互集中在独立组件中，不改变原有表现。
- [PR #206](https://github.com/montricwang/poeticus/pull/206) 加入按句读生成视觉诗行及标点片段的逻辑。`buildPoemLines()` 保留每行对应的 UTF-16 原文起止位置，`buildPoemTextRuns()` 只改变标点呈现；复制时仍从原文位置取出连续文字，避免块级视觉分行额外污染剪贴板。
- [PR #208](https://github.com/montricwang/poeticus/pull/208) 约束桌面讨论区的宽度，修复诗文与伴读区宽度分配上的问题。

随后根据温庭筠《更漏子》等真实阅读效果，连续调整字号、行高、片间距、标点对比度和滚动条。[PR #210](https://github.com/montricwang/poeticus/pull/210) 曾把行高从 `2` 收至 `1.65`、标点强度降至约 40%；实测后发现行距偏紧，[PR #211](https://github.com/montricwang/poeticus/pull/211) 将最终值调回**行高 `1.75`、字号 `1.375rem`、字距 `0.05em`、来源段间额外留白 `0.9em`、当时标点强度 50%**。阅读滚动条保持原生拖动与滚轮行为，只让可见滑块更细、更安静。这两项 PR 均已合并，[#209](https://github.com/montricwang/poeticus/issues/209) 已关闭。

这一阶段确定了一个底线：**阅读器可以拆分 DOM、改变行距和标点颜色，但不能改动词文本身的字符顺序。** 选区、UTF-16 offset、复制和 AI 引用始终以 `poemText()` 产生的原文为准。

## 二、长短句怎样居中：#213 的光学居中实验

最初正文按最长诗行决定整个文本块的宽度，再将这个块居中。对于长短句混合的词，少数长句容易把大部分短句挤到左边；但只取中位数又会忽视少数长句对视觉重心的影响。讨论时用过 `4、4、4、8、8` 的长度分布作反例。

[PR #213](https://github.com/montricwang/poeticus/pull/213) 最终没有采用 Canvas 逐像素测墨迹、固定左偏或复杂幂权重，而是根据**真实渲染行宽与行长分布，在传统块居中和文字质心居中之间自适应折中**：

```text
strength = 有效诗行平均宽度 / 最长有效诗行宽度
offset = (诗文块中心 - 文字质心) × strength
```

这里还会对位移进行安全夹紧；行尾标点仍显示，只在有效墨迹宽度测量中降低影响。窄屏自然折行时可以回退传统居中，容器尺寸和字体加载变化会重新测量。开发态保留 `?poemCenter=classic`，方便与原来的布局对照，不增加正式用户设置。

桌面和 iPhone 截图对照过温庭筠《更漏子》、柳永《戚氏》等作品，用户接受长句适度向右延伸、整体视觉平衡的效果。#213 已 Squash and Merge 至 `main`（`44bf6efb`），[#212](https://github.com/montricwang/poeticus/issues/212) 已关闭。**阶梯缩进没有随 #213 一起实现**，留给 [#214](https://github.com/montricwang/poeticus/issues/214) 独立试验。

## 三、阅读与伴读界面：#216 的封板与后续布局收敛

[PR #216](https://github.com/montricwang/poeticus/pull/216) 从居中算法扩展到阅读页整体体验。迭代中实际比较过短词、长词、目录开合、空聊天、长回复与赏析切换，主要调整包括：

- 阅读区／伴读区的宽度与留白、随内容高度变化的竖分割线；滚动条复用为 `.poeticus-scrollport`，阅读区上下边缘只在确有隐藏内容时渐隐。
- 对话字号调整至约 16px、输入区更紧凑；赏析章节间距、译文行高与注释间距收紧，减少无意义的大面积空白。
- 按钮统一采用克制的小圆角，复制、编辑、重新生成等操作使用 `ActionTooltip`，避免原生 `title` 提示在滚动容器内显得突兀；AI 消息署名统一为「Poeticus」。
- 修复赏析切换到对话后再回来会回到顶部的问题：`App` 保存 `analysisScrollTopRef`，`AnalysisPanel` 在滚动时更新，并在重新挂载的 `useLayoutEffect` 中恢复；切诗或重新生成赏析时重置。**只恢复当前页面内切换视图的阅读位置，不是跨刷新持久化。**

这一 PR 曾因 Prettier 格式问题和一条错误的分行测试预期导致 CI 失败。定位后修正格式与测试，而不是为了通过测试篡改分行算法；最终全部检查通过。#213 先合并，#216 再调整 base 并 Squash and Merge 至 `main`（`981be0e3`），[#215](https://github.com/montricwang/poeticus/issues/215) 已关闭。

这里也暴露出工程管理问题：**一个 Draft PR 不适合无限吸收视觉微调**。完成赏析位置修复后主动封板，而没有继续把后续主题和导航需求塞进去。

### 分割线与动态布局的第二轮收敛：#220

以 [PR #218](https://github.com/montricwang/poeticus/pull/218) 的开发分支为基础，[PR #220](https://github.com/montricwang/poeticus/pull/220) 继续处理响应式布局、聊天消息动画、软过渡及线条归属。

- `ReaderCompanionLayout` 负责桌面阅读列、独立竖线、伴读列的共同 Grid 和实测高度，不再把竖线埋进聊天内容。
- `ReaderPane` 负责桌面正文与底部阅读导航之间的横线；手机端独立 `ReaderNavigation` 自己绘制导航横线；`CompanionPane` 组合视图工具栏与短线；`ChatPanel` 负责消息与 Composer 之间的横线。
- `ChatMessageList`、`ChatComposer`、`QuotePreview` 分开管理历史区域的高度收放、输入区和引文预览；引用由一行变两行、取消引用，以及空消息与长回复，都尽量保留双向平滑过渡。滚动与输入区保持原有功能边界。
- 修复了手机上下首按钮靠两端、中间提示可换行、发送按钮持续靠伴读区右侧等具体问题；阅读舞台宽度与两栏分配也在此后进一步调整。

在 Windows Chrome 实测时，`1.5px` 分割线受物理像素位置影响，偶尔看起来像不同粗细；当时的 DPR 为 `1.5`。讨论过按 DPR 对齐像素的方案，但没有充分证据值得引入额外定位算法。**最终用户直接验收了统一 `2px`**：`--editorial-divider-thickness` 同时控制所有 Editorial Divider 和竖线所在 Grid 轨道。没有浏览器专属像素补偿，也没有为短线单独覆盖为 1px。

#220 合并到了 #218 的**开发分支**，并非直接进入当时的 `main`。截至今天最终版本，`index.css` 中阅读舞台上限为 **`82rem`**，桌面阅读／伴读列为 **`0.95fr : 1.05fr`**；它们取代了 #216 阶段尝试的 `74rem` 和 `0.85fr : 1.15fr`。[#219](https://github.com/montricwang/poeticus/issues/219) 保留了这一系列定位、滚动、动画问题和待验收项。

## 五、排版反过来暴露了底本文字问题

完成视觉布局之后，讨论开始转向文本本身。越是打算让诗行的缩进、留白与节奏有规律，越不能把编辑标点和词的格律结构视为同一件事。

### 缺文与编校说明：#74、#221、#222

《历代名家词集精华录》中的李煜《谢新恩》有「（以下缺）」「（以下缺十二字）」等文字。最初想把中文圆括号一律独立成行并整体弱化，但随后否定了这条过宽规则：其他数据库中的括号可能是作者自注、普通正文或不同性质的编校文字。

新的边界是**先辨识语义，再决定视觉表现**：优先利用来源明确给出的结构信息；没有结构时才考虑针对可靠标记的保守识别。识别位置应该集中，避免分行函数、标点着色函数和 React 组件各自重复解析括号。数据库迁移定义包含 `lacunae`、`inline_notes` 等字段，但生产活库中具体有什么、是否与正文同时保留缺文标记，尚未核实；当前作品 API 也尚未向阅读器提供 `lacunae`。

因此建立了 [#221](https://github.com/montricwang/poeticus/issues/221) 进行缺文实例与真实记录调查，[#222](https://github.com/montricwang/poeticus/issues/222) 负责对照活库 Schema、导入结构、API 与前端契约。今天**没有实现括号自动解析，没有修改数据库**。

对比其他传本文字后，还发现《谢新恩》不只涉及「缺十二字」怎样标注，也涉及个别异文、缺阕，以及「春光镇在人空老」是否应与「庭空客散人归后」拼合作一首的问题。**这是版本与作品身份问题，不是简单替换标点。** Poeticus 应保留原书来源文本，由人工确认后的修订形成自己的阅读工作文本；`text_version` 可以记录修订代次，但仅有一个版本号还不足以保存历次文本和跨来源作品分合关系。这一方向关联 [#36](https://github.com/montricwang/poeticus/issues/36)、[#62](https://github.com/montricwang/poeticus/issues/62)，尚未确定数据库新 Schema。

此外还提出用简繁转换结果的 diff **定位疑似未清理的繁体字**：脚本只生成候选及来源上下文，不能把所有差异自动认定为错误，更不能直接批量覆盖古籍原文。该事项本日仅讨论，**没有创建专门 Issue 或执行扫描脚本**。

### 格律与句读：#225

以周邦彦《兰陵王·柳》连续多个逗号、辛弃疾《兰陵王》的现代引号，以及李煜残词不易套入通行词谱为例，发现原书标点可能使未来的阶梯缩进不断递增，视觉效果违背词体节奏。

今天提出参考唐圭璋《全宋词》的一种克制方案：按格律将**韵位、句界、读**分别与 `。`、`，`、`、` 建立候选对应，不让问号、感叹号直接决定视觉缩进层级。但格律并不能无歧义恢复所有句读、引文或残词结构，一首词也可能有正格、变格和多种传本。

新建 [#225](https://github.com/montricwang/poeticus/issues/225)：先统计库中 `？`、`！`、冒号、引号和长串逗号等现象；验证 **CNKGraph 的格律 API 是否确实具备可调用的词谱匹配能力及适用许可**；挑选代表性作品做小样本对照，给无法匹配或有歧义的作品留下人工复查记录。**今天没有完成 API 实测，更没有批量改标点。**

[#214](https://github.com/montricwang/poeticus/issues/214) 的阶梯缩进仍可作为开发专用、可撤销的视觉实验推进，没必要等到全库 3,491 首全部校勘完毕；但不能把未经校验的逗号数量误认为已经确认的韵律结构。未来理想的方向是让「原始文本 → 经验证的句读／韵位信息 → 展示层分行与缩进」逐步分离。

## 今天的收获

今天最初只是在调整诗文看起来居不居中、横线粗不粗、输入区该放在哪里；到晚上却开始讨论《全宋词》的标点法、词谱的正格变格，以及《谢新恩》的不同传本。排版越精细，底本文字的不确定性就越显眼。**软件已经能把内容显示出来，不代表内容就天然具备供算法使用的结构。**

同样，前端布局也不能靠不断堆积特殊 CSS 把所有截图修到满意：居中有独立的测量规则，分割线由表示边界关系的布局层负责，消息动画和输入框有各自组件；争议留给可撤回的试验，验收后及时合并封板。

不过 Poeticus 的目标仍是一个可以阅读、提问、展示工程能力的产品，不是重新编纂一部《全宋词》。**把问题识别出来、把来源保留下来、把修订变成可追踪的工作，就已经是软件工程可以提供的价值。** 不必由一个人把所有词作逐一校订到完美，才能继续做下一个版本。
