# Poeticus 开发日志｜2026-10-11

> 今天没有继续扩展阅读器功能，主要完成了 MCP 的第一次动手实验，并重新讨论 Poeticus 后端的调用关系与可读性。实际交付是一项已合并的 MCP 接口与测试；LangGraph 改走 MCP、跨机器部署和后端代码梳理仍处于讨论或规划阶段。

## 一、把现有证据查询工具接入 MCP

沿用 [#185](https://github.com/montricwang/poeticus/issues/185) 的学习计划，从 MCP Inspector 的本地连接、工具列表与调用开始，逐步将 Poeticus 已有的 `lookup_allusion`、`lookup_reference` 暴露为 MCP Tools。过程中遇到过从仓库外直接运行脚本导致 `backend` 模块无法导入的问题，改为从项目根目录通过 `python -m backend.mcp.server` 这一模块入口运行。Inspector 的角色可类比 FastAPI `/docs` 的工具调试界面，但它是独立客户端。

[PR #229](https://github.com/montricwang/poeticus/pull/229) 已合并（`4bb1312`），主要增加：

- `backend/mcp/server.py`：注册两个 MCP 工具，沿用已有 `EvidenceService` 和 `CNKGraphProvider`，限制输入长度及证据返回数量；不另写一套查询业务逻辑。
- `tests/test_mcp_server.py`：使用 Fake Provider 验证工具发现、两种查询、无命中、非法输入与 Provider 异常。
- `requirements-dev.txt`：加入 MCP SDK 开发依赖，不改变生产依赖。

本地 MCP Client 的实际输出确认能列出两个工具；模拟查询得到 `ok`，不存在的查询得到 `no_hit`。开发者报告关联 pytest 通过；提交 `eaa7f31` 的 GitHub Actions 中 **Tests、Python lint、Python types、English commit subjects 均通过**。

**验收边界**：这些结果证明 MCP 注册和模拟调用链有效，不能据此宣称真实 CNKGraph 接口、独立进程上的正式 MCP Server 调用或远程连接已经通过验收。此 PR 未修改原有 LangGraph Agent。

## 二、重新理解 MCP 与现有后端的关系

今天澄清了一个容易误会的地方：把工具「MCP 化」，不等于原来的 Agent 必须立即改用 MCP。当前存在两条入口：

```text
现有 LangGraph → execute_tools() ──┐
                                  ├→ EvidenceService.search()
新增 MCP Client → MCP Server ─────┘    → CNKGraphProvider.search()
                                         → CNKGraph HTTP API
```

`EvidenceService` 目前主要负责统一查询入口和按名称选择 Provider；`CNKGraphProvider` 才负责 HTTP 请求以及将第三方结果转换为项目内部的 `EvidenceItem`。两个入口分别创建自己的 Service 实例，但共用相同的类和 Provider 实现。后续接入更多证据来源时，可以遵守 `EvidenceProvider` 的 `search()` 接口，而不必全部继承同一个实体父类。

进一步讨论了求职与未来部署：如果 Web／Agent 在甲骨文云服务器运行，而部分检索或计算能力保留在本地电脑，那么让 LangGraph 通过 MCP 调用独立工具服务就有明确的实践意义。本地 `stdio` 与跨机器的 HTTP 连接需要分别设计和验收。**今天只形成了这个后续方向，没有修改 LangGraph 调用链，也没有部署跨机器 MCP 服务。**

## 三、记录后端代码「能运行，但难以读懂」的问题

阅读 `Chat → LangGraph → EvidenceService → CNKGraphProvider` 时，发现当前代码增长速度明显快于项目负责人理解代码的速度。此前已经在改进静态检查与注释语言，但函数自身的职责、调用者和返回路径仍不够直观；仅靠 AI 对话临时解释，不能解决下一次接手时再次看不懂的问题。

因此新建 [#230](https://github.com/montricwang/poeticus/issues/230)：**后端核心调用链、函数职责与必要注释的分批梳理**。首批从聊天入口、LangGraph、Evidence 和 MCP 开始，重点是能让具备基础 Python 知识的读者从入口追到实际执行函数。优先改进准确命名、关键函数的简短职责说明及必要的「为什么」注释；结构性重构另以真实问题和回归证据决定，不机械给每个函数加长篇教程。Retrieval 内部的专项问题继续归 [#182](https://github.com/montricwang/poeticus/issues/182)，避免重复。
