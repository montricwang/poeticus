## 一、先兑现昨天的决定：把已经跑起来的工程骨架理顺

昨天的结论不是“开始大重构”，而是：先从真实代码流理解现有系统，只有在职责已经明显混杂、重复规则已经产生维护成本时，才做小规模、可验证的整理。

今天早上连续完成了六轮结构清理。

### 前端：让 `App.tsx` 回到协调者角色

[PR #91](https://github.com/montricwang/poeticus/pull/91) 将原先集中在 `App.tsx` 里的聊天会话、持久化、赏析、目录 / 作品加载等职责拆到独立 Hook 和组件中。

这次不是为了追求“文件越短越好”，而是把几条真正不同的状态流分开：

- 聊天会话与消息操作由会话 Hook 管理；
- 对话持久化从页面布局里抽离；
- 作品目录 / 正文加载独立；
- 整首赏析独立；
- `App` 继续负责把这些状态和桌面 / 移动端界面组合起来。

Commit：[`e7bfcd37`](https://github.com/montricwang/poeticus/commit/e7bfcd37b6a7d8224164da1135dd9a7ce3857cc4)。

### 后端：把 Python API 与 AI 代码真正收进 `backend/`

[PR #92](https://github.com/montricwang/poeticus/pull/92) 将 FastAPI 与 AI 实现统一整理到 `backend/` 包中，明确 `backend/app.py`、API 与 AI 模块的边界，同时保持既有路由和 Railway 启动行为不变。

Commit：[`8950c8aa`](https://github.com/montricwang/poeticus/commit/8950c8aa4ba25bf587376efe247b7c9be824bc07)。

紧接着 [PR #95](https://github.com/montricwang/poeticus/pull/95) 删除已经没有必要保留的根目录兼容 shim，内部 import 全部转向 `backend.*`。这里体现了今天反复出现的一条原则：

> **迁移期兼容层可以临时存在，但一旦所有调用者已经迁走，它继续留下就只会制造“到底哪个入口才是真的”这种认知负担。**

Commit：[`a9af50da`](https://github.com/montricwang/poeticus/commit/a9af50dac5e2823e3bf150c20b76f1eb1e21543b)。

Commit：[`f6b276d6`](https://github.com/montricwang/poeticus/commit/f6b276d6d1f897bfbf8439d6aef5113ef5637abf)。

## 二、真实局域网测试又暴露了一个浏览器能力边界

在本地局域网 HTTP 环境测试时，会话 ID 初始化失败。原因不是业务逻辑，而是 `crypto.randomUUID()` 在非 secure context 中并不总是可用。

[PR #98](https://github.com/montricwang/poeticus/pull/98) 增加 `crypto.getRandomValues()` fallback，使局域网 HTTP 也能正常初始化会话。

Commit：[`2b48f7ee`](https://github.com/montricwang/poeticus/commit/2b48f7eeab0a52e9baa74295ff04713dce0ec923)。

这个小问题和下午的 Alook 排查其实很像：浏览器能力不是抽象的“Web 标准支持 / 不支持”二分，而会受到 secure context、浏览器壳、viewport 行为等具体运行环境影响。真机和真实访问方式仍然不能被桌面 localhost 替代。

## 三、把“诗歌像出版物，界面像软件”落实成字体和排版基线

上午另一个重点是字体。

先有 [PR #97](https://github.com/montricwang/poeticus/pull/97) 做自托管文学字体比较实验；形成正式方案后这个实验 PR 关闭，没有合并。随后 [PR #99](https://github.com/montricwang/poeticus/pull/99) 建立正式字体栈：

- 拉丁 UI：Inter Variable；
- 苹果中文 UI：PingFang SC；
- 其他平台中文 UI：自托管 Noto Sans SC Variable；
- 文学正文：Noto Serif SC Variable；
- 生僻字补充：HanaMin。

Commit：[`3373a844`](https://github.com/montricwang/poeticus/commit/3373a844876bb4b7bebc994f6008f18a793708ab)。

这里明确了一条长期视觉原则：

> **诗歌是“出版物”，界面是“软件”。**

文学正文可以有宋体、字距和呼吸感；搜索、按钮、状态提示等软件控件仍然使用清晰的无衬线体系。不需要为了“古典感”把整个网站做成仿古卷轴。

接着 [PR #100](https://github.com/montricwang/poeticus/pull/100) 收紧词牌、小序、作者与正文之间的垂直节奏，并把阅读器字号、行高、字距等集中到 `.poem-reader` 调参区。以后调整阅读排版不必在多个 TSX className 里寻找零散数值。

Commit：[`212317ff`](https://github.com/montricwang/poeticus/commit/212317ff4829363db09308df85471bb93a7f5570)。

## 五、一下午几乎重做了移动端讨论体验

下午的主要工作集中在 [PR #103](https://github.com/montricwang/poeticus/pull/103)。

最初曾尝试 [PR #101](https://github.com/montricwang/poeticus/pull/101) 的“底部书页分栏 / discussion dock”方向，但随着手机键盘、可用高度、空对话与已有消息高度变化不断加入约束，这个结构越来越难维护。#101 最终关闭，未合并。

#103 最后形成的结构更简单：

### 手机

手机上的阅读和讨论是两个全屏工作区。

- 阅读页继续保持挂载；
- 打开讨论后，DiscussionScreen 覆盖阅读页；
- 手机主要使用淡入淡出，不再让整页横向滑动；
- 输入区位于讨论页底部，消息只有一个内部滚动区。

### iPad / 平板

768–1023px 仍使用与手机相同的“全屏阅读 / 全屏讨论”结构，但保留左右滑动切换。

今天专门讨论过要不要让 iPad 重新变成“正文在上、讨论在下”。最后暂时不这样做，因为那会重新引入第三套布局结构和 dock 高度所有权问题。当前更倾向于：**只有真的证明 iPad 需要同时看正文与聊天时，再为它增加独立结构。**

### 桌面

1024px 起进入阅读 + 伴读双栏：

- 正文独立滚动；
- 对话 / 赏析作为右侧伴读区；
- 宽屏保留约 60dvh 的视觉阅读舞台。

### 目录

目录也按宽度分成三种行为：

- 手机 <768px：全屏覆盖，以淡入淡出为主；
- 768–1535px：左侧 drawer 滑入；
- ≥1536px：目录常驻，通过网格列宽展开 / 收起。

手机目录取消自动聚焦搜索框，避免刚打开目录就弹软键盘；搜索框继续保持移动端 16px 字号，避免 iOS focus auto-zoom。

### 对话与赏析外观

同一 PR 还完成了几项视觉整理：

- 顶部只保留“对话 / 赏析”切换；
- “生成整首赏析”不再长期挤在工具栏里，而放到赏析空状态；
- 赏析去掉 Card、阴影和固定高度；
- 用户消息编辑态改成轻量札记式；
- 划词引用改成细竖线旁引；
- 讨论区输入框上方恢复轻微渐隐，但该层不接管点击。

最终合并 Commit：[`96a3bca5`](https://github.com/montricwang/poeticus/commit/96a3bca556bd2319fe777e41a8b694cb523dbbbf)。

## 六、今天最有价值的一次排错：问题不是“iOS WebKit”，而是 Alook

#103 中最消耗时间的一段，是手机键盘收起后页面出现白 / 灰横带、上半部分没有恢复、触控似乎失效，直到手动滚动才重新正常。

一开始很容易把它理解为通用的 iOS / WebKit viewport 问题，于是尝试过：

- `visualViewport` 高度同步；
- 根节点高度改写；
- `interactive-widget=resizes-content`；
- `svh` / 稳定 viewport；
- 键盘关闭后的滚动 / hit-testing recovery；
- 多轮 delayed recovery。

这些 workaround 不但没有真正解决问题，某些版本还让键盘打开时聊天区直接变空。

后来用户才确认：此前主要是在 **Alook** 中测试。重新使用真实 Safari 与 iOS Chrome 后，这个问题都没有复现；更关键的是，Alook 自己底部的浏览器工具栏也会在键盘关闭后被顶住，说明异常已经发生在浏览器壳自身，而不只是 Poeticus DOM。

因此最终决定：

- Safari + iOS Chrome 作为移动端主要基线；
- Alook 的键盘 viewport / 工具栏恢复异常不再作为 Poeticus 的侵入式兼容目标；
- 所有为这个问题加进去的 root height、VisualViewport、theme-color 等 workaround 全部撤回；
- 保留真正有产品意义的全屏 DiscussionScreen 重构。

这个过程值得记录，因为它说明：

> **兼容问题首先要缩小责任边界。不能因为“在 iPhone 上发生”就把问题提升成“iOS WebKit 通用缺陷”，更不能让一个第三方浏览器壳的异常反过来决定整个应用根布局。**

## 七、两个问题没有继续硬磨，而是明确留到后面

#103 收口时还有两个“已经可用，但值得专门做”的问题：

- [#104 优化手机端目录与讨论切换动画的视觉质感](https://github.com/montricwang/poeticus/issues/104)：当前 fade 仍有轻微残影 / ghosting 感，后续单独比较时长、easing、图层合成和深浅色，不在 #103 中继续凭感觉调参。
- [#105 让作品目录分页数量随可用视口高度自适应](https://github.com/montricwang/poeticus/issues/105)：当前固定分页数量在较矮屏幕上会让下方结果藏在滚动区里，用户未必意识到还有内容。未来考虑用可用高度、实际列表行高和合理上下限动态计算 `limit`。

把这些单独记 Issue，而不是继续往已经很大的 #103 塞，是今天另一个重要的收口动作。

## 八、一个按钮位置问题，让“布局所有权”变得非常具体

#103 合并后，手机发送按钮仍显得偏高。

一开始直觉会去找：

`top`、`bottom`、`translateY`。

实际却没有任何一个“发送按钮位置参数”。

真正原因是三层间距叠加：

1. 外层 DiscussionScreen 已经为 safe area 留了底部空间；
2. ChatComposer 又有 `py-3`；
3. 按钮行还有 `pb-1`。

三个值单独都合理，但叠起来就不自然。

[PR #106](https://github.com/montricwang/poeticus/pull/106) 没有给按钮再加一个 `translate-y` 补丁，而是重新明确责任：

> **safe area 由最外层负责，Composer 不重复垫底。**

Commit：[`64339ac9`](https://github.com/montricwang/poeticus/commit/64339ac92078af5153a81f1279e714a664327343)。

这几乎可以当作今天下午前端工作的缩影：很多 UI Bug 并不是“缺一个参数”，而是**同一个空间被多个层级共同拥有**。

## 九、赏析区：先和对话统一，再处理生成结果的“闪现”

随后 [PR #107](https://github.com/montricwang/poeticus/pull/107) 处理电脑端赏析体验。

原先“对话”没有消息时是自然高度，而“赏析”空状态 / 生成中仍带较大的最小高度，所以两个同级视图切换时体量不一致。现在赏析改为与对话一致的高度模型：没有内容时自然高度，有长内容时才使用共享上限并内部滚动。

另一个问题是生成结果一次性返回后整块突然出现。

后端 `/api/analyze` 仍然一次返回完整 JSON，没有为了动画改成流式接口；前端在收到结果后负责展示动画：

- 字符快速错峰淡入；
- 下方区块使用可视区触发，避免在屏幕外提前把动画播完；
- 切到对话再回来不重复播放；
- `prefers-reduced-motion` 下关闭动画。

最终 Commit：[`ffd6493f`](https://github.com/montricwang/poeticus/commit/ffd6493f91acb989165ff76c35780b7f8eadfdbd)。

目前仍有一个非阻塞视觉瑕疵：**词语注释部分偶尔仍有瞬间出现的感觉**。已经记录，但今天不继续追。

同时又明确了一个更大的后续方向：未来可能把“赏析”从右侧伴读区移动到正文下方，成为阅读流的一部分。届时：

- API、赏析数据结构、内容组件和动画能力可以继续复用；
- `fillAvailableHeight`、右栏 `max-height`、内部滚动、`border-l` 等布局参数应重新评估，不能机械搬过去。

因此当前右栏赏析只需要做到协调、可用，不值得在即将变化的布局壳上无限抛光。

## 十、下午最后一轮：开始主动防止“前端参数考古学”

做完一下午 UI 后，用户提出一个很准确的问题：

> 前端的屎山是不是和后端不太一样——改版以后很容易留下很多莫名其妙的配置，之后也不敢乱调？

今天的实际代码已经给出了答案。

后端技术债常见的是：

> **逻辑不知道从哪里来。**

前端技术债则经常表现为：

> **画面不知道由谁决定。**

一个按钮位置可能同时由：

- 父容器 flex；
- 自身 padding；
- 祖先高度；
- safe area；
- breakpoint；
- overflow；
- viewport；
- 浏览器壳行为

共同作用。

这也解释了为什么 AI 辅助 UI 开发尤其容易产生“补偿层”：

> 按钮高了 → `translateY(6px)`  
> iPad 不对 → 再加 media query  
> Safari 看着怪 → 再加 viewport workaround

每一次局部修补都可能让画面暂时正确，但最终没有人知道哪个参数是真正的 owner。

因此今天结束前专门做了 [PR #108](https://github.com/montricwang/poeticus/pull/108) 的 **UI 参数收尾**，目标不是再重构一次，而是把真正有产品语义的参数从普通 spacing 中识别出来：

- 集中 1024px / 1536px 两个交互模式 breakpoint；
- 给手机目录 fade、tablet drawer slide、discussion fade / slide、desktop grid resize 分别命名；
- 提取共享 easing；
- 对话与赏析共用一个桌面最大高度参数；
- 左右两栏共用一个 60dvh 阅读舞台最小高度；
- 给手机正文 `pb-24` 留下 why 注释：为右下浮动讨论按钮让出最后几行；
- 删除 `index.css` 中已经失效的旧 `chat-message-enter` 动画规则。

Commit：[`1e578176`](https://github.com/montricwang/poeticus/commit/1e57817689c94febb012a7797576f259e6e39faa)。

有意**没有**为了“看起来干净”去删除 `h-165`、`min-h-155` 等尚未证明失效的空状态高度。清理历史遗留不等于猜测性删代码。

今天形成的参数维护原则可以写成一句：

> **注释解释为什么这个值必须存在，不解释这个值是多少；重复且必须同步的参数只保留一个 owner。**
