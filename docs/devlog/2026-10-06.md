# Poeticus 开发日志｜2026-10-06

> **今日主线：** 今天第一次把 AI Eval、Evidence 边界和 Text Retrieval 串成一条工程路线。上午用 Seed Eval 看清“典故检索”和“前代文本候选发现”不是同一个问题；中午一度把 Retrieval 做成偏研究型的 Corpus / Benchmark / 多模型比较，随后主动撤回；下午到晚上完成 Werneror/Poetry 全量画像、Work / sentence Chunk、Qwen3 Embedding 本地加载，以及可断点续跑的全量向量生成器。

## 一、Seed Eval 开始真正约束 Agent

[PR #118](https://github.com/montricwang/poeticus/pull/118) 建立 Seed AI Eval 基线，并补齐 reference evidence、工具预算耗尽后的收尾等能力。

这一轮最重要的结果不是“多少 Case 通过”，而是把问题分开：

- 人物、故事、典故性短语适合 `lookup_allusion`；
- 带明显字面锚点的前代成句可以由 `lookup_reference` 提供候选；
- 高度压缩、反用、跨句重组不能靠继续调 Prompt 稳定补齐。

因此后续问题被重新定义为：

> **Poeticus 是否需要一个专门负责前代文本候选发现的 Text Retrieval？**

这成为 [Issue #119](https://github.com/montricwang/poeticus/issues/119) 的主线。

## 二、一次主动撤回：不把 Retrieval 做成研究项目

中午曾经沿着“既然要评测，就把实验做完整”的方向，考虑同时建立 Benchmark、hard negatives、多个 Embedding 模型和多种 Chunk policy。

相关 PR #121、#125、#128 曾进入历史，但随后主线被主动恢复到更早的可信基线；当前 `main` 不保留那套 Retrieval 实现。[PR #131](https://github.com/montricwang/poeticus/pull/131) 负责重新对齐文档与当前状态。

这里形成了今天最重要的停止线：

> **为了决定产品是否值得做一件事，不能先让验证本身膨胀成另一项同等规模的研究工程。**

我们已经有 intertext Eval。真实 Retrieval 搭好以后，可以直接测产品真正运行的链路；没有必要再单独制造一个替代环境。

模型选型也因此收缩：先用一个强、现代、许可清楚的默认方案；只有真实结果出现系统性问题时，再用领域模型做反例检查。

## 三、Retriever 的职责终于明确

今天固定下来的核心定义是：

> **向量检索不是文学知识库，也不是“判断化用”的机器；它只是前代文本候选发现器。**

职责链路：

```text
当前词句
↓
Text Retriever
↓
Top-K 前代文本候选
↓
DeepSeek / Agent 比较、判断、解释
```

因此 Retrieval hit 只是候选证据，不自动等于“来源已证实”。

同时拆开两个容易混淆的问题：

1. **Corpus Chunking**：前代语料离线怎样切；
2. **Query Strategy**：当前作品哪些片段在运行时拿去搜。

第一版 Query Strategy 暂不增加“哪些句子值得查”的前置分类器。诗词本身很短，提前过滤节省不了多少，却可能在 Retrieval 之前损失 Recall。

## 四、Werneror/Poetry 成为第一版 Retrieval Corpus

当前 Draft [PR #132](https://github.com/montricwang/poeticus/pull/132) 建立 Werneror CSV → Work JSONL 的导入基线。

本地全量结果：

- 作品：853,385 首；
- 空字段：0；
- 含 `?` 的作品：5,742 首；
- 完全重复记录：28 条；
- 五个公开来源探针全部命中。

第一版 Work 只保留：

```text
work_id
title
author
dynasty
content
source
source_record_id
```

没有因为上游还能提供更多信息，就提前把它做成文学知识库。

## 五、sentence Chunk 基线落地

语料画像显示：

- clause 级约 942 万；
- sentence 级约 482 万。

当前先采用 sentence baseline：按 `。！？!?` 结束，逗号和分号保留在句内。

真实生成结果：

- Chunk：4,822,054；
- 平均 5.651 Chunk / Work；
- 无 Chunk 作品：0；
- 最长 Chunk：132 字符。

Chunk 保留 `work_id` 和 `[start, end)` 原文 offset，因此候选句可以回查整首作品。

sentence 只是第一版 baseline。BERT-CCPoem 的训练单元更接近古典诗歌单行；如果真实 Eval 证明 Qwen + sentence 在某类关系上明显失败，再派生 clause 数据即可，不构成 Work 层返工。

## 六、Qwen Embedding 链路真实跑通

晚上通过 ModelScope 下载并从本地加载 `Qwen/Qwen3-Embedding-0.6B`。

最小 smoke test：

- device：CPU；
- 默认输出：1024 维；
- “客舍青青，特地添明秀”在三个候选中把王维相关句排到第一；
- cosine 约 0.582。

这只证明：

```text
中文诗句 → Qwen → 向量 → cosine → 排序
```

链路可用，不把三选一结果当成正式 Retrieval 质量证明。

今天还确认了 Query / Document 可以非对称编码：Corpus 文本直接编码，未来 Query 可以带固定 retrieval instruction。具体 instruction 尚未冻结。

## 七、全量 Embedding 先做成可复用构建产物

今晚最后完成了可断点续跑的全量 Embedding builder：

```text
4,822,054 sentence chunks
→ Qwen3-Embedding-0.6B
→ 512 dimensions
→ normalized float16
→ 每 10,000 条一个 NumPy shard
```

纯向量约 4.6 GiB。

输出：

```text
data/output/retrieval/embeddings/qwen3_0.6b_sentence_512/
├─ manifest.json
├─ shard_00000.npy
├─ shard_00001.npy
└─ ...
```

manifest 绑定语料 SHA256、模型 fingerprint、维度、dtype、shard size 和完成位置；参数或输入变化时拒绝混用旧结果。每个 shard 原子落盘，再次执行同一命令即可续跑。

这里明确了一条架构原则：

> **Embedding 是昂贵的离线构建产物；pgvector、FAISS 或其他索引只是部署形式。**

以后换数据库或重建 ANN，不应因此重新做 482 万次模型推理。

截至本日志写入时，全量任务正在本机 CPU 上运行，**尚未宣称完成**。

## 八、今天明确没有决定的事

仍然待定：

- pgvector 还是 FAISS；
- Exact / HNSW 的具体实现；
- 时间 / 朝代过滤怎样与 ANN 配合；
- Query instruction；
- Qwen 512 维在真实 intertext Eval 上的 Recall；
- 是否值得引入 BERT-CCPoem + clause 对照；
- Hybrid / sparse / reranker。

当前顺序是：

```text
Embedding Artifact
↓
真正的向量检索
↓
复用已有 intertext Eval 测真实系统
↓
只有失败类型证明需要时，再增加复杂度
```

## 九、今天沉淀下来的工程经验

1. **不让评测反客为主。** 已有 Eval 能回答问题时，不再为了严谨另造一套 Benchmark。
2. **模型选型不默认等于模型联赛。** 先用强默认方案，只检查最可能推翻它的反例候选。
3. **Corpus Chunking 与 Query Strategy 分开。** 离线表示和在线检索策略可以使用不同粒度。
4. **可重建不等于应该反复重算。** 昂贵派生结果需要 shard、checkpoint、manifest 和来源指纹。
5. **复杂度由真实失败购买。** 不因为“以后也许有用”提前上文学知识库、多模型联赛、Hybrid、Reranker 或专门向量数据库。
