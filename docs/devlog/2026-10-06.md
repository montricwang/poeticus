# Poeticus 开发日志｜2026-10-06

> **今日主线：** 建立第一轮 Seed AI Eval，并让评测真正反过来照出数据、Agent、Tool 与现有架构的边界。过程中没有追求“把测试集全部跑绿”，而是逐步区分 Ground Truth 错误、代码 Bug、Routing 缺陷和能力缺口。最终 PR #114 合并，Seed Eval 阶段收口；下一阶段转向 Text Retrieval / RAG Benchmark。

## 一、从“想做 Eval”开始，先补评测材料

最开始并没有现成可用的 Eval Dataset。直接凭印象写几十道题容易得到一个好看的题库，却不一定覆盖 Poeticus 真正困难的地方。

因此沿用了此前 EPUB 数据工程中已经验证过的工作方式：

```text
私人 normalized JSON
→ 批量画像
→ 可读 Markdown 报告
→ 人工观察
→ 调整抽样脚本
→ 候选集
→ AI 辅助初标
→ 人工复核
→ 小规模 Eval Dataset
```

这一轮重点使用私人编者注作为“困难问题候选来源”，而不是把出版物注释直接当作 Ground Truth。画像先回答覆盖率、长度、重复、来源形式和不同词集的分布，再从相对干净的结构池中抽样。

在标注过程中，最初把“来源角色”和“文本复用形式”混成一个标签，后来拆成两个轴：

- `source_role`：predecessor_text / allusion_source / explanatory_reference / later_parallel / uncertain；
- `reuse_form`：near_quote / adapted_quote / compressed_cue / narrative_allusion / transformed_use / none_or_unknown。

这个调整不是为了 taxonomy 完整，而是因为单轴标签已经无法解释真实样本。

## 二、第一轮对照：不是“Agent 一定比 No Tool 好”

Runner 比较两条链路：

- `control_no_tools`：同模型、同 Poeticus Prompt / context，但禁止 Tool；
- `current_agent`：走当前 LangGraph Agent。

这一阶段没有加入 bare model；当前目标只是测“现有 Agent + Tool 相比同 Prompt 无 Tool 到底增加了什么”。

第一轮 8 条代表性关系 Case 很快暴露出几类不同问题：

1. **两边都能答对：** 常见知识或明显文本关系，Tool 不一定带来增量；
2. **模型本身会答、Agent 反而失败：** Tool 决策和执行链可能降低质量；
3. **模型和 Agent 都错：** 需要继续区分是 Tool 没能力、Agent 没调用，还是题目本身有问题；
4. **Agent 调 Tool 后答对：** 才能说明这一类 Evidence 真正带来增量。

因此后续不再用一个总分描述结果，而是开始看 Process。

## 三、Eval 先发现了产品 Bug：Tool budget 后泄漏 DSML

“片片轻鸥”一题中，Agent 连续两次查询未命中；达到 Tool budget 后，模型仍想继续调用工具，最终把 DeepSeek 的内部 DSML Tool 协议当普通正文返回给用户。

这不是文学知识问题，而是 Agent robustness bug。

修复后：

- Tool budget 用完时，最后一轮不再向模型暴露 Tool Schema；
- Prompt 明确要求直接收束回答；
- 非流式与 SSE 都拦截内部协议泄漏；
- `tool_results` 改为保留本次请求内的累计结果；
- Eval Runner 增加 Tool Call、参数、Tool Result 和 Evidence 摘要。

这一改动让后续失败可以继续拆开判断：

> 是没调用、查错词、Tool no_hit，还是查到证据却没用好？

## 四、Eval 又发现“尺子自己也可能错”

“片片轻鸥”最初 expected 沿用了私人编者注中的错误文字，把杜甫《小寒食舟中作》的一联混写成“片片轻鸥落闲幔”。

复核原诗后，正确文本应为：

> 娟娟戏蝶过闲幔，片片轻鸥下急湍。

因此 Dataset 修正，而不是继续改模型来迎合错误 expected。

这件事把一个原则变得很具体：

> 出版社注释、外部数据库、AI 初标和人工整理都只是不同等级的证据；Eval Dataset 自己也必须允许被质疑和修正。

## 五、“食牛”把 Routing 与 Tool Coverage 分开了

“未满三朝已食牛”最初两条链路都没有稳定找到《尸子》相关来源。

直接 Probe CNKGraph 后发现：

- `lookup_allusion("食牛")` 能命中正确材料；
- 换成更长的 `食牛之气`、`虎豹之驹` 反而 no_hit。

因此这里不是“Tool 没能力”，而是 **Routing / Query Formulation** 问题。

随后调整 Agent：

- 用户问短词 / 短语“从哪里来、是什么典故”时优先考虑典故 Tool；
- 查询词优先抽取最短且有辨识度的典故锚点；
- no_hit 后最多再缩短一次，不无限改写近似长句。

最终回归中，“食牛”正确调用 `lookup_allusion` 并利用证据回答。

## 六、从 qingshang 找回 reference retrieval，而不是马上造新 RAG

“片片轻鸥”属于另一类问题：它不是人物故事典故，而是前代诗句的近似改写。

回看旧项目 qingshang 后确认，当时已经接过 CNKGraph `/api/tool/reference`，用于前代成句 / 化用候选；这与现有 `lookup_allusion` 是两条不同路径。

重新 Probe 后得到清楚边界：

- `客舍青青` 等保留明显字面锚点的关系，reference retrieval 表现较好；
- “片片轻鸥落晚沙”如果只提交目标短句，可以找到杜甫“片片轻鸥下急湍”；
- “未满三朝已食牛”这种高度压缩，reference 很弱，但 allusion 能补；
- “一弦弹尽仙韶乐”这种反用，现有两类 Tool 都不稳定；
- “才下眉头，却上心头”之类较大改写也可能漏掉真正来源。

于是 Poeticus 新增第二个通用 Tool：

- `lookup_allusion`：人物、故事、典故性短语；
- `lookup_reference`：前代成句、近似文本、改写与拆取重组候选。

reference 结果明确标为 candidate，不把“相似”自动等同于“已证实化用”。

## 七、为什么没有继续把 BERT-CCPoem 塞进同一个 PR

用户想起旧项目还试过 BERT-CCPoem：它可以把古典诗词编码成向量，用于语义相似检索；这可能补 reference retrieval 对较大文本距离的不足。

但这里选择停止，没有为了当前 Eval 继续引入向量库。

原因不是 BERT-CCPoem 没价值，而是它已经属于新的能力建设：

```text
Seed Eval
→ 暴露现有 Tool 的能力边界
→ 记录新的 Retrieval 假设
→ 另开独立 Benchmark / Feature
```

如果为了让固定 Case 全绿继续加入 embedding、向量库、rerank、hybrid search，这个分支会从“建立评测基线”膨胀成新的搜索系统，也会逐渐把 Eval 当成训练题。

因此新建 #119，下一阶段先做 Text Retrieval / BERT-CCPoem Retrieval Benchmark；只有证明存在稳定增量，再决定是否进入生产 RAG。

同一轮还记录了 #120：同一请求内重复执行完全相同 Tool Call 的低优先级优化。

## 八、第一轮 Seed Eval 的最终状态

PR #114 最终形成的阶段成果包括：

- Seed Eval 数据契约与 Runner；
- 私人编者注画像 / 候选挖掘脚本；
- `control_no_tools` 与 `current_agent` 对照；
- Tool Call / Tool Result / Evidence Process Trace；
- Tool budget 后的安全收尾；
- allusion routing 改进；
- CNKGraph reference Evidence Provider；
- `lookup_reference` Tool；
- 对应回归测试。

PR #114 已 Squash and Merge。

这轮结果没有被总结成一个“Agent 得分”。更有价值的是已经形成了失败分类：

```text
Ground Truth defect
Code / Agent bug
Routing / Tool-use defect
Capability gap
Acceptable uncertainty
```

以后遇到 Eval 红灯时，先分类，再决定是修 Dataset、修代码、补 Tool，还是仅进入 Roadmap。

## 九、今天形成的工程经验

今天对 Eval 的理解从“项目写好了以后出题考试”变成了“开发过程中的诊断探针”。

它可以同时照出：

- 数据和标签是否可信；
- 产品已经承诺的能力是否真的工作；
- Agent 的 Tool Routing 是否稳定；
- Tool 本身的覆盖范围；
- 当前架构还缺哪些能力；
- 哪些失败应该现在修，哪些只需要进入 Roadmap。

评测框架可以领先于项目当前实现，但不能把“尚未实现”误当成“代码坏了”。更不应该为了让固定测试集全部变绿，持续把新能力塞进同一个分支。

**当日阶段结果：** 第一轮 Seed AI Eval baseline 已建立并完成一次真实“发现问题 → 修复 → 回归”的闭环。下一阶段不继续调这批 Case，而是把 Text Retrieval / RAG 作为独立问题重新开始。
