## Retrieval 从概念进入真实全库诊断

今天继续沿着 #119 / #134 推进 Text Retrieval。最大的变化是：不再只讨论“Embedding 应该有用”，而是已经能拿真实 Corpus、真实 Artifact、真实已知互文案例去看正确来源到底排在哪里。

当前 Exact Search 需要特别区分两个概念：

- 传统文本 exact / lexical match：比较字面、词项、n-gram 等；
- 当前代码里的 Exact Search：对所有允许参与的向量逐个计算相似度，不经过 ANN 近似索引。

所以 Exact Search 依然属于 Dense Vector Retrieval，只是它没有 FAISS / HNSW 这类加速层。

## 朝代过滤已经能用，但边界也暴露出来

当前只有 dynasty metadata，因此先用朝代做粗过滤。

现在允许：

- 明确早于目标朝代的作品；
- 类似“唐末宋初”这种开始于目标朝代以前、跨入目标朝代初期的过渡标签。

暂时排除：

- 同朝代；
- 并行政权；
- 明确更晚时期。

这样已经能避免周邦彦查询把自己、后世作品排在前面。

但同朝人物先后依然无法处理。比如李清照查询范仲淹，两人都标成“宋”，当前规则就会把范仲淹一起排除。这个失败说明长期应该补作者 / 作品年代，而不是继续堆更多朝代字符串规则。

另外 Exact Search 已经会先判断整个 shard 是否包含任何可参与排名的行；没有候选的 shard 直接跳过，不再读取 .npy。

目前查询仍然慢，主要不是只有向量计算：每次还要扫描 Work / Chunk JSONL 重新构建 row mask。它适合当诊断 baseline，不值得现在为它做生产级优化。

## Sentence Retrieval 的真实结果比“好 / 不好”更细

今天拿几个已有互文关系做 probe：

### 近似直接引用：sentence 很强

“画船听雨奈无眠” → 韦庄“春水碧于天，画船听雨眠”：

- 正确来源可到 rank 2 / 3；
- cosine 大约 0.70。

“蜡烛到明垂泪” → 杜牧“替人垂泪到天明”：

- 正确来源可到 rank 1 / 2；
- cosine 大约 0.78。

说明 sentence baseline 并不是普遍不行。

### 局部化用占整句一半：容易被句内其他内容稀释

“片片轻鸥落晚沙” → 杜甫“片片轻鸥下急湍”：

Corpus sentence 是：

```text
娟娟戏蝶过闲幔，片片轻鸥下急湍。
```

正确来源约 rank 445，cosine 约 0.51。

这给了很具体的证据：不是“Qwen 不懂诗”，而是需要比较 clause 粒度是否能减少上下文稀释。

### Corpus 版本差异也是 Retrieval 误差来源

查询“客舍青青”时，Werneror 王维《渭城曲》里是：

```text
渭城朝雨浥轻尘，客舍青青杨柳春。
```

而当前 Eval / 常见版本使用“客舍青青柳色新”。

对 Corpus 自己的这个版本做 probe，正确作品大约 rank 560，cosine 约 0.56。

这件事固定了一个边界：

> Werneror 是候选发现 Corpus，不自动成为权威底本。

以后候选真正要作为“原文”或决定性证据引用，且文本存在冲突 / 来源不清时，再做可靠来源核对；没有必要联网核对每一个候选。

## 因真实失败而增加 clause + BERT 对照

Clause 已全量生成：

- Work：853,385；
- Clause：9,425,173；
- 平均 11.044 / Work；
- 最长 34 字符；
- 无空作品。

现在 Artifact 对照固定成三路：

1. Qwen sentence 1024d；
2. Qwen clause 1024d；
3. BERT-CCPoem clause 512d。

BERT-CCPoem 不是“模型联赛”，而是 sentence / Qwen 已经出现真实失败后才引入的领域模型 challenger。

同时新增 manifest-driven comparison runner：同一个 query / probe 可以直接穿过三套 Artifact，比正确来源的 rank 和 cosine，不再为模型差异另造随机 benchmark。

## Embedding Artifact 的心智模型今天彻底理顺

离线流程：

```text
Werneror
→ Work JSONL
→ Sentence / Clause Chunk JSONL
→ Tokenizer
→ Embedding Model
→ Vector
→ normalize
→ float16
→ .npy shards
→ manifest.json
```

Artifact 不是“某个数据库”，而是昂贵计算之后可以独立保存、复用的构建产物。

当前 .npy 只装数字，例如一行 1024 维向量；原文仍然在 Chunk / Work JSONL。二者靠稳定 row / chunk_id 对应。

manifest 负责说明“这批数字到底是什么”：

- 来自哪份输入；
- 用什么模型 / fingerprint；
- 什么 chunk policy；
- 多少维；
- dtype；
- 是否 normalize；
- 哪些 shard 已完成；
- shard hash 等。

所以：

> .npy 保存数据，manifest 解释并约束这批数据是什么。

以后可以把同一批 Artifact 导入 pgvector、FAISS、Qdrant 等，而不用重新跑 Qwen。

## AutoDL 4090D 上的构建与传输

Clause Qwen 正在 RTX 4090D 上构建。

早期 batch 64 大约 6 秒 / 10,000-row shard；改到 256 后约 2 秒 / shard。

继续测试 512 时，显存只有约 3.3 / 24 GB，GPU Util 约 87%，功耗约 276 / 425 W，仍有明显余量。下一步可以继续观察 1024 是否还有吞吐收益；判断标准应该看 chunks/s / shard time，不是单纯追求显存占满。

Builder 每个 shard 先写临时文件再 atomic rename，所以正式 `.npy` 出现时就是完整 shard。利用这一点，本地可以在远端生成的同时不断 scp 新 shard，不需要等 18 GiB 全部生成后再一次性搬。

最终 manifest 应在构建完成后再同步一次，因为构建期间它还在变化。

## RAG 的整体心智模型也重新梳理了一遍

RAG 不是“向量数据库”本身。

最简单地看：

```text
Retrieval
→ 把相关资料找出来

Augment
→ 把资料放进 LLM Context

Generation
→ LLM 基于资料回答
```

Dense Retrieval 只是 Retrieval 的一种做法。

传统检索也一直存在：

- exact string / phrase；
- 倒排索引；
- TF-IDF；
- BM25；
- character n-gram 等。

Embedding 的变化是：不要求字面完全重合，而把文本映射成向量后比较模型学到的相似性。

它更灵活，但也更不可控。Rank 445 正好说明向量不是“更高级所以一定更准”。

## 存储、索引、检索是不同层

今天把几个经常混在一起的东西拆开了。

### 原文

可以存在：

- JSONL；
- PostgreSQL；
- SQLite；
- 其他文档 / 数据库。

### 向量

当前在：

- `.npy` Artifact。

以后也可以写进：

- pgvector；
- FAISS index；
- 其他 Vector DB。

### 索引 / 搜索

当前：

- Exact vector scan。

未来：

- pgvector HNSW / IVFFlat；
- FAISS Flat / HNSW / IVF / PQ 等；
- 或其他 ANN。

“向量存在哪里”和“怎么搜”不是同一件事。

## pgvector 和 FAISS 的定位

pgvector 更像：

```text
PostgreSQL row
= chunk metadata + text + embedding

SQL filter
+ vector ORDER BY
+ LIMIT
```

所以朝代、作者、source 等业务条件与向量检索天然在一个查询体系里。

FAISS 更像专门的 Vector Index：

```text
Query Vector
→ FAISS
→ vector / chunk ids
→ 回 PostgreSQL / Corpus Store
→ 取正文和 metadata
```

它不是严格意义上的完整数据库，而是专门把“几百万 / 几千万向量里快速找邻居”这件事做得很好。

纯向量算法工具箱方面 FAISS 更丰富，尤其 IVF、PQ、GPU、大规模索引；pgvector 的优势主要是 PostgreSQL 业务数据、过滤、事务和 SQL 集成。

## Poeticus 允许大胆尝试多索引 / 多后端

今天一个很重要的业务判断：

> 越稳定、越静态的数据，越适合预计算、复制、多索引，甚至多后端。

Poeticus 的两个天然条件：

- 古诗 Corpus 基本固定；
- 朝代 / 作者等 metadata 基本固定。

因此我们可以大方尝试：

- 按朝代 / 时间范围预分索引；
- BM25 / n-gram 一套；
- FAISS 一套；
- pgvector 一套；
- sentence / clause 多套 Artifact / Index。

同步成本不会像电商 / 社交系统那么严重。

电商 / 社交数据持续变化，价格、库存、权限、删除、审核等如果在多个索引间不同步，会变成产品错误；Poeticus 没有同等级别的实时一致性压力。

客服 Agent 也常类似：产品手册、FAQ、SOP 这类相对静态知识适合 RAG；订单状态、库存、余额这类实时信息应该直接调 API / DB Tool。

## 增量更新也不用每次全量重算

首次建库：

```text
全 Corpus
→ 全部 Chunk
→ 全部 Embedding
→ 建 Index
```

以后新增资料通常：

```text
新增文档
→ 新 Chunk
→ 只计算新增 Embedding
→ append / insert 到向量存储与索引
```

真正容易触发全量重算的是：

- 换 Embedding 模型；
- 改 Chunk policy；
- 改向量维度；
- 某些 Index / 量化结构需要重训；
- 大量更新 / 删除导致索引需要重建。

## 下一步很可能是 Hybrid Retrieval

Poeticus 的互文检索天然有两类：

### 字面高度接近

例如只改一两个字：

```text
片片轻鸥落晚沙
片片轻鸥下急湍
```

这种 Lexical Retrieval 可能非常强，不一定需要 Dense Embedding 才能抓到。

### 字面变化更大

例如：

```text
才下眉头，却上心头
眉间心上，无计相回避
```

Dense Retrieval 更有机会补 lexical 的漏召回。

因此未来更像：

```text
Lexical Retrieval
+
Dense Retrieval
↓
Candidate Fusion / 去重
↓
DeepSeek 判断关系
```

而不是让向量检索单独包打天下。

## Query 怎么切，也是独立门道

Corpus 怎么切与 Query 怎么切继续分开。

比如：

```text
客舍青青，特地添明秀。
```

Query 可以：

- 整句查；
- 分句查；
- 整句 + 分句都查；
- 提取更短的特征短语查。

所以需要关心的不是只有 Corpus sentence / clause，而是运行时 Query Strategy。

多粒度查询可能是很自然的路线：

```text
整句 → Dense
分句 → Dense
分句 / 特征短语 → Lexical
↓
合并候选
```

## 分词属于哪里

今天还讨论了古汉语分词。

需要先区分：

- Embedding 模型内部 tokenizer：把文字变成模型 token id；
- NLP / Search 里的 word segmentation：把文本切成词 / 短语，服务 lexical retrieval、关键词分析等。

后者属于 NLP 的文本分析能力，放在检索工程里则属于 Document / Query Analysis。

古汉语确实可以尝试 Jiayan 一类专用分词，也可以比较通用分词器；但对 Poeticus 最值得先测的也许反而是不分词的 character n-gram。

因为诗词近似引用经常只是改一两个字：

```text
片片
片轻
轻鸥
...
```

字符级 n-gram 不需要先解决“轻鸥是不是一个词”这种语言学边界，就可能已经很适合互文召回。

因此暂时不启动“古汉语分词工程”，而把它当成可替换 Retrieval component：

```text
character n-gram
vs
Jiayan
vs
通用分词
```

只有真实 Eval 证明需要，才继续投入。

更高一层的问题其实是：

> 怎样把输入拆成最有利于召回互文关系的单位，而不是怎样得到语言学上最正确的分词。

## 上午后续：多粒度结论开始形成

三套 Artifact 已经完成第一轮对照，两个代表性 Case 给出了互相相反、但非常有价值的结果。

### Case 1：局部化用被 sentence 上下文稀释

查询：

```text
片片轻鸥落晚沙
```

已知前文本：

```text
片片轻鸥下急湍。
```

结果：

- Qwen sentence：rank 445；
- Qwen clause：rank 2；
- BERT-CCPoem clause：rank 3。

这说明把 Corpus 从 sentence 切到 clause 后，局部互文不再被前半句上下文稀释。这里真正起决定作用的是 Chunk 粒度，而不是换领域 Embedding 模型。

### Case 2：化用跨两个 clause 压缩信息

查询：

```text
蜡烛到明垂泪
```

已知前文本：

```text
蜡烛有心还惜别，替人垂泪到天明。
```

结果：

- Qwen sentence：rank 1；
- Qwen clause：rank 10；
- BERT-CCPoem clause：rank 6。

这里 clause 反而丢掉了“蜡烛”与“垂泪到天明”跨分句共同组成的线索，所以 sentence 更好。

因此目前不再问“sentence 还是 clause 谁更优”，而是接受：

> **多粒度 Retrieval 是由真实失败买出来的，而不是为了架构复杂度主动堆出来的。**

当前只保留两种主要检索粒度：

```text
sentence + clause
```

命中后再回 Work / 整首作品取完整上下文，不继续扩张更多 Chunk 层级。

### BERT-CCPoem 暂时降级为实验对照

当前两个 Case 中：

- 第一例 Qwen clause 2，BERT clause 3；
- 第二例 Qwen clause 10，BERT clause 6。

有小幅胜负，但远小于 Chunk 粒度造成的 445 → 2、1 → 10 的变化。

所以当前更合理的判断是：

> **先把 Retrieval 结构做对，比继续寻找“更懂古诗”的 Embedding 模型更重要。**

BERT-CCPoem 已经完成 challenger 的主要任务：证明领域模型没有稳定压倒 Qwen。除非后续代表性 Case 出现系统性优势，否则不再为它增加生产复杂度。

## Lexical Retrieval 收敛为 character n-gram + BM25

上午进一步区分了两个层次：

```text
文本怎样表示成词项？
→ character n-gram / 分词

这些词项怎样排序？
→ TF-IDF / BM25
```

因此 Lexical Retrieval 不需要在“字符级近似检索”和“BM25”之间二选一。当前最自然的 baseline 是：

```text
character n-gram
→ inverted index
→ BM25 ranking
```

这样既适合古诗中常见的一两字改写、近似引用，又能覆盖求职时需要理解的主流 sparse retrieval 机制。

暂时不单独做 TF-IDF 产品实现，也不提前投入 Jiayan / 通用分词器比较。后者只有在 character n-gram + BM25 的真实 Eval 暴露不足时再引入。

因此当前 Retrieval 主线进一步收敛为：

```text
                 Query
                   ↓
         ┌─────────┴─────────┐
         ↓                   ↓
 Dense Retrieval       Lexical Retrieval
 Qwen sentence+clause  char n-gram + BM25
         ↓                   ↓
         └─────────┬─────────┘
                   ↓
          Candidate Fusion
                   ↓
                DeepSeek
```



### BM25 全量 sentence 索引

本地完成 Werneror sentence Corpus 的 character 2-3 gram + SQLite FTS5 BM25 全量索引：

- sentence Chunk：4,822,054；
- Work：853,385；
- 最终数据库：1,672,269,824 bytes（1,594.8 MiB，约 1.56 GiB）；
- 核心建库时间：200.0 s；
- 吞吐：约 24,106 Chunk/s；
- 输出：`../poeticus-data/output/retrieval/lexical/bm25_sentence_2_3`。

此前 100k 样本索引为 38.86 MiB，线性外推约 1.83 GiB；全量实际更小，说明当前 2-3 gram 方案在 sentence Corpus 上没有出现不可接受的索引膨胀。至此，Lexical baseline 的工程可行性已基本确认，下一步转向真实互文 Case 的召回质量验证。
