## 二、值得记住的问题与解决过程

### 1. 整首诗的引用没有及时更新（#17）

**现象：** 选择一个字时正常，拖选整首诗或在正文外松开鼠标时，右侧引用可能没有及时更新。

**原因与修复：** 旧实现只在诗歌段落的 `mouseup` 处理选区，并要求 Range 两端严格落在同一个正文文本节点上。新实现追踪阅读区域内开始的 pointer 操作，等待最终选区，把实际 Range 与诗歌正文 Range 求交集，再计算 `text/start/end`，保持与 FastAPI 的 `poem[start:end] == text` 校验一致。[对应提交](https://github.com/montricwang/poeticus/commit/64534c067dc0fa9d4c7dfcd801ce076ac5014ad3)。

**经验：** 浏览器 DOM Selection 的边界不等于肉眼看到的文字边界；应根据所需正文范围截取，而不是假设用户精准选中单一 Text 节点。

### 2. Markdown 引用诗句多出空行（#16）

**现象：** 引用中的标准 Markdown 硬换行（行末两个空格加换行）被显示为额外空白行。

**修复：** 对照精确复现样例，移除 `AssistantMarkdown` 段落上的 `whitespace-pre-wrap`，由 Markdown 解析出的换行结构负责展示，避免 CSS 再保留源文本换行。[对应提交](https://github.com/montricwang/poeticus/commit/97689292e9546925dbcd361da18a9fe980397bf5)。

**经验：** 先确认 Markdown 语法、渲染后的 DOM 和 CSS 三者分别做了什么；不要通过全局删除空行破坏真正的诗歌分节。

### 3. 引入 Graph 后，需要重新建立测试边界

**现象：** 原本的 `/chat` 回归测试容易与新的路由及真实模型请求混在一起。

**处理：** 在 API 模块边界模拟 Graph，把 Router 评测与普通接口回归分开；相关变更经 [#20](https://github.com/montricwang/poeticus/pull/20) 合并。加入 LangSmith 方便日后核查执行路径，但不能用追踪代替测试。

**经验：** 接口契约测试、路由分类测试和真实模型质量评测是不同层次，不应互相依赖外部服务。

### 4. 消息操作与异步体验需要分别处理

**处理：** 复制、重新生成、编辑历史消息依次落地；`ChatPanel` 拆成更小组件。流式生成由后端真实 Token 驱动，轻微入场动画和滚动跟随由前端处理；阅读历史时不强制滚到底部，尊重系统的减少动画设置。[流式提交](https://github.com/montricwang/poeticus/commit/8559e23e134b0520f7007c76de85b99266937dd6)、[动效提交](https://github.com/montricwang/poeticus/commit/4b4e09feac90f2e5f83bad5299a47c594577bf46)。

**经验：** “真实数据何时到达”“消息容器怎样出现”“何时跟随滚动”是三个独立问题。部分失败、断线恢复等验收仍以 [#6](https://github.com/montricwang/poeticus/issues/6) 为准。

## 三、当日决定及留下的边界

- **分流先于复杂 Agent。** 初版 `classify_intent` 已使用 LLM 作结构化意图分类，Graph 分别处理细读、查证和澄清；查证节点当日仍是占位，不把框架存在误认为检索已经可用。
- **让原文与展示规则分开。** [#25](https://github.com/montricwang/poeticus/issues/25) 当日仅在已有生成入口的 Prompt 中加入中文引号规则，没有全局重写文本；后续新增生成入口必须继续覆盖。简繁混排及引文保真另见 [#34](https://github.com/montricwang/poeticus/issues/34)。
- **保留完整决策链。** Issue 记录问题、复现和验收，Commit 记录实际代码变更，本日志串联当天的因果和经验；复杂架构取舍再单独写 ADR。
