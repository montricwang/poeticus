## 二、值得记住的问题与解决过程

### 1. “长期上下文”其实混在了一起

**现象：** #9 最初容易被描述成“长期上下文”或“记忆”，但真实需求只是：用户在同一首诗、同一场连续对话里追问“刚才那个典故”时，模型需要看见前几轮。

如果直接从“记忆”出发，很容易顺势引入：

- Server-side Session；
- LangGraph Checkpointer；
- Summary Memory；
- Retrieval Memory；
- 数据库；
- 跨设备同步。

这些都比当前问题大一层。

**重新框定：**

> 当前要解决的是**同一 Conversation 中的短期 Conversation State 如何跨用户轮次传递**。

在比较 Client-carried history、服务端 Thread、Sliding Window、Summary Memory 和 Retrieval Memory 后，v0.1 选择 **Client-carried bounded history**：

- 只携带成功完成的完整 user → assistant turn；
- 最近最多 6 个 turn；
- 单条历史消息最多 4000 字符；
- 历史总长度最多 12000 字符；
- 客户端不能通过 history 注入 `system` role；
- 编辑、重试、重新生成旧 turn 时截断其后的未来分支。

[对应实现](https://github.com/montricwang/poeticus/commit/1181eab2f7f6b006d01d011edf67290e75e52473)。

**经验：** 先给问题命名，再选技术。Conversation State、Persistence 和 Memory 看起来都在“保存上下文”，但解决的不是同一个问题。越早把它们混成一个“大记忆系统”，越容易为 MVP 提前支付不必要的数据库与状态管理成本。

### 2. “刷新后聊天还在”也不是一个 localStorage 小功能

**现象：** 初看 #8 似乎只是“按 poemId 把 turns 放进 localStorage”。但如果直接这样实现，临时存储方案会反过来决定长期产品模型：一首诗是不是只能有一个聊天？清空消息是不是等于新建 Conversation？以后跨设备时怎样迁移？

**重新建模：**

> **Poem 是 Poeticus 的主要领域对象；Conversation 是围绕阅读发生的上下文。**

v0.1 只在 UI 中暴露“每首诗当前的一场 Conversation”，但存储结构仍保留：

- `conversationId`；
- `poemId`；
- schema version；
- turns；
- Draft / selection。

`localStorage` 被明确视为当前的 persistence adapter，而不是长期权威数据源。将来需要账号、跨设备、多 Conversation 或服务端生命周期管理时，再迁移到 [#40](https://github.com/montricwang/poeticus/issues/40)。

**经验：** 临时实现可以轻，但领域语义不要因为临时实现而变形。今天多保留一个 `conversationId` 和明确的生命周期语义，能够避免未来为了从 localStorage 迁移数据库而重新定义整个产品。

### 3. 切换作品时，“状态已经在 React 里”不等于“已经可靠持久化”

**现象：** 第一版本地持久化在切诗时仍存在时序风险：如果只依赖状态变化后的 effect 落盘，当前作品可能先被切换，随后才发生保存。

**处理：** 在切换作品的动作边界直接保存当前 active poem 的 Conversation / Draft，再恢复目标作品；同时把持久化所需的 ref 从 render 语义中分离。[相关提交](https://github.com/montricwang/poeticus/commit/23aac7c1816c40ef167d21cabe85f743e88d22ab)、[相关提交](https://github.com/montricwang/poeticus/commit/a49dc4f7ff2d0601d3e4c28d11cda4b2e8682522)。

**经验：** 对“离开当前对象前必须保存”的状态，操作边界往往比泛化的响应式 effect 更可靠。尤其当对象 ID 本身也在变化时，要明确保存的是“切换前的谁”。

### 4. 保存 Conversation 不等于刷新后继续生成

**现象：** #8 可以恢复已经完成的消息，但用户在 SSE 正在生成时刷新页面，浏览器连接仍会断开。不能因为“会话持久化完成”就声称“生成任务也可恢复”。

**当前处理：** v0.1 将 pending / streaming turn 恢复为明确的 interrupted 状态并允许重试；真正的 resumable generation 独立记录在 [#46](https://github.com/montricwang/poeticus/issues/46)。

长期需要给一次生成建立独立于浏览器连接的 `run_id / generation_id`，让服务端继续执行并允许客户端重新查询或订阅。

**经验：** Message persistence、Conversation persistence 和 Generation lifecycle 又是三层。把状态问题分层以后，降级策略也会更清楚：当前做不到“继续生成”，就明确中断，而不是伪装成完整恢复。

## 三、下午的产品与工程路线讨论

今天下午没有继续增加代码功能，而是集中讨论“作品库到底应该多大”以及 Poeticus 作为求职项目应该怎样分配工程投入。以下属于**方向与边界**，不是当日已实现能力。

### 1. 不把“大而全”作为前台产品价值

调查了多个公开诗词数据项目后，进一步确认“作品数量最多”和“阅读质量最好”不是同一个目标。

当前更倾向于：

> **公共空间做有人编选的精品馆藏；长尾作品通过外部发现能力进入；用户自己读过或收藏的内容形成个人书架。**

概念上可以分为：

```text
Curated Library
  精品馆藏，承担较高质量责任

Personal Library
  用户自己读过、收藏或讨论过的作品

External Discovery
  馆藏外按需寻找的作品
```

这使“外部有几十万首可检索”与“正式馆藏只放认真选择的作品”可以同时成立，而不必要求 Poeticus 为每一条外部脏数据背书。

### 2. 严格质量标准不等于必须清洗整个世界

过去项目中，大量时间消耗在 EPUB、脚本清洗和追求“每个字都不能错”。今天讨论后明确一个更适合 Poeticus 的质量原则：

> **不降低正式馆藏的正确性标准，而是缩小对外承诺的范围。**

未来即使导入 40 万或 85 万级语料，也可以把它们作为：

- `imported_unreviewed`；
- 带 source / provenance；
- 带质量状态；
- 用于 ETL、Search、RAG 和工程实验。

它们不必自动进入精品阅读馆藏。

因此，大规模数据工程的责任重点是**可追踪、可分层、可查询和可维护**，而不是人工逐首总校勘。

### 3. v0.1 暂不为了数据库而上数据库

当前约十几首到未来几十首、约百首级的精品馆藏仍适合静态 JSON：

```text
frontend/src/data/poems/
├── index.json
└── *.json
```

在这个规模下，引入 PostgreSQL、Migration、分页 API 和部署依赖不能解决真实瓶颈。

数据库留到后续大规模语料接入时再引入，让架构变化由真实数据规模驱动：

```text
Static JSON
   ↓
Large External Corpus
   ↓
ETL / Normalize
   ↓
PostgreSQL
   ↓
Index / Search API
```

这样既能学习数据库，也能解释为什么系统是在这个时点演进，而不是为了技术栈名词提前增加复杂度。

### 4. Poeticus 的近期最高目标重新明确为“项目驱动学习 + 求职展示”

十月底以前，Poeticus 不以商业化成熟度为最高目标，而是要同时做到：

1. 有一个真正可以演示的古典诗词 AI 阅读产品；
2. 让 Agent、Tool、RAG、Data、Skill、Evaluation 等简历能力都落到真实项目经验。

因此新增 [Roadmap](../roadmap.md)：

- **v0.1：** AI 阅读闭环；
- **v0.2：** Data / PostgreSQL / ETL / Search / Minimal RAG；
- **v0.3：** Skills / Agent Orchestration / Evaluation；
- **Spikes：** MCP / Rerank / Cache / Memory 等只在有学习价值时做短实验，不自动进入主架构。

一个技术词准备写进简历前，至少达到：

> **做过 → 遇到真实问题 → 能解释设计取舍。**

## 四、当日决定及留下的边界

- **短期 Context、持久化、长期 Memory 分层。** #9 已完成短期多轮 Context；#8 已完成 v0.1 本地 Conversation persistence；服务端存储、跨 Conversation Memory 分别留给 #40、#45。
- **Poem-first，而不是 Chat-first。** Chat 是进入作品的一种阅读方式，不把 Poeticus 默认演进成通用 ChatGPT 克隆。跨作品比较 [#43](https://github.com/montricwang/poeticus/issues/43) 也应作为显式 Multi-poem Context，而不是偷偷拼接多个聊天历史。
- **v0.1 不引入数据库。** 数据库等到大规模外部语料真正改变访问模式后再做。
- **AI Eval 已进入 Backlog，但不阻塞 v0.1。** [#42](https://github.com/montricwang/poeticus/issues/42) 先保留 10–20 条固定问题的基线方向，后续用于 Prompt / Tool / Evidence 改动前后的回归。
- **产品馆藏与工程语料池可以有不同质量承诺。** 正式馆藏可以继续严格校对；大规模外部数据通过 source、review status 和 provenance 明确标记，不伪装成已校版本。
- **Roadmap 记录阶段目标，Issue 记录具体任务。** 远期 RAG、Data、Skill、MCP 等不继续塞入 v0.1 当前 Issue；实施时再拆独立闭环。
