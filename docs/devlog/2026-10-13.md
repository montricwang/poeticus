## 一、修复中文 Squash Commit 绕过检查的问题

检查发现，10 月 12 日合并的 [PR #232](https://github.com/montricwang/poeticus/pull/232) 生成了中文标题的 Squash Commit `64707778`。原因不是原 CI 把中文识别成英文，而是 `.github/workflows/english-commit-subjects.yml` **只监听 `pull_request`**：PR 内的英文 Commit 可通过检查，GitHub 在合并时却默认拿中文 PR 标题生成最终提交。仓库 `main` 也没有启用分支保护。

今天保留旧提交的备份分支 `backup/main-before-english-squash-fix-20261013`，从父提交 `200eccf` 重建与 #232 **相同内容树**的英文提交 `56b6180`，随后补交 [10 月 12 日 Dev Log](2026-10-12.md)（`593a960`）并更新英文提交标题 Action（`9f2d5c9`）。新的工作流同时监听 PR 和 `main` push，文档明确：**push 检查只能在提交进入主线后发现问题，不能代替合并前核对 Squash 标题或 GitHub Ruleset**。

这次更新通过带预期旧 SHA 的 `force-with-lease` 改写了 `main` 历史；随后新提交上的 English commit subjects、Python lint、Tests 都通过。原 #232 文档内容没有回退，旧 SHA 在备份分支保留。此举属于针对最新主线提交的一次受控历史修正，不能当作日常重写共享 `main` 的通用流程。

另一个方向是独立的 **Poeticus Code Atlas** 可视化原型。此前已有 ZIP 形式的 v4 原型，尝试用 AST 提取部分导入/调用关系、展示源码并可视化代码结构；但审查时发现其功能分组与部分架构连接仍依赖硬编码，不能当作真正从源码自动推导出的系统架构。今天进一步确定：初始只显示**仓库真实目录树**，必要时隐藏 `__init__.py` 等噪声；由用户人工创建、命名、保存合理的单系群/并系群，关系随聚合汇总；避免系统提前按 HTTP、Agent 等主观功能分类。新版设计还涉及自然收敛布局、Codicons 与保留源码查看能力。**Code Atlas 不在 Poeticus 仓库内，也没有取得完整仓库的真实分析与最终交互验收**；不能与今天已合并的代码重构混为一谈。

## 三、Agent：从图节点转向节点内部职责

阅读 `backend/ai/graph.py` 后，明确现有 `agent_decide → route_agent → execute_tools` 的 ReAct 拓扑没有必要为整理代码而改动。针对工具定义、状态类型与执行边界创建 [#251](https://github.com/montricwang/poeticus/issues/251)，并通过 [PR #253](https://github.com/montricwang/poeticus/pull/253) 落实首批改造：

- 将面向模型的工具 Schema、`TOOLS`、`TEXT_RETRIEVAL_TOOL` 和 `available_tools()` 放入 `backend/ai/tools.py`；只有配置 Retrieval URL 才暴露对应工具。不为静态定义引入 ToolRegistry。
- `RouterState` / `RouterUpdate` 更名为 **`AgentState` / `AgentStateUpdate`**；同步 HTTP 和 Eval 消费者，不改 State 字段、合并语义或 Graph 拓扑。
- Agent 和对外 MCP 都复用 `EvidenceService` 返回的 `EvidenceItem`，但**各自整理协议输出**：Agent 管 ToolCall、预算、State 和证据裁剪，MCP 管对外参数限制与响应。因此这一轮**没有抽取共用 Tool Executor**，也没有增建 Registry/Parser 层。
- 对 CNKGraph HTTP 10 秒超时、错误 JSON、地址等补离线回归；现有 404→空结果语义保持不变，是否误吞路由错误仍待真实接口核对。

#253 已合并（`3151b4a`）。PR 记录的本地测试为 **512 passed、1 warning**；Mock/Fake 回归能保护旧契约，但真实 CNKGraph、远程 MCP Client、LLM 和完整浏览器交互仍未验收。[#230](https://github.com/montricwang/poeticus/issues/230)、[#251](https://github.com/montricwang/poeticus/issues/251) 不因一次 PR 自动关闭。

## 四、Retrieval：承认现有实现就是 Poem Retrieval

重新复核 [#182](https://github.com/montricwang/poeticus/issues/182) 时，发现早期审计的几条结论已经过时：字符 n-gram/FTS5 共用规则已有 `lexical_terms.py`，资产路径和哈希已有专属模块，Dense/BM25 通道也已从巨大的 `serving.py` 分离。今天不再照着过时清单重复重构。

更重要的设计判断是：当前 Pipeline 依赖**诗歌 Corpus 的 Work 身份、诗歌文本召回、Work-level RRF、作品自身排除和朝代资格过滤**，不是未来对古籍、词话、辞书、现代书籍都通用的 Local Text Retrieval。围绕这条业务边界完成了连续两个 PR：

1. [PR #254](https://github.com/montricwang/poeticus/pull/254)（已合并，`15bde5e`）：将 `query_strategy.py`、`fanout.py`、`fusion.py`、`eligibility.py` 移入 `backend/retrieval/poem/pipeline/`，更新调用方 import、测试和架构说明，不动检索算法。
2. [PR #255](https://github.com/montricwang/poeticus/pull/255)（已合并，`1d49af3`）：再把 `client`、`server`、`service`、Serving/Channels、Chronology、Metadata、Artifact 等 **13 个实现模块**内聚到 `backend/retrieval/poem/`，并更新脚本、测试及相关文档。旧导入位置不保留空转发层。

两次移动都**保留**现有 `TextRetrievalClient` 等对外类型名、`/v1/retrieval/search` HTTP 契约、`POETICUS_TEXT_RETRIEVAL_*` 配置和索引资产格式；没有为不存在的第二种检索预建 `shared/`、`text/` 或泛用适配框架。#255 最新组合 CI 记录：Python `pytest -q` **512 passed、1 warning**，以及对应 lint、typecheck、前端质量检查通过。

**真实验收仍未完成**：迁移后的 Qwen/FAISS/BM25 Serving Bundle 尚未在本轮重新启动，陆游→杜甫、姜夔→杜牧 canary 的候选排名、来源、时延，以及 Railway → Tunnel → WSL 链路均待核对。#182 仍开放；[#151](https://github.com/montricwang/poeticus/issues/151) 中同作者异本 self-hit 的身份正确性不在目录重构中偷偷修改。

## 六、历史语音与词乐：建立备忘，试听后暂缓

另一场对话从「用 AI 读诗」延伸到更具体的产品目标：让读者在普通话朗读之外，通过粤语感受入声韵尾、通过吴语对照清浊声母，通过注明方案的中古汉语拟音体验历史语音；另把**词乐歌唱**与朗诵区分，讨论现存姜夔词谱的现代译演，以及依据词牌/宫调进行*明确标为现代拟古创作*的 AI 谱曲。

技术上核对过 Azure Speech、Qwen-TTS、切韵 TTS、ACE-Step 等候选和 API/MCP 边界；例如 `edge-tts` 不能直接接受任意自定义 SSML，宫调也不能单独确定失传旋律。新建 [#252](https://github.com/montricwang/poeticus/issues/252) 记录现成入口、限制、试听与潜在最小实验。用户初步听过粤语/吴语方案后评价「都不咋样」，**决定暂缓**：没有统一测试集或完整 API 对照，更没有接入产品、训练或微调模型。

## 七、当前停止线

今天真正进入 `main` 的是 Git 检查修复、10 月 12 日日志补记、源码注释、数字人文资源说明、Agent 边界与 Poem Retrieval 文件归属整理。它们改善了**代码的可读性、职责归属和工程记录**，但不能由 CI 绿灯直接推出外部服务、真实索引或用户体验全部正常。
