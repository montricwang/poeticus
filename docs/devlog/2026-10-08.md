# Poeticus 开发日志｜2026-10-08

> 这份日志记录 10 月 7 日晚到 10 月 8 日凌晨的 Retrieval 上线过程。重点保留实际数字、故障现象、判断变化和最终生产闭环，方便以后复盘服务器选型、服务通信和线上故障。

## 从本地 Retrieval 进入真实 Linux

白天已经完成 Hybrid Retrieval 的主要产品链：

```text
Query Plan
→ Dense sentence / clause
→ BM25 sentence
→ Work-level RRF
→ Candidate Eligibility
→ TextRetrievalService
→ Agent Tool
```

晚上开始处理部署问题。目标很具体：让这套约 85 万首作品的 Retrieval 离开开发机，在一台普通 Linux 主机上长期运行，再让 Railway 上的 Poeticus Agent 通过 HTTP 调用它。

### Serving Bundle 最终体积

metadata v2 重建后，线上真正需要的 Artifact 为：

| Artifact | 大小 |
| --- | ---: |
| sentence FAISS | 1.189 GiB |
| clause FAISS | 2.320 GiB |
| sentence BM25 | 1.557 GiB |
| metadata v2 SQLite | 1.828 GiB |
| Qwen3-Embedding-0.6B | 1.125 GiB |
| 合计 | 约 8.02 GiB |

原始 sentence + clause float16 Embedding 合计约 27.17 GiB。它们继续作为离线构建资产保存，没有上传到 Serving 节点。

FAISS 的 sentence + clause IVFPQ Index 合计约 3.509 GiB。当前参数：

```text
nlist = 512
pq_m = 256
pq_bits = 8
nprobe = 64
```

pq64 的压缩损失过大；pq256 已经达到可部署水平。继续加大 nprobe 对 Recall 改善很小，说明主要损失来自 PQ 压缩本身。当前停止继续围绕参数做细调。

## 服务器选型经历了三次修正

最初为了靠近 Railway SFO，AI 提出了 DigitalOcean SFO3 16 GiB / 8 shared vCPU。用户随后指出第一轮资源验证完全可以先看国内云，这个判断改变了部署方向。

随后又短暂考虑腾讯云上海 8核16G，但很快发现“肯定够用”和“第一台应该怎么测”是两件事。Spike 的价值在于测最低可行规格，因此最终从：

```text
腾讯云上海
2 vCPU
8 GiB RAM
Ubuntu 24.04
50 GiB 系统盘
CPU only
single worker
```

开始。

这个过程当时记入 Decision Register，保留 DigitalOcean 16G、腾讯云 8C16G、腾讯云 2C8G 三次选择的替代关系。决策快照后续统一归入 ADR；当前有效结论见 [ADR-0001](../adr/0001-separate-text-retrieval-service.md)。

## 2C8G Linux Benchmark

实际主机：

- Linux 6.8；
- 2 vCPU；
- 可用内存约 7.4 GiB；
- AMD EPYC 9K65；
- 约 1 physical core × 2 SMT；
- swap 约 1.9 GiB；
- 空机内存占用约 433–505 MiB。

第一轮完整 Serving Benchmark：

### 内存

```text
baseline                46.1 MiB
model                  914.2 MiB
metadata               914.7 MiB
sentence FAISS        2121.7 MiB
clause FAISS          4404.0 MiB
BM25 / ready          4404.0 MiB
post benchmark        5307.4 MiB
```

只观察到约 6 MiB swap，没有持续 memory pressure。

这给出一个很实用的结论：**2C8G 可以承载当前完整 Corpus 的单 worker Retrieval。**

### 冷启动

首次 benchmark：

```text
model load       ≈ 6.57 s
sentence FAISS   ≈ 9.68 s
clause FAISS     ≈ 18.62 s
startup total    ≈ 34.87 s
```

之后重启时，Linux page cache 已经保存了大量文件页，启动明显变快。凌晨一次真实 systemd restart：

```text
model load       ≈ 6.91 s
sentence FAISS   ≈ 8.98 s
clause FAISS     ≈ 2.35 s
startup total    ≈ 18.25 s
```

这也解释了今天反复看到的“同一套代码为什么第二次快很多”：冷启动、文件 page cache、Query cache 需要分开看。

### 单请求与并发

Linux warm benchmark：

- 陆游 → 杜甫：p50 约 255.5 ms，target visible；
- 李清照 → 范仲淹：p50 约 903.7 ms，本轮 target false；
- 姜夔 → 杜牧：p50 约 668.1 ms，本轮 target false。

5 并发：

- wall 约 2802 ms；
- individual p50 约 2030.8 ms；
- p95 约 2795.5 ms；
- throughput 约 1.78 req/s。

因此第一台机器当前更容易先撞到 CPU / concurrency 限制，RAM 仍有余量。早期低流量产品足以使用，暂时没有理由立刻升到 16 GiB。

## 正式形成 Web 与 Retrieval 两个服务边界

当前生产拓扑收敛为：

```text
Browser
   ↓ HTTPS
Railway poeticus-web
   ├─ FastAPI / Agent
   ├─ 3491 首公开词作
   └─ Railway PostgreSQL
          │
          │ HTTPS + Bearer token
          ▼
Tencent Cloud Shanghai
   Nginx :443
          ↓
   127.0.0.1:8787
   Text Retrieval Service
   ├─ Qwen query encoder
   ├─ sentence FAISS
   ├─ clause FAISS
   ├─ sentence BM25
   └─ metadata SQLite
```

Railway Web 保持轻量；Qwen、FAISS、BM25 和 metadata 常驻腾讯云单独进程。

### Retrieval 节点安全边界

最终配置：

- Retrieval 进程由 systemd 管理；
- 服务只监听 `127.0.0.1:8787`；
- Bearer token 放在 `/etc/poeticus-retrieval.env`；
- 环境文件权限 `600`，root-only；
- Nginx 对公网提供 80 / 443；
- 80 用于 ACME challenge，并把其他请求重定向到 HTTPS；
- 443 终止 TLS，再反向代理到 localhost:8787；
- 腾讯云安全组没有开放 8787；
- Railway 保存 Retrieval HTTPS URL 与 token。

Let’s Encrypt 的公网 IP 证书已经签发，Certbot 报告自动续期任务已建立。证书生命周期另开 #167 做第一次实际续期验证。

## 第一次线上 E2E：通信成功，结果却错了

Railway 配置完 Retrieval URL / token 后，线上陆游 Case 已经能返回非常具体的候选：

- 范成大；
- 许有壬；
- 郑岳；
- 陆游自己的同句记录。

这证明：

```text
Railway Agent
→ HTTPS
→ Nginx
→ Retrieval Service
→ Hybrid Retrieval
→ Agent
```

已经真实连通。

但已知目标杜甫“片片轻鸥下急湍”消失了，而且元、明候选进入最终结果。

问题最后定位到当前作品上下文：

```ts
dynasty: null
```

本地 benchmark 一直显式传入 `dynasty="宋"`；线上产品数据库没有逐首 dynasty 字段，所以 Candidate Eligibility 无法排除明确后世候选。

## “全库写宋”很快被否掉

第一反应是：当前公开阅读库以宋词为主，可以暂时统一传“宋”。

用户马上指出实际库里还有：

- 温庭筠；
- 韦庄；
- 冯延巳；
- 李璟；
- 李煜。

因此不能把 3491 首词作统一标成宋。

我们随后直接查询部署节点上的 Werneror metadata：

```text
温庭筠 [('唐', 416)]
韦庄   [('唐', 393)]
冯延巳 [('唐', 113)]
李璟   [('唐', 6)]
李煜   [('唐', 76)]
```

这又暴露了 Werneror taxonomy 的粗粒度：南唐人物也统一标成“唐”。

最后采用的语义是 **Werneror-compatible chronology label**。这个值只服务同一 Retrieval Corpus 内部的粗粒度先后判断，不把它展示成经过考证的作者历史朝代。

## #165：缺少 dynasty 时由 Retrieval 自己补足

最终策略放在 Retrieval Service：

1. 请求里已有 dynasty，直接使用；
2. 当前作品能找到 exact-content alias 时，优先看这些 alias 的 Werneror dynasty；
3. alias 无法解决时，对 exact author 统计 Werneror dynasty 分布；
4. 唯一最高计数作为当前 corpus-compatible label；
5. 最高计数并列或没有已知标签时保持 unknown。

前端继续发送真实状态 `dynasty=null`，没有增加一份作者朝代硬编码表。

CI 通过后 #165 合并。

## 部署阶段又踩了两类很典型的小坑

### 腾讯云访问 raw.githubusercontent.com 卡住

服务器直接 `curl raw.githubusercontent.com` 长时间没有数据。

没有继续折腾代理或 DNS。改为：

```text
本地开发机 git pull
→ SCP 文件到 /tmp
→ 服务器 py_compile
→ 覆盖代码
→ systemd restart
```

后续将这一流程收敛为仓库脚本，私钥显式传入，不使用 SSH 密码。

### systemd active 之后公网仍然 502

第一次 restart 后等了 15 秒：

```text
systemctl is-active → active
HTTPS /health       → 502
```

继续检查发现：

- systemd 进程已经存在；
- Uvicorn 仍在加载 Qwen / FAISS；
- 8787 尚未进入 ready 状态；
- Nginx 此时无法连接 upstream，所以返回 502。

约 18 秒后：

```text
127.0.0.1:8787 LISTEN
local /health 200
public /health 200
```

因此部署检查不能把固定 `sleep 15` 当 ready signal。以后循环请求 localhost `/health`，直到 ready 或超时。

这次故障也把几个常被混在一起的概念分开了：

```text
systemd active
≠ port ready
≠ local health ready
≠ reverse proxy ready
≠ public endpoint ready
```

这些内容已经进入后续教学 Issue #166。

## 最终 Retrieval 验收

新代码部署后，故意发送：

```json
{
  "author": "陆游",
  "dynasty": null
}
```

Retrieval 返回：

```text
rank 6
杜甫《小寒食舟中作》
娟娟戏蝶过闲幔，片片轻鸥下急湍。
dynasty = 唐
chronology_status = clearly_earlier
support_count = 2
```

说明：

```text
dynasty=null
→ Retrieval metadata inference
→ Werneror-compatible 宋
→ chronology eligibility
→ 杜甫重新进入候选
```

当前仍有两个已知边界：

- 许有壬“元”与“宋”在粗区间 1271–1279 重叠，因此 status 为 `overlapping`，按 recall-first 规则保留；
- 两条陆游同句异本 / 重复记录仍会进入候选，继续由 #151 跟踪 canonical self-hit。

## 最终线上 Agent E2E

在线 Poeticus 再问陆游“片片轻鸥落晚沙”的来源，Agent 回答：

```text
杜甫《小寒食舟中作》
“娟娟戏蝶过闲幔，片片轻鸥下急湍。”
```

并进一步指出：

- 陆游自己的同句记录属于自用成句；
- 文本对应支持较强的化用判断；
- 没有明确文献记载时，不把“有意化用”写成已经证实的引用事实。

至此生产链闭环：

```text
线上 UI
→ Railway Agent
→ search_predecessor_texts
→ 腾讯云 Retrieval
→ chronology filtering
→ 杜甫 candidate
→ Agent 判断
```

#164 随后按 completed 关闭。

## 今天留下的工程学习问题

今晚很多时间花在服务器规格、内存、磁盘、冷启动、反向代理、端口和 502 上。这些知识以前没有形成完整心智模型，所以操作时会觉得细碎。

这件事值得单独补课，已经建立 #166：

**从 Poeticus Retrieval 部署理解服务器、存储与服务通信。**

计划重点讲：

- database / index / artifact 的资源影响；
- CPU / RAM / disk 的选型方法；
- cold / warm；
- service-to-service communication；
- localhost / public endpoint / reverse proxy；
- systemd / health / 502 的逐层诊断。

这门课放到 Retrieval 主线之外，避免继续把部署执行和基础概念学习搅在一起。
