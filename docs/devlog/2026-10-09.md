# Poeticus 开发日志｜2026-10-09

> 今天主要没有扩展新的线上文学功能，而是回头检查全项目的代码质量、模块边界和 Agent 的下一阶段方向。工程上把 Retrieval 与 Agent 的一些稳定契约从历史实验和混杂逻辑中分离出来；产品规划上则从“发现一个数字人文工具就研究一个”，转向先列用户任务和能力缺口，再决定复用、自建或暂缓。以下区分已经合并的代码、已完成的调查整理，以及仍未验证的运行状态。

## 一、代码审查从 Retrieval 延伸到整个 Poeticus

昨天的重心还是 Retrieval 的真实部署与文档收口。今天继续 [#182](https://github.com/montricwang/poeticus/issues/182) 所代表的可读性、依赖方向和数据契约审查，发现许多问题不属于某个复杂算法，而在于**稳定规则被放在实验入口里，或者跨层模块依赖方向不清楚**。

### Retrieval：让正式链路不再借用实验 CLI

今天合并了几组边界修复：

- [#187](https://github.com/montricwang/poeticus/pull/187)：提取共用的词项规则、FTS5 查询表达式和 Artifact 哈希函数；离线 BM25 构建与在线 Serving 复用同一语义，诊断 CLI 原本的错误行为仍保留。
- [#188](https://github.com/montricwang/poeticus/pull/188)：把 Qwen Query Encoder、FAISS 和 BM25 Channel 从 `serving.py` 的 Runtime 编排中分离；Manifest 读取与校验也有明确归属。保留独立 Hybrid Eval，不为了文件数量更少而删掉诊断能力。
- [#189](https://github.com/montricwang/poeticus/pull/189)：把 Serving Bundle 默认路径解析移到独立模块，使 benchmark / inspect 工具不再依赖服务启动入口；同时消除重复的 SHA256 实现。
- [#190](https://github.com/montricwang/poeticus/pull/190)：把 Embedding Manifest 的结构和校验放到正式的 `backend/retrieval/embedding_artifact.py`，索引构建器不再从 `artifact_search.py` / `exact_search.py` 等实验脚本间接获得基础契约。
- [#197](https://github.com/montricwang/poeticus/pull/197)：单独提取目标作品朝代标签的来源优先级，保留显式请求 → 当前作品 alias → 作者 Corpus → unknown 的顺序，新增回归测试。

这些改动的目标是**改变代码归属，不改变检索行为**。FAISS / BM25 索引格式、Work/Chunk 对应关系、Query Plan、RRF、Eligibility 和 HTTP Schema 均不作为这轮重构对象。真正的模型与 Artifact 回归仍要与 [#180](https://github.com/montricwang/poeticus/issues/180) 的环境验收区分。

### 全项目：小范围修正真实的依赖与信任边界

随后把审查范围从 Retrieval 扩大到前后端：

- [#198](https://github.com/montricwang/poeticus/pull/198)：把 `ChatTurn`、`HistoryMessage`、`SelectedText`、`PoemAnalysis` 等共用类型放入前端 `types/`，使 Hook / 存储模块不再从 React 展示组件取共享契约。
- [#199](https://github.com/montricwang/poeticus/pull/199)：修正 Evidence Provider 包的 `__init__.py` 命名，补足 Agent、Corpus、CNKGraph Adapter 和 Eval 的模块职责说明。
- [#200](https://github.com/montricwang/poeticus/pull/200)：从 `execute_tools()` 中提取 `_parse_tool_query()`，在真正执行工具前集中校验模型生成的参数；执行循环继续负责预算、错误转换和结果累积。

尤其是最后一项，体现了一个稳定边界：**模型返回的是不可信的工具参数，必须先校验，才能交给业务能力执行。** 不需要为此增加通用 Framework，也不需要修改 LangGraph 的图结构。

## 二、静态检查与中文注释形成统一基线

之前讨论过“怎样让 AI 生成的代码更可读”，今天把一部分要求落实到了持续集成，而不只是人工审查：

- BasedPyright 已在 CI 中检查 Python 类型；[Ruff #193](https://github.com/montricwang/poeticus/pull/193) 限定为 `E4/E7/E9/F` 等基础规则，清理已发现的旧诊断，不一口气开启全部风格限制。
- [#194](https://github.com/montricwang/poeticus/pull/194) 为前端固定 Prettier 格式基线，保留 ESLint 与 TypeScript 检查；CI 只检查，不自动修复或提交。
- [#192](https://github.com/montricwang/poeticus/pull/192) 先把 Retrieval 子系统 30 个 Python 文件的英文解释性注释和 Docstring 改为中文；[#201](https://github.com/montricwang/poeticus/pull/201) 进一步覆盖全项目另外 64 个文件，包括后端、Corpus/EPUB、Eval、前端、测试、SQL Migration 及 Shell/YAML。
- 翻译时继续保留标识符、SQL、命令、工具指令、常用术语及真正的设计约束；Git Commit subject 与 PR 标题仍使用英文，不把“中文可读性”扩大成破坏机器接口的机械翻译。

[#201](https://github.com/montricwang/poeticus/pull/201) 的合并前验证记录：`498 passed`、1 条第三方库 warning；BasedPyright 检查 184 个文件，0 errors / 0 warnings；Ruff、前端质量检查与英文提交检查均通过。这些是**当次 PR 的 CI 结果**，不是本地真实 Qwen / FAISS Service 的验收。

这一轮得到的认识是：可读性不只是变量命名和排版。**稳定契约在哪里、依赖箭头指向哪里、代码能否从入口顺着数据流读懂**，比过度拆分函数更重要。静态检查解决能机械判定的一部分问题，不能替代对数据流和实际行为的审查。

## 三、数字人文：从“逐个挖工具”转向能力规划

今天围绕数字人文外部资源进行了较长时间讨论。CNKGraph、萌典、汉典、CTP、CBETA、CBDB、维基文库、古汉语典故数据集、公开的诗文资源与论文方法，看起来都有价值；但它们的职责彼此交叠，无法靠“哪一家最好”一次性决策。

最初很容易陷入一种“猴子搬玉米”的过程：每发现一个新资源，就去查它还有哪些 API；刚想到自建 Corpus，又发现别人的数据或搜索接口可能已经完成了部分工作。真正缺少的不是资源清单，而是**从用户任务出发的完整能力地图和停止线**。

### 已有资源地图，但还不是完成了工具评测

今天已整理 [数字人文资源地图](../digital-humanities-resources.md)，由 [#184](https://github.com/montricwang/poeticus/issues/184) 跟踪实际验证。它区分：

- 可取得的古籍、诗词、词话数据及外部 API；
- 可以借鉴的检索、典故识别和文献关系建模方法；
- TEI、Web Annotation 等组织文献的标准；
- 只有论文或项目介绍、尚未证明可调用的线索。

必须分别核实**能否访问、能否拿到必要字段、能否合法用于公开产品、是否真的节省工作**。特别是已有的 CNKGraph API 和四月曾调查过的古汉语典故资源，不应因为再次发现它们就把旧工作从头做一遍。今天讨论了若干候选接口，但没有形成一轮可复现的现场 API 对照测试，也没有接入新 Provider。

### Agent Capability Map 已进入主分支

最后确定先回答“Poeticus 需要什么”，再回答“外部有什么”。[PR #203](https://github.com/montricwang/poeticus/pull/203) 已合并，新增 [Agent Capability Map](../architecture/agent-capability-map.md)；[#202](https://github.com/montricwang/poeticus/issues/202) 负责首次核查。

第一版按用户任务划分七类能力：

1. 字词训诂；
2. 典故考证；
3. 文本互文；
4. 古籍原文查证；
5. 文学史事实；
6. 历代评论对读；
7. 文学分析与对话。

这不是规定要实现七个独立 Tool。**Corpus 提供材料与检索，Agent 判断这些材料能证明什么**；某类能力可以复用多个来源，一个 Corpus 也可以服务多类任务。

当前代码中的 Agent 仍是单 Agent ReAct：`lookup_allusion`、`lookup_reference`、条件开放的 `search_predecessor_texts` 共三种工具定义；每次请求最多执行两次真实 Tool Call。整首赏析的 `/api/analyze` 仍由独立模型调用完成，不经过这一工具循环。今天没有提高预算、增加工具，也没有引入 Planner 或多 Agent。

以后的一项能力选型，先写用户任务和最低证据要求，再查现有系统缺的是**资料、检索、判断还是交互**；必要时用半天至一天做小样本 Spike，得出“复用、补充、自建缺口、暂缓或不采用”的结论。不能因为一个数据库还有更多字段就无限追下去。

## 四、求职展示与部署现状重新排序

下午进一步讨论了下一阶段该优先开发什么：更丰富的 Agent、MCP、服务端 Conversation persistence、可恢复生成、写入审批、域名，还是继续扩展数字人文检索。

实地查看 Railway 项目后，确认**Web 和 PostgreSQL 已经部署**：

- Railway `poeticus-web` 仍从 GitHub `main` 部署，检查时处于 `SLEEPING` 状态，没有报告近期部署失败；
- PostgreSQL 处于 `online`；
- Railway 已提供 `https://poeticus-web-production.up.railway.app/`，尚无自定义域名；
- Web 环境中存在 `POETICUS_TEXT_RETRIEVAL_URL` 变量名称，但本次没有读取或验证其实际值，也没有完成公网浏览器 E2E。

**旧腾讯云 Retrieval 实例已经销毁。** 10 月 8 日日志中的完整在线检索与性能数字是当时真实完成过的历史实验，不代表今天依旧可用。当前 [#180](https://github.com/montricwang/poeticus/issues/180) 的本地 Serving、真实 Corpus canary、Railway 断连降级与重新部署选择尚未全部验收。部分 README / `docs/deployment.md` 仍沿用旧主机在线的表述，需要改正。

因此明天不应该把“购买域名”或“再增加 Agent Tool”误当作上线的首要条件。真正优先的是：**招聘方打开现有链接，能否可靠体验作品阅读、AI 对话和可明确解释的降级行为。**

这份次序面向当前求职阶段，不代表全部功能的永久重要性排名。已有工作需要演示证据与可解释性，远比无限延长 Feature List 更紧迫。

## 今天的收获

今天的两条主线表面上很不一样：上午是去掉代码中的不合理依赖，下午是避免被形形色色的数字人文工具牵着走。它们其实都在处理同一个问题——**哪些是系统自己应当掌握的稳定责任，哪些属于可以替换的具体实现？**

对代码，稳定规则应该有明确归属，不能被实验脚本或展示组件偶然持有。对 Agent，Poeticus 必须掌握用户任务、证据契约、工具路由和文学判断，而数据、索引与第三方 API 能复用就复用。

> 先确定要完成什么，再决定由谁来做；先验证当前缺口，再决定增加什么。

今晚的停止线也因此很清楚：不再扩展工具清单，暂不增加生产功能；留下已合并代码、能力地图、开放 Issue 与明天的部署验收计划。真正的下一步，是把已有成果整理成**稳定、可演示、可解释的工程作品**。
