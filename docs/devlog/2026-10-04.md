### 代码审查：哪些资料可能传到互联网

依据 `chore/public-deployment` 中的实际迁移、转换、API 代码，得到以下已验证事实：

1. `db/migrations/0001_corpus.sql` 至 `0003_yusheng_title.sql` 定义 `poems`（阅读作品）、`poem_source_texts`（私人来源证据）；没有 `annotations`、`commentary` 两列。
2. `scripts/corpus/adapter.py` 只将 `content.text`、`content.prefaces` 等转换为正式阅读字段；现代 `annotations/commentaries` 不进入这个转换所得的数据库记录。
3. `backend/corpus/repository.py` 的列表和详情 SQL **仅查询 `poems`**；详情 `body_segments`、`prefaces` 返回正文和词序，不查询来源证据表，不返回 `inline_notes` / `lacunae`。
4. **限制**：没有访问本地 3491 条真实数据的权限，尚不能断言每一条 `body_segments` 与 `prefaces` 均只包含公有领域原作文字；尤其来源 EPUB 的现代整理和标点等使用许可还应依据具体来源核对。字段名称不等于逐条版权保证；不存在逐条人工精校的证据。
5. 现有 `db_import.py --import` 会同时写 `poem_source_texts`，且插入新 UUID，故不适合作为云端公开读库迁移命令。
6. Railway Postgres 当前无公网 TCP 代理，可使用官方 CLI `railway connect Postgres --tunnel-only` 建本地临时 SSH 隧道。避免开放数据库公网端口与将私人词文提交公开仓库。

### 已实现但尚未真实跑源数据的迁移工具

[Draft PR #80](https://github.com/montricwang/poeticus/pull/80) 新增 `scripts/corpus/public_corpus_transfer.py` 和合成测试：

- 显式白名单：只读取并写入 `poems` 的十二列（含本地稳定 UUID、原序、词牌/标题、正文/词序、校审状态和版本），绝不复制 `poem_source_texts`、`inline_notes`、`lacunae`、现代 annotations/commentary。
- `--check` 离线于云端，批量验证数量默认 3491、唯一 ID、排序连续、非空正文、词序格式、质量状态及潜在现代编辑措辞；只输出统计与序号，不输出含全文的报告。
- `--apply --confirm-publish` 必须在用户本地由两条 DB 连接运行；云端必须已停止合成播种。事务只会删除精确识别的测试记录，且导入后用阅读字段 SHA-256 全量核对；发现未知记录或内容漂移即拒绝覆盖；重复运行内容一致则不重写。
- 使用官方 Railway CLI 隧道直接传输，不把原文 JSON 提交到 GitHub、聊天或第三方文件服务。具体 Windows PowerShell 步骤见 `docs/deployment.md`。

**证据等级**：源码字段审查 = 已验证；合成 CI = 待确认最终工作流；用户本地 3491 行预检、云端完整导入、分页搜索、内容许可 = 尚未验证。不能把脚本写好等同于已经发布作品。

### 全量迁移初试：无进度的逐行 SQL 导致长时间等待，已改成 COPY

首次在用户 Windows 本地 Git Bash 执行 `public_corpus_transfer.py --apply --confirm-publish`，输出了 3491 首本地校验统计后等待数分钟，无任何写入进度提示。**没有来自目标数据库的提交确认**，不能据此认为已写入或者必然失败；另一个新开的 Git Bash 窗口没有继承环境变量，属正常进程隔离，不代表原进程的执行情况。建议停止旧版进程，保留 Railway SSH 隧道；新迁移脚本会查询云端，内容已一致则直接确认，否则原事务未提交时按安全规则重试。

分析代码发现旧版 `for row: dest_conn.execute(INSERT)` 会产生 3491 次独立的远程 SQL 往返，加上进度打印缺失，造成用户无法判断是否卡住。**改进已提交到 Draft PR #80**：

- 改用 psycopg3 的 PostgreSQL `COPY FROM STDIN` 批量流式写入，保留原 12 列白名单、UUID、整表 SHA-256 核对、未知云端内容拒绝覆盖，以及单事务的回滚和幂等性。
- 每 500 首展示传输进度、开始/结束校验和提交阶段提示；云端连接超时 10s、锁等待 15s、SQL/COPY 180s，避免无休止等待。重复执行若云库数据相同则提示 `already_identical`。
- 在同一个 Git Bash 终端直接运行导入脚本，程序在缺少目标变量时自行提示粘贴 Railway SSH 隧道的连接 URL，避免跨 Shell 环境变量传递。仅允许目标 `localhost/127.0.0.1:55432`。
- 更新合成测试 FakeCursor/COPY，增加中途中断时的事务回滚测试；更新 `docs/deployment.md` 只保留 Git Bash 的简短流程。真实 SSH 隧道和 3491 首 COPY 尚待本地实践验证，不能把合成测试通过等同于迁移成功。

**密钥注意**：用户此前曾将 PostgreSQL 连接 URL 连密码贴在聊天与截图中，迁移后必须轮换 Railway PostgreSQL 凭证，并检查 Web 服务继续使用有效内网变量。勿把 URL 回传给 AI。

## 三、朋友开始试用后，匿名 AI 的额度真正成为产品问题

网站公开后，朋友遭遇「AI 体验额度耗尽」。核对服务端配置和日志发现，当时 `POETICUS_AI_DAILY_REQUESTS=8` 是**全站所有访客共用的每日额度**，并且整首赏析与聊天一起计数；此前不能将这个 429 解释成每个人只拥有八次。

用户决定改为**全站每日 200 次、每个 IP 每日 20 次**，保留每个 IP 每分钟最多 3 次、单实例同时生成最多 1 次；由 [PR #87](https://github.com/montricwang/poeticus/pull/87) 实现、测试、合并并部署：

- 新增 `0005_ai_ip_daily_quotas.sql`；每日全站额度与每日单 IP 额度在同一个 PostgreSQL 事务中预留。若某 IP 当天已用完，撤销该事务，**不会误扣全站额度**。被接受但随后生成失败或中断的请求仍占相应请求次数。
- 不保存明文公网 IP：以服务端私密 `POETICUS_AI_IP_HASH_SECRET` 对 UTC 日期及可信客户端 IP 做 HMAC-SHA256；密钥缺失或预算数据库不可用时拒绝 AI 请求，而不是绕过额度。只在已核对的 Railway 代理边界内信任 `X-Real-IP`，不直接信任任意 `X-Forwarded-For`。
- 计数按 UTC 日重置，即**北京时间每天早上 8:00**。同一家庭、学校或公司可能共享一个公网 IP，因而共享 20 次。`200` 是请求次数上限，**不是人民币硬预算**；DeepSeek 余额、模型实际费用与自动充值设置需要另外管理。本次限额验证以合成测试为主，没有实际调用模型刷满 200 次。

用户随后指出红色「请求失败」会令正常限流显得像网站故障。由 [PR #88](https://github.com/montricwang/poeticus/pull/88) 将分钟限流、并发繁忙、单 IP 日限与全站日限分别写成较自然的提示，说明等待或恢复时间；前端将 HTTP 429 显示为中性状态，真正的网络或模型故障仍是错误。用户已输入的问题不因这种提示被清空；不以含糊的「系统繁忙」掩盖额度规则，也不要求普通访客「联系发布者」。此外，将浏览器页签标题从开发默认的 `frontend` 改为 `Poeticus`，页面语言设为 `zh-CN`（Commit `b38768c`）。

这里的工程认识来自真实试用：**限流既是后端的预算与并发规则，也是前端需要清楚解释的使用边界。** HTTP 429 是机器状态，呈现给读者时还要区分原因、恢复条件和失败等级。

## 六、八天快速开发后的转向：理解已有代码，再决定是否重构

晚上用户提出一个明确的停止点：项目已经能让陌生人使用，但这八天大量工作由 AI 辅助快速完成，**需要知道现有系统中每一步是谁完成、数据流到哪里，以及出了问题该先查看哪里**。Poeticus 不仅用于作品展示，也将作为后续 AI 应用工程岗位面试的实战案例。

决定从真实用户动作逐条拆解代码，而不是先上 React、FastAPI、PostgreSQL、LangGraph、Railway 各自的通识课程。暂定学习路径：打开网页与前端入口 → 作品目录/搜索/数据库 → 划词问答与 LangGraph/SSE → 直接模型调用的整首赏析与 Pydantic → 浏览器状态、失败恢复与匿名 AI 保护 → GitHub CI、Railway 和部署。每个闭环先说清「谁调用谁、传什么数据、结果去哪」，必要时再进入函数细节和失败路径。

当天的前端导读已经从用户对 Discuz! 旧论坛、日本 Yahoo 门户、手机缩放页面和 EPUB 排版的直觉开始，说明 HTML/CSS/JavaScript 的职责仍然有效；React、Vue 是帮助组织界面和状态变化的工具，DOM 是浏览器可操作的页面结构，TypeScript/TSX 与 Vite 处在开发和构建环节。先建立这层直觉，再正式从 `frontend/index.html`、`frontend/src/main.tsx` 和 `App.tsx` 进入 Poeticus 的实际启动过程；**这属于教学讨论，还没有重构这些文件。**

用户进一步提出在学习中顺便整理包、组件、类、配置及历史脚本。商定采用**「架构导读 + 渐进式重构」**：先理解已运行的闭环，发现确有维护成本的职责混杂或重复规则，再提出最小改法、补测试、验证外部行为不变。现有 `frontend/src/App.tsx`、`api.py`、`intent_router.py` 与配置/迁移脚本是候选检查点，**文件较长不是必须拆分的证据**；不要为追求类、层次或“消除所有胶水”而额外增加抽象。纯重构与修 Bug/加功能分开提交，尤其不能随意删除已经执行的数据库迁移文件。

## 七、验证边界与接下来的主线

- **已交付：** 3491 首公开阅读、v0.1.0 Release、最小匿名 AI 限额保护、额度友好提示、网站页签标题和发布后的仓库状态整理。
- **已知未完：** iPhone 页面与目录问题、iOS 选区同步、语料逐首校勘与来源授权复核、#77 更全面的生产安全/成本核查。按 IP 的限制依赖可信代理链且共享网络会共用额度；单实例并发控制不等于未来多实例的全局锁；请求次数不能代替模型供应商的现金预算。
- **接下来的优先事项：** 暂停新功能堆叠，使用线上已经存在的用户操作理解前端 → HTTP → FastAPI → 数据库/Agent → 部署；在形成可预测的心智模型后，再对确实必要的地方做小规模重构和回归测试。对尚待确认的效果，继续记录为 Issue 而非在 Devlog 中宣称已解决。

**当日阶段结果：** 上午还在确认一个三首合成数据的受控站点，下午已发布可供朋友打开的 Poeticus。上线带来的真实反馈让预算规则、提示语和移动端问题从“预想的风险”变成了具体的工程问题。下一阶段的重点从尽快增加代码，转为能解释代码、判断设计并安全地接手维护。
