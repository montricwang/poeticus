## 一、把目录作为独立的弹性布局，而不是不停调整像素

继续验收 10 月 14 日开发的桌面双栏阅读和目录。在 **1200px 最大版心**下，左侧阅读约 **500px**，中间分割线与间距合计 **50px**，右侧讨论／赏析／目录约 **650px**。目录使用右侧现成辅助区，切换目录时不挤压左侧阅读区；桌面可以连续选诗，移动端选诗后仍关闭抽屉。桌面页头把目录入口放在右上角，按钮显示图标与「目录」文字，收起目录使用向上的 `ChevronUp`。

借助 React Developer Tools、VisBug 和浏览器真实盒模型尺寸，重新区分 React 组件边界、DOM 元素与 CSS 布局职责：`ReaderCompanionLayout` 管双栏及中线；`PoemCatalog` 内部分为标题、搜索、独立横线、作品列表和分页。标题／搜索高度主要由内容决定；横线两侧留适度可伸缩间距；**作品列表使用 `flex-1` 消化剩余空间**，根据列表实际高度与当前 **56px 行高**计算每页条目，而不是让空白任意堆在分割线上。目录下方分页保留独立横线。长词题截断，桌面条目用题名、首句和作者共同定位作品；移除了不必要的首句悬停提示。手机仍保留原有更紧凑的目录样式。

## 二、诗词阅读页：偏上、居中与小序的取舍

短词过少时，原来的垂直居中让书页显得不够稳；但左侧不应逐首追随右侧空对话区的位置。于是给 `PoemReader` 的原有内容容器加 CSS 伪元素，让正文以外的剩余高度按**上方 42%／下方 58%**分配：短词略偏上，长词自动挤掉留白并正常滚动。没有新增 React 布局组件，也不更改诗句本身的行高和字距。

使用 VisBug 检查《扬州慢》时发现阅读滚动区原来只在右侧预留 **8px**，导致标题和正文的中心比底部分割线、翻页导航偏左约 **4px**。改为左右各 **4px**，让词题、作者、底部分割线和「上一首／下一首」真正共用阅读区水平中心线；手机阅读同样不横向溢出。

小序最终采用**最大 400px 的居中版心、`width: fit-content`、多行正常左对齐、浏览器自然换行和 `1.7` 行距**：一行短序的文字本身居中，多行长序左对齐且自动换行，手机按较窄的可用宽度排版。中间试验过 `text-wrap: balance`、收窄到 `26em`、以及按 `Range.getClientRects()` 检查换行后施加 `text-indent: 2em`。后者虽可在桌面／手机根据实测行数切换，但《扬州慢》出现孤零零的末行「也。」，增加了复杂度又未改善体验；**最终移除条件缩进组件及其测量逻辑，也撤销均衡换行**。取舍是保留书卷气但不机械复制纸书段落格式。

## 七、Safari 竖排修复及跨设备版心

在 `fix/home-safari-vertical-20261015` 分支继续 #294，先调查真实 Safari 与桌面模拟视口差异。手机竖排不再依赖容易出错的 RTL 横向滚动定位：正文放入受限视口，推荐块使用左右对称空间进行几何居中。手机采用连续竖排，桌面仍按句逐行排列，跨越 **1024px** 阈值时自动切换，不再保留用户可见的「样式一／样式二」按钮。标点恢复浏览器原生竖排字格，撤销试过的负 margin；正文保持约 **0.12em** 字距。

超长词不在首页强行展示全文：先用浏览器实际宽度测量，能放全词就放全词，否则优先保留完整片／叠，空间不足时再按句读截取；只有发生截取才在词牌下、作者上方标「**节选**」，不修改馆藏正文，也不在末尾加省略号。印章从远离诗文的固定左侧轨道移到实际诗文左缘附近，间隔约 **12px**，不把印章宽度算入正文居中。片间恰好另起竖行时留 **0.5em** 横向间距，片间仍在同一行时使用全角空格。手机正文实际高度与搜索区上方可用空间联动。

新增「选词」调试入口，先后选入《杨柳枝》《菩萨蛮》《水调歌头》《如梦令》《戚氏》《八声甘州》，再补《满庭芳》《兰陵王》《踏莎行》，共**九首**，以短令、长调和分片作为布局样本。用户的 iPhone Safari 后来已能真实显示竖排诗文，说明「正文完全不可见」的症状不再持续；但这**不等于**全尺寸、所有交互和断行结果都已通过 Safari 验收。#294 仍 Open。

## 八、手机智能断行：从像素调整走向明确约束

今天主要时间花在连续竖排的断行取舍。初版曾按标点或短词特例断行：《杨柳枝》四行各七字，《菩萨蛮》有时把「弄妆」等短语拆开。后来删除短词特殊分支，新建 `frontend/src/lib/home-preview-columns.ts`，对所有词统一使用动态规划：给每个候选断点计分，优先完整句号，其次逗号，句中硬拆惩罚更重；同时计入行长参差。动态规划是在既定评分下寻找总代价较小的方案，**不会自行理解词的语义和审美**。

进一步澄清了两条不同层级的规则：

1. **候选约束**：动态测量右侧第一竖行的词牌、「节选」、作者及间距，换算成正文所需字格数；最长正文行的有效文字高度（**不计末尾标点**）应超过它。屏幕物理高度不足时暂允许回退，避免首页一字不显示。正文行高再按最终实际最长行收缩，而不是完全由字数经验公式决定。
2. **候选评分**：避免「雪。懒起画蛾眉」这样行首仅留一个字收束上句，或「关河冷落，残」这样行尾只留下一字开头。给这种孤字断行加惩罚 **100**，在可选方案足够时宁愿换一种行数；标点优先级和行长均衡也参与评分。

曾为了让页面「窄而长」而强制选最少行，后来改成每增加一行罚 **65** 分；反复讨论发现这是把手段误当成目标：《杨柳枝》要从四行变两行，本来是因为四行太短、无法超过右侧标题行，**不是因为两行天然优于四行**。最终**移除 65 分及 `preferFewerRows` 参数**，保留长度约束和断行评分。手机视觉质心算法也试过引入现有 `poem-optical-center.ts`，但其逐字权重模拟不符合原来逐行计算的设计，**已撤销**，现阶段只用 CSS 几何居中；没有动横排阅读器原有算法。

在 **390×844 Chromium 模拟手机视口**重排九首，结果如下（以本轮最后一次本地检查为准）：

| 行数 | 作品 |
| --- | --- |
| 2 | 《杨柳枝》《踏莎行》 |
| 3 | 《如梦令》《菩萨蛮》《戚氏》 |
| 4 | 《水调歌头》《满庭芳》《兰陵王》《八声甘州》 |

移除 65 分后这九首的行数没有变化；`320×667` 矮屏仍能显示搜索区，桌面 `1440px` 继续一句一行。新增孤字用例验证「腮｜雪。」和「，残｜照」两类断行在有选择时得到规避，极窄布局仍允许退让。末轮 **13/13 项相关 Node 测试**通过、TypeScript 通过，ESLint 对相关文件 **0 error／15 条 Tailwind 规范 warning**。**完整 Playwright E2E 仍因 WSL 缺 Chromium Headless Shell 未跑到断言**；这些结果只证明局部逻辑与 Chromium 浏览器行为，不是所有 Safari 机型的保证。

用户的**真实 iPhone Safari 截图**显示同一首《杨柳枝》仍排成**三行**，与 Chromium 390×844 的两行不同。具体原因尚未通过真机盒模型与可用高度读数独立证实；可能涉及浏览器实际视口、字体或页面高度预算，不能直接归罪于动态规划。截图中搜索区下方仍有相当多空白，也提示**整页空间分配可能比继续增加断行惩罚更值得检查**。不要再以某个模拟分辨率的成功推断真机一致。
