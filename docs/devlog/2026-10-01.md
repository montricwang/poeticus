## 二、今天真正暴露的问题

### 1. 过早把局部样本提升为通用 Parser

最初的原型依赖 `h2 → 标题`、`p → 正文`、文本前缀区分注释与评论，确实可以快速抽取部分作者。但不同词集的 HTML/CSS 排版本就有显著差异：有的把词题放在标题的小字中，有的放在楷体子节点中，有的标题内换行，有的另用一个居中的段落。小序和纪年也可能与正文使用相邻的普通段落。

真正的问题不是「少写了几条 if」，而是**一开始没有把输入分布调查清楚，却已把局部抽取逻辑视为全书通用的结构解释**。后续反例被用户逐个发现，AI 被动地跟着修；每增加一条局部特例，都可能掩盖更深的错误抽象。

**调整：** 把全书结构统计与语义提取分成两阶段。先按 22 册统计标题子节点、CSS 声明、相邻段落与无法判断的模板；再决定分册语义规则。DOM/CSS 告诉我们原书怎样区分文字，不能自动保证这些文字在文学上属于「词题」。

### 2. 数据中存在信息，不意味着 Schema 必须容纳它

讨论贺铸时，发现他将所用词调与自命名称的顺序倒置；有的标题还含「亦名」说明。讨论欧阳修《西湖念语》、温庭筠与欧阳修的成套词时，又出现组序、组词关系、别名体系等潜在字段。

如果沿着每个发现都新增字段，词作数据库会逐渐承担词学辞典、文献校勘和作品关系图谱的职责。用户及时提出反问：**这些是不是当前阅读产品真正需要的数据？**

**调整：** 本轮 Poem 只关心一首词的词牌、显示用题名、正文、小序、注释、评论和必要的警告。组序可以有意识地不导入；套词关系、调名异称、系年争议留待未来按需检索和知识增强。`title_raw` 不再放进最终 Poem，但调试阶段保留定位和证据；有意跳过非作品内容，不能把它们误并入某一首正文。

### 3. 自动测试通过，不代表真实读取路径正确

DOM Profiler 的第一版合成测试能通过，但实际报告一度显示各册 CSS 数量为 0。核查原始 EPUB 后，发现 CSS 文件和 `<link rel="stylesheet">` 确实存在：问题出在 EbookLib `get_content()` 重建 XHTML 的行为。改为读取原始 XHTML 后，又在 Windows 的回归测试里遇到字节编码误判，中文词题变为乱码。

**调整：** 将测试证据分层：合成用例证明解析规则，真实 EPUB 扫描证明特定输入结构，用户本机 CLI 证明依赖与编码环境，人工抽查帮助判断文学语义。每次报告必须说清「哪一层通过了」，不能把单元测试全绿说成全书质量已确认。真实缺陷还需补最小复现用例。

### 4. AI 调查不充分，却把发现问题的负担交给用户

今天的重要协作问题是：用户本来希望 AI 系统地研究 22 册的差异，却多次由用户指出标题内部样式、分册差异、贺铸题名、成套词、非作品序文等边界。用户负责提出产品目的与取舍，不应成为依赖随机阅读才能发现漏洞的唯一「全书扫描器」。

**调整：** AI 负责先统计输入分布、寻找反例、规划测试与检查覆盖范围；用户负责确定哪些文学精度值得当前投入，并运行本地私有数据、提供有限代表性验收。允许快速做原型，但原型推广为通用能力之前要验证它的适用范围。

### 5. GitHub 的最新文件清单干净，不等于提交历史干净

合并准备阶段才发现，早期 PR #49 曾提交 EPUB 派生的结构、图片与 DOM 报告，部分可能带有商业电子书的文本。这些文件后来虽然从分支最新版本删除，但旧提交历史仍会保留它们；`.gitignore` 同样不会让已经提交的内容自动消失。

**处理：** 从 `main` 建立新整合分支，只提交三轮开发的最终源代码、文档及合成测试快照；创建 [#52](https://github.com/montricwang/poeticus/pull/52)，核对 diff 与 CI 后合并。这样避免将旧报告历史继续带入主分支，原 #49–#51 关闭而不合并。

**仍未解决：** 早期公开提交可能通过 SHA、PR 引用或平台缓存访问。此次整合不是对旧公开历史的彻底清除；是否需要进一步清理，应作为独立的隐私/版权风险任务谨慎评估。这是本日最应记住的交付教训：**安全审查必须发生在首次 push 前，而非最后准备 merge 时。**

## 三、明确做出的工程取舍

- **调查覆盖要宽，正式模型要窄。** 全书 DOM/CSS 画像不是要求保存全书每一种编辑结构。
- **修正确定的抽取错误，推迟文学知识增强。** 贺铸「主词调，亦名别调」不能整体落入 `tune`；但不因此新增完整 alias 数据模型。
- **按词谱检查字数值得做，但只能先当异常提示。** 同调存在不同体式、添减字和版本差异；未来按具体词谱核对正文、分阕，而不是超字数就自动判错或改字。
- **词牌别名先用规范化名称表与确定性映射。** 向量检索不是短专名等价判断的默认工具，需求真正出现时再考虑模糊匹配与语义召回。
- **测试通过不等于逐篇 reviewed。** 功能验收与文本校勘是两种不同的责任。
- **PR 收口后停止继续扩展。** 当前 MVP 不增加套词关系、《西湖念语》组序 Schema 或全量异文考证。

后续增强集中记录在 [#36](https://github.com/montricwang/poeticus/issues/36)，当前导入流程见 [#48](https://github.com/montricwang/poeticus/issues/48)。

## 四、今晚的停止线与下一步

今天不再修改 EPUB Parser，也不将抽出的商业 EPUB 正文、现代注释或评论直接发布到公开仓库。下一轮重点回到 v0.1 产品闭环：

1. 为 **ETL 输出 → 前端现有 Poem JSON** 增加独立转换与检查，处理分阕、显示标题、稳定 ID、来源和 `review_status`；不能默认一个 `<p>` 就是一阕。
2. 先接入少量可审核的苏轼词，让阅读器能够选择、显示、划词并进行 AI 问答，不以一次收满三百多首为目标。
3. 完成 README、Python tests、前端 lint/build、核心阅读链路 smoke test，再决定 `v0.1.0` 发布。

**本日最重要的工程经验：** 速度不只来自 AI 能更快写代码，还来自它能在动手前识别输入分布、承担主动调查、把不必要的需求留在当前范围之外，并在 PR 合并前为代码、测试证据和数据安全一起负责。


## 五、晚间复盘：从单次数据工程问题上提到协作方法（讨论结论，非新增代码）

当天工程工作收口后，继续讨论了一项更普遍的问题：为什么 AI 已经知道 Beautiful Soup 等工具的能力，却没有在最初充分利用 EPUB 的 DOM/CSS 证据？原型快速跑通，为什么反而让我们长期围绕 `h2+p` 和字符串规则补丁？这些属于**对工作方法的事后解释**，并非新的代码提交，也未做严格效率对照实验。

### 1. 实现速度与调查深度是不同维度

最早的做法是「先让一个词集工作，再随新作者迭代」，后来转向「低成本扫描全部 22 册结构，再收缩到必要的作品语义规则」。不能简单称前者为谨慎、后者为激进：**我们后来扩大的是调查范围，最终业务 Schema 反而更克制**。GitHub 小版本迭代也不能证明作者事前只有局部知识；可同时做到广泛调查和小步交付。

### 2. 尚未验证的工具与问题假设

事后判断，最初更值得验证的是「区分词牌、词题和小序所需的证据究竟在哪里」，而不是直接将「怎样用 `get_text()` 清洗字符串」作为问题。过早把丰富的 HTML/CSS 信息简化为纯文本，使部分区别消失；随后投入越来越多逻辑修补既有假设。**怀疑的根因是过早收缩了解决空间**，但目前无法证明这比其他因素（需求演进、时间约束、工具真实行为未确认）占更大比重。

### 3. 设计一项更轻量、跨领域的任务启动机制

对陌生或影响面大的任务，AI 应先用有限时间辨认真实目标、已有框架/库的可用能力、可能在转换中丢失的信息及最关键的反例。对于已完整存在且容易扫描的数据，优先做结构画像；对于产品价值尚不确定的功能，优先建立端到端 Walking Skeleton 或小型 MVP；对于重要架构修改，先用代表性复合任务挑战方案；普通低风险修复仍可直接动手。**不把“任何事都先全量调查”写成万能规则。**

### 4. QA 与质量数据：能统计的直接统计，不能证明的不要臆测

自动化检查可以统计空记录、未分类模板、异常标题、数量对照以及字符替换等问题；即使没有全部作品的标准答案，也能通过结构不变量、独立参照、分层抽样和人工核对提高问题的可发现性。但**零告警不等于零错误**，数百条提取结果不等于数百条已校准文本。若未来需要准确率，必须先确定标注与抽样方法，而不是凭主观抽查给出百分比。

### 5. 用户与 AI 的学习分工

用户既不应被要求先成为所有领域专家，也不应只按按钮判断「对不对」。AI 应主动调研工具、揭示不确定性、设计机器能完成的验证；用户逐渐负责识别真实问题、质疑假设、作产品取舍、理解代表性数据流与故障。工程学习的目标是获得**提出关键问题和判断证据的能力**，而不是学会重复全部机械工作。
