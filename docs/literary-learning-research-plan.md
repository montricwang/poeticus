# Poeticus：文学推荐与持续学习研究规划（提案）

> 状态：Research Proposal / 尚未批准任何自动写入生产知识的实现
> 编制：2026-10-14
> 定位：跨 Issue 的研究地图和分阶段实验契约，**不是第二套 Backlog、现行架构文档或已经实现的能力清单**。
> 主要执行入口：[推荐 #157](https://github.com/montricwang/poeticus/issues/157)、[诗学画像 #156](https://github.com/montricwang/poeticus/issues/156)、[评论者 Persona / Skills / Notebook #148](https://github.com/montricwang/poeticus/issues/148)。
> 后续发生方向改变时更新本规划；具体任务、进展、验收只在对应 Issue 维护。不为下方每个研究方向预建新 Issue。

## 0. 为什么做，怎样判断值得做

Poeticus 首先要解决一个具体产品问题：**读者读完一首宋词后，能自然地沿着可靠、有趣、可解释的文学联系继续阅读。** 同一套关系可支持首页专题推荐、作品页相似词、读者主动请求时的 AI 对照赏析。

深入建设后，Poeticus 应能把强 LLM 的文学分析从一次性回答转成可维护的知识资产：作品画像、批评概念、分析方法、引用证据、阅读札记、判断修订史。再探索在**不训练本地模型、不修改模型权重**的前提下，通过持续阅读、反例检验和 Prompt / Skill 迭代提高评价能力，最后形成相对稳定而可修正的审美倾向。

**首要评价目标是文学判断质量，不是 Agent 自主性、人格戏剧性、记忆量或 Prompt 长度。** 自主演化与人格是后续假设，不能反过来阻塞基本推荐。

成功必须在独立作品上表现为：推荐关系确实值得阅读；分析能引用文本并处理反例；概念运用更准确；模型更换后部分研究成果仍可继承。模型自评、自己赞成自己的旧标签、单纯多写札记，不算成功证据。

## 1. 已有基础与本轮边界

### 项目已有能力（2026-10-14 仓库基线）

- 公开阅读库约 3,491 首词；已有 React 阅读界面、FastAPI / PostgreSQL、LangGraph ReAct Agent、LangSmith / Seed Eval。
- 约 853,385 Work 的外部诗歌语料，以及句 / 分句 Qwen3-Embedding-0.6B Dense、字 n-gram BM25、RRF、朝代过滤、FAISS 的 **Poem Retrieval**。该服务的任务是寻找可能的前代互文，不等于「对 3,491 首读者作品进行全篇文学推荐」，尤其不能把 chronology eligibility 直接搬到推荐场景。
- [#156](https://github.com/montricwang/poeticus/issues/156) 已提出多标签稀疏诗学画像、来源/理由/强度/置信度/版本；[#157](https://github.com/montricwang/poeticus/issues/157) 已提出 Text / Poetics / Criticism 多视图近邻，先排名再考虑聚类。
- [#148](https://github.com/montricwang/poeticus/issues/148) 已定义 Persona / Skills / Library / Notebook，以及候选洞见经过验证后才进入稳定层。它是共享评论者状态，与 [#45](https://github.com/montricwang/poeticus/issues/45) 私有读者记忆分开。
- [#133](https://github.com/montricwang/poeticus/issues/133) 研究词话结构化文献与检索；[#149](https://github.com/montricwang/poeticus/issues/149) 研究有出处的评论关系；并不意味着目前已具备完整的文献库或文学知识图谱。
- 已有设计/学习规范强调单一权威位置、优先复用、真实 Eval、不要提前锁定庞大架构。具体见 [文档导航](README.md) 与 [开发者指南](development.md)。

### 不做的事

- 不以 LoRA、SFT、DPO 或模型微调为前置条件；不为了产品故事引入独立多 Agent 集群。
- 不要求一次设计完全部中国古典诗学 ontology；不把专家争议性审美判断写成客观真值。
- 不把模型反思当作历史文献，不把模型信心当作经过校准的概率；不让模型自己生成的内容互相引用后冒充多份独立证据。
- 不自动覆盖原始文献、已审校的 Canonical 判断或稳定治学原则；不把用户私聊、用户偏好写成全站共享的批评者人格。
- 不先为全部 85 万首诗生成百维画像；首个产品范围是公开阅读库现有词作。

## 2. 分层架构：两条运行路径，共用同一批资产

### 面向读者的在线路径

~~~text
当前作品 / 阅读兴趣
    ↓
候选召回：作品原文向量 / 文学标签近邻 / 批评史关系
    ↓
评分与多样化重排：同作者/同词牌集中度、相似理由、题材跨度
    ↓
相似词卡片 / 连续阅读路径 / 首页推荐
    └── 用户主动要求时 → Agent：
          原文 + 诗学画像 + 相关分析 Skill + 必要的词话 RAG
          → 独立核验、比较、说明异同和证据
~~~

### 离线阅读与学习路径

~~~text
新作品 / 新文献 / 待解决的批评问题
    ↓
按版本化 Skill 分析 → 结构化画像、证据、阅读记录
    ↓
发现不一致、边界案例、反例、新概念
    ↓
形成候选札记 / 候选策略修订 / 需要重读的对象
    ↓
外部证据核验 + 固定 Eval + 人工抽查
    ↓
按权限晋升稳定画像、知识或 Skill 新版本
    ↓
更新推荐索引；下一轮阅读按需召回
~~~

在线服务**默认只读稳定资产**。离线实验有单独的数据/版本命名空间；学习任务不得因一次用户请求触发无上限递归。

## 3. 研究模块与可复用成果：先调查，再选型

| 主题 / 现成参考 | 可直接借鉴 | Poeticus 仍要解决 | 优先级 |
| --- | --- | --- | --- |
| 推荐三阶段：Google Candidate Generation → Scoring → Re-ranking；Sentence Transformers 检索工具 | 多路召回、近邻排序、去重与多样性 | 「文学上值得同读」的定义和人工验收 | **P0** |
| 结构化抽取：LLM Structured Output、Pydantic、Batch API | 批量任务、Schema 校验、断点重试、版本记录 | 中国传统词学概念、原文锚点、审美争议 | **P0** |
| 传统批评研究：《文心雕龙》《词源》《人间词话》及现代阐释研究 | 既有文学术语和可查案例 | 哪些概念可逐首判断；术语的历史差异 | **P0/P1** |
| LangGraph Store / PostgreSQL、LangMem | 长期记忆的写入、检索、整理和 Prompt 更新接口 | 文献/解释/个人品位的信任边界 | **P1** |
| Generative Agents、Reflexion、ExpeL | 经历记录、反思、回忆、总结成策略 | 反思后究竟有无文学能力增益 | **P2** |
| **ACE**（Agentic Context Engineering） | Generator → Reflector → Curator；细粒度 Playbook 增删/合并；helpful/harmful 反馈 | 文学任务缺少确定性对错信号，如何设计有效 feedback | **优先复现研究，集成 P2** |
| **DSPy / GEPA** | 带文本反馈的 Prompt 变异、候选选优、训练/验证分离 | 不能把文学趣味缩成单一自动分数或过拟合名篇 | **优先复现研究，集成 P2** |
| LangSmith Eval | 数据集、Trace、pairwise、离线回归 | 独立的人文评价口径和盲测样本 | **贯穿全程** |
| BERTopic / HDBSCAN / 知识图谱专用数据库 | 发现簇、展示关系、探索全局结构 | 当前近邻是否已经足够，何时有真实多跳需求 | **按证据再开** |

**研究状态说明**：以上是已发现的研究与工具，不表示已在 Poeticus 运行或已验证适合古典文学。具体框架的最新版本、许可证、成本、部署条件必须在试用前重新核对；尤其区分「论文提出的机制」「作者官方代码」「第三方复现」，不要把三者的测试/兼容性混为一谈。

### 3.1 ACE 的复现任务（先于正式集成）

原始论文：[arXiv:2510.04618](https://arxiv.org/abs/2510.04618)；作者官方代码：[ace-agent/ace](https://github.com/ace-agent/ace)；[扩展任务指南](https://github.com/ace-agent/ace/blob/main/EXTENDING_ACE.md)。官方仓库 LICENSE.txt 为 Apache-2.0；仍应单独检查具体依赖及示例数据授权。

重点读其论文及代码中的：Generator / Reflector / Curator 分工；Playbook 条目格式；局部 delta 而非整篇 Prompt 重写；去重和遗忘策略；offline vs online；helpful/harmful 计数依据；无 Ground Truth 时反馈从何而来；消融实验与失败案例。

**最小复现**：在不接 Poeticus 生产数据库的独立实验中，准备一组有明确错误案例的中文文本分析题，复现「静态 Skill / 整篇重写 / ACE 增量条目」三种更新。固定同一模型、输入和评测集合，记录可重复改进与退化。如果原项目接口/依赖与现有 LangGraph 不相容，允许只借鉴 Playbook Delta 与审查机制，而不依赖其 Runtime。

**迁移门槛**：把任务切换成真实宋词后，需能提出可核查的改进理由并避免循环自证；否则 ACE 只留研究结论，不进入在线 Agent。

### 3.2 DSPy / GEPA 的复现任务（与 ACE 并列比较）

文档：[GEPA 官方说明](https://dspy.ai/) 与 [源码教程](https://github.com/stanfordnlp/dspy/blob/main/docs/docs/getting-started/gepa-optimization.md)；论文：[arXiv:2507.19457](https://arxiv.org/abs/2507.19457)。

重点研究：DSPy Signature / Module 与现有 Prompt 文件怎样对应；GEPA 使用 scalar + text feedback；reflection LM 与 task LM 分工；训练集/验证集/从未参与优化的测试集分离；优化预算、版本输出和可复现随机种子。

**最小复现**：固定一个可以客观检验部分结果的文学任务，例如「识别比兴/对写的有据证据句并给出反例保留意见」，运行初始 Prompt、手工修订、GEPA 三组。保留每组原始输出、人工或规则反馈、费用与失败案例。不要用某次优化期间的模型自评替代独立测试。

**ACE 与 GEPA 不预设二选一**：ACE 偏向持续积累和维护大量经验条目；GEPA 偏向在明确评价函数下优化特定任务的 Prompt。可能组合，也可能只需其中之一；先通过同题比较决定。

### 3.3 长期记忆基础研究

参考：[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)、[LangMem](https://github.com/langchain-ai/langmem)、[Generative Agents](https://arxiv.org/abs/2304.03442)、[Reflexion](https://arxiv.org/abs/2303.11366)、[ExpeL](https://arxiv.org/abs/2308.10144)。

先对照现有 PostgreSQL / LangGraph 调查：持久化何种记录、按什么 namespace 查询、如何更新/撤回、谁能晋升长期记忆。LangGraph 的 Checkpointer 是会话状态；Store 可用于跨 Thread 的长期资产，但不因此自动解决其文学可信度与用户隔离。

不为了概念好听另造 Memory Server。若普通关系表和 Markdown 已满足首版读写/回滚，继续沿用。

## 4. 文学分析框架：先研究一套概念，再扩维

先从王国维《人间词话》选择「境界 / 有我之境 / 无我之境」等相互关联的概念；核对原文、例词、代表性现代研究、异议与边界情况。不要只依据模型对名词的预训练印象或网站二手释义。

每个可执行 Concept Spec 至少说明：

- 术语、来源文献、出处、历史语境；不同批评家是否用相同含义；
- **可观察现象**：模型究竟应在具体词句、章法、抒情主体、意象关系中看到什么；
- 典型例、边界例、可能推翻简单定义的反例；
- 不能推出的判断（例如「没有我字」不等于「无我之境」）；
- 适用范围：逐句、单篇、作者整体、批评史意见，不相互下放；
- 模型面对证据不足、相反意见时的处理方式；规范版本与修订理由。

用一份人可读 Markdown 研究札记保存争议和上下文；只有能执行的规则提炼到小型、版本化 Skill。不让每一个小术语生成一套独立 Persona。

### 分轮分析，而不是一次穷举几十维

1. 第一批：较易检查的题材/情感、情感转折及原文依据（避免只输出正/负面）。
2. 第二批：表达机制、用典、对写、铺陈、起结与结构。
3. 第三批：字法句法、虚字、语言风貌、词学风格。
4. 后续：有我/无我、清空/密丽等解释分歧大的审美判断及不同批评视角。

客观字段（作者、字数、词牌等）优先来自核实后的数据库或算法，不让 LLM 猜测作者性别、时代、格律事实。允许「开放观察 + 归一化多标签」并存；不强迫所有作品属于某个唯一簇。

## 5. 作品画像：判断不是标签列表，而是一份可审查记录

**候选数据契约**（先用于样本 JSONL，不意味着立即建立生产表）：

~~~yaml
work_id: ...
dimension: 表现机制
concept_id: contrast_past_present
label: 今昔对照
strength: medium        # 特征在作品中的体现程度，不是正确概率
confidence: medium      # 模型自报信心：未经校准
claim_kind: inference   # inference / historical_claim / curated_review
rationale: ...
evidence_spans:          # 具体词句及原文 offset
  - text: ...
    start: ...
    end: ...
counter_reading: ...     # 合理的不同解释 / 不适用理由
lens_id: ...             # 分析视角，例：王国维理论相关规范
taxonomy_version: ...
prompt_version: ...
model_id: ...
run_id: ...
review_status: candidate
~~~

原则：

- **分析强度、模型信心、核验状态是三个不同概念**。信心不能只用模型自报数字充当概率，必要时与人工样本做校准。
- 初次打标就保存理由与具体原文依据；之后请求模型解释旧标签，属于新的分析，不是取回其真实内部推理。
- 历史评论需有可追溯的来源、章节、原文与评论对象层级；模型对作品的判断不能冒充「张炎/王国维明确说过」。
- 保留新旧版本和审核记录。单条候选可撤回；已发布画像不得静默覆盖。文章版本变化后必须检查原文 span 是否仍准确。
- 模型 A 负责初标、模型 B 独立分析并复核是候选流程；**先独立判断再看旧标签**，降低跨模型锚定偏差；不同模型意见一致不等于独立事实证据。
- 只从公开阅读库现有作品小样本开始，不把原始私有 EPUB、商业论文、API Key 或受限语料提交公开仓库。

## 6. 推荐：首个面向读者的可验收成果

推荐与前代互文检索不是同一个产品问题。复用算法/Encoder 的经验，但不沿用「必须早于当前作品」的业务规则，也不要求直接把 85 万 Work 的 Chunk 索引变成 3,491 首词的作品推荐服务。

**第一版两路基线**：

A. 原文近邻：对公开词作整篇或合理多段表示建立作品级相似排序；优先使用现成 Embedding / cosine、可缓存的离线 Top-K。检查长调与短调的表征偏差。

B. 文学特征近邻：利用 #156 的多标签和开放式机制短释，尝试标签加权相似度与文字 Embedding 近邻；常见「月、秋、悲伤」不等于细致修辞相似。

C. 只有 A/B 都形成真实样本结果后，再比较融合、按入口重排（作品页/首页）、按作者分散、多样性和「意外近邻」（语义远、写法近）。

**呈现要求**：每条推荐最好能说清「像在哪里」，区分「内容相似」「写法相似」「前人曾比较」；不把相似当作化用/影响事实。阅读页至少能够从 A 连续进入 B 再进入 C；AI 对照赏析由用户主动发起。

**首轮实验**：选 50–100 首风格/篇幅/作者有差异的样本，制作 10–20 个起点的 Top-K 推荐对照；人工盲读（隐藏模型来源）记录：有无真正值得读的共同点、理由是否针对文本、重复率与意外发现。先拿出能展示的结果，再判断是否需要更复杂的排序器或 BERTopic 聚类。

## 7. 持续学习：把「读过」变成「理解发生了什么变化」

### 分层保存

| 资产 | 写入策略 | 修改权限 |
| --- | --- | --- |
| 原始文献、经过许可的底本 | 保存来源、版本、文本位置；不可由模型改写 | 只能走文献校勘/纠错流程 |
| 阅读经历 / 具体案例 | 记录作品、分析版本、时间、所遇反例 | Append-only 或留完整变更史 |
| 候选洞见 / 候选策略 | 模型可频繁新增、合并、否定、标记争议 | 受配额控制的实验区 |
| 稳定画像 / 稳定研究笔记 | 有外部证据、重复案例与 Eval 才晋升 | 版本化、有回滚 |
| Skills / Playbook | 经独立 Eval 的修订可升级；保留旧版本 | 显式发布/晋升流程 |
| 稳定治学原则 | 如不得伪造文献、应标出不确定性 | 不由日常自动阅读直接修改 |
| 读者偏好 | 每位读者独立的私有数据域 | 用户有查看、更正、撤回能力 |

**推荐的更新机制**：新发现 → 候选记录 → 找相关旧判断和反例 → 提出最小修订 → 受控复测 → 决定保留、降权、合并、替换；不直接让一次对话改写整个 Persona。

「证据积分」只能作为优先审查/提议修订的信号，而不是「10 票自动升格」：要区别独立来源与相互转述、重复引用、单个决定性反例、反例适用范围。可先用计数+来源去重+规则判断，不急着发明复杂概率模型。

### 阅读课程：有目标的探索与随机性并存

在出现稳定作品画像和一小批旧判断后，研究三种阅读选取：随机作品；当前理论不确定/有冲突的作品；可能推翻现行规则的边界样本。固定随机种子、抽样策略、已读清单、模型/Skill 版本，记录触发了什么新的认识。

学习记录应体现「尚不确定」「与旧观点冲突但未解决」这种中间状态。不是每读十首就必须强行总结成新原则。

### 审美人格置于最后

可探索不同起始审美偏好、批评视角和临时阅读心境，但先区分：
- 治学底线：不可随心境改变；
- 文学解释和审美偏好：可逐渐调整，需有记录和理由；
- 临时情绪/表达语气：只影响当次关注和语言风格，默认不写回长期知识；
- 用户私有偏好与 Poeticus 共享 Critic Persona：绝不混淆。

最终目标不是声称 LLM 具有人类意识，而是构建可回溯的长期批评历史与相对连贯的审美判断。

## 8. Eval：把「成长」和「积累得更多」区分开

### 数据集

50–100 首第一批样本中，应有名家典型作品、同一作者非典型作品、冷门作品、相似词牌但写法不同的负例、题材不同而写法相近的正例。**训练/探索、验证、保留测试三组分开**；同一作者或高相似版本泄露须标记，重要评测应尝试按作者组隔离。不能用刚被反复优化过的同一组作品证明泛化。

### 指标按任务分层

| 任务 | 推荐观测指标 |
| --- | --- |
| 批量标注 | 原文引用/span 有效性、结构输出通过率、跨运行稳定性、人工分歧类型 |
| 传统概念应用 | 是否错用概念、能否识别边界/反例、证据是否足够；允许不同合理流派结论 |
| 相似推荐 | 人工盲测「值得同读」比例、Top-K 相关性/多样性、重复/伪近邻、实际连续阅读行为 |
| AI 比较赏析 | 隐藏标签后的独立判断 vs 先给标签；对照说明的文本具体性和异同质量 |
| Prompt 更新 | 同任务旧 Skill vs 新 Skill 在保留测试集的错误、退化、成本、稳定性 |
| 长期学习 | 初始 / 读完一批 / 加入新理论后的盲测；是否更能解释陌生作品与修正错误 |

LLM-as-Judge 可用于筛选可疑样本和辅助比较；关键争议要有人读原文并审核。不要把模型自己生成的标签用作同一模型的绝对答案；也不把「更符合审美种子」算作通用文学正确率提升。

**必要的对照组**：
1. 固定 Prompt + 直接原文（无外部记忆）；
2. 固定 Prompt + 普通文献 RAG；
3. 固定 Prompt + 已积累画像与研究札记；
4. 以上基础上加入经 Eval 升级的 Skill / Playbook；
5. ACE / GEPA 与手工修订基线在相同模型、样本、Token/费用预算下比较。

评价必须同时看文学质量、性能/费用、Prompt 长度、记忆检索错误与旧 Case 退化。若只有主观风格改变，明确记作偏好迁移，不冒称能力进步。

### 回滚与污染防控

每次实验至少保留：数据集版本、作品文本/来源指纹、模型及参数、Skill / taxonomy 版本、检索结果、随机种子、运行记录、成本、候选 delta、发布决定。

防止三类污染：旧模型的错误被新模型照单全收；模型反复引用自己的札记造成虚假「多份证据」；根据保留测试集反复调 Prompt 导致过拟合。更新只晋升到有版本的稳定层，可随时回滚到上一版。

## 9. 分阶段路线与真正的启动条件

### 阶段 A｜复用研究 + 推荐基线（先开始）

- 阅读并复现 Google 三阶段推荐和现成文本近邻接口的最小示例；对现有 3,491 首作品建立**独立于前代互文**的作品级近邻实验，不修改旧 #119 Serving。
- 并行阅读 ACE 官方论文/源码与 GEPA 官方教程，记录可借用的实验数据契约、反馈接口、delta/版本机制，不先引入生产依赖。
- 从作品页实现或至少离线展示 10–20 个起点的 Top-K 对照，检查重复、泛泛相似及「继续阅读」的价值。
- **验收**：有可复现的 Top-K 推荐与逐例对照；能够说明现成框架的真实边界，以及 ACE/GEPA 哪些部件值得复现。
- **停止线**：如果文本近邻就能满足初步产品价值，先上线小功能；没有证据不以「将来会需要」为由建设大型全局聚类。

### 阶段 B｜第一套真正可用的诗学画像

- 选《人间词话》一组概念，结合可靠文本和研究形成 Concept Spec v1 + Skill v1。
- 对 50–100 首进行结构化分析，含开放观察、标签、强度、信心、原文依据、异议、模型和版本。
- 用 ChatGPT 生成一组、DeepSeek 独立评估另一组等方式研究模型差异；让人工核查出现分歧的作品。比较原文近邻 / 标签近邻 / 融合的真正增量。
- **验收**：可追溯画像、能被推荐/赏析复用的标签与说明；存在一些只看原文相似度难以发现的合理近邻。
- **停止线**：如果标注理由空泛、概念混乱、缺乏稳定结果，不扩至全库；先修 Concept Spec 和 Eval。

### 阶段 C｜研究札记与记忆闭环

- 用普通 PostgreSQL / Markdown 或 LangGraph Store 做最简单的 Candidate → Review → Stable 数据路径，验证按作品、概念、问题召回及版本回滚。
- 允许模型在阅读中提出新概念和反例；把原始文献、历史评论、模型解释、稳定经验分开存储。
- **验收**：同一首作品后续分析能够准确找回旧见解，也能明确指出分歧；不会把自己的研究笔记冒充原始文献。
- **停止线**：若简单版本化表和文件足够，就不额外引入 Memory MCP / 图数据库。

### 阶段 D｜ACE、GEPA 的受控迁移实验

- 先分别使用原框架的示例任务跑通；再用同一小型宋词案例集对比固定 Skill、手工迭代、ACE 增量 Playbook、GEPA 自动改写。
- 不让三者共享有污染风险的评测反馈；记录 Token、费用、实例失败和回滚行为。
- **验收**：至少一条方法在**独立保留案例**上展示可复现的分析增益，或明确得到「无增益/不适用」结论。
- **停止线**：不能形成稳定评测反馈或收益小于复杂度时，保留人工审校+版本化 Skill，不上线自改 Prompt。

### 阶段 E｜长期阅读课程与审美成长（远期）

- 随机/疑点/反例相结合地选择旧作重读；添加新词学理论后的实验；逐步积累跨作品札记和审美偏好史。
- 探索两个不同审美种子的 Critic，在固定基准原则下是否形成可解释差异、是否真正纠错。
- **验收**：对未参与训练的新作品有更丰富、可靠、可追溯的判断；能解释自己何时为何修改了旧方法或偏好。
- **停止线**：若只是不同口吻或人格剧本，而非文学能力提升，就保留为可选 UX，不称作持续学习成果。

阶段不是强制瀑布：例如 A 的推荐可以先用粗画像，研究 ACE/GEPA 可以在早期独立复现；正式引入自动策略更新必须等待可靠的评测基线。

## 11. 风险登记与替代方案

| 风险 | 最小防范 | 应触发重审的事实 |
| --- | --- | --- |
| 模型自信但误读词句/概念 | 保留 span、理由、反读法，人工抽查 | 多次出现无法追溯的术语判断 |
| 纯自评造成循环自证 | 隔离事实文献与模型札记；盲测保留集 | 新版只在自评上进步 |
| 早期审美偏好使探索变窄 | 随机样本 + 反例优先 + 名家去标签 | 无法承认不同写法的优秀作品 |
| Prompt 自动修改破坏其他维度 | delta 版本、分层回归、撤回旧版 | 单项改善但跨任务显著退化 |
| 文档/Issue 无限膨胀 | 本文总导航、Issue 唯一 owner、避免重复副本 | 同一事实在多处都要同步 |
| LLM 批量成本、API 不稳定 | 小样本、批处理预算、缓存和断点续做 | 生成成本大于实际阅读收益 |
| 文献授权和质量 | source/provenance、版本与发布许可审查 | 外部来源不能合法缓存/公开 |
| 用户隐私污染全站 Critic | 专用 namespace 和访问控制 | 共享资产包含用户私人对话 |
| 审美理论本身存在争议 | 允许多个 Lens、相反解读与不确定 | 模型硬把各批评家解释合并成唯一真理 |

## 12. 下一次工作应该从哪里开始

**建议先做两项并行、小规模工作，而不是立即动手开发自动进化系统：**

1. **推荐 P0**：从 #157 选 10–20 首起始词，验证公开阅读库全篇语义近邻的基线与读者持续跳转的价值；记录缺陷后再决定哪些诗学标签最能改进推荐。
2. **框架复现 P0**：从 #148 出发，先读 ACE 作者代码与 GEPA 教程各一个最小例子，写一份真正跑过的三方比较（固定 Prompt / ACE / GEPA 的任务输入、反馈、输出、资源、成功与失败）。若这轮尚无稳定文学评分，先用可明确判断的任务复现机制，**不要冒充已验证宋词分析收益**。

待两者有真实案例，再将 #156 的概念画像与 #148 的反思机制连接。第一轮任务可以用最少的 JSONL、Markdown、现有 LangSmith/pytest，不需要新平台。
