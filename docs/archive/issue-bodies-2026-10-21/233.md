## 目的与边界

本 Issue 汇总 **Poeticus 产品自身**可能调用的外部 MCP / HTTP API / CLI / 网页查询能力，按真实问题逐项做限时实验；**不是** ChatGPT 开发 Poeticus 的工具清单，也**不是**给 Poeticus 对外提供 MCP 的任务（后者见 #185）。

当前 Poeticus 已有 CNKGraph 的 `lookup_allusion` / `lookup_reference`、自建 `search_predecessor_texts`、`EvidenceService` 与 ReAct 式 Agent。`backend/mcp/server.py` 是 Poeticus **作为 MCP Server** 的方向；产品调用外部 MCP 需要 **MCP Client**，不能混同。现有 Agent 实际使用 OpenAI 兼容 Function Calling，不为试用重写 LangGraph。

**职责分工：**
- #202 + `docs/architecture/agent-capability-map.md`：产品问题域与能力缺口，不维护工具百科。
- #184 + `docs/digital-humanities-resources.md`：外部数字人文来源、授权与资源事实。
- #153 / #154：Web Search 产品能力与证据域路由；#133 / #147：文献库及书目；#149：关系图谱。
- #24（已关闭）：早期汉典、萌典等 API 可行性历史调查，**不自动重开**。
- #185：Poeticus 对外暴露自身查询工具的 MCP 学习 / Server 实验。

**明确从近期队列撤出**：Pipeworx `mcp-wiktionary` 约 2 Stars，虽然命名正中需求，但代码只有薄薄几层封装，其远程 Gateway 会额外声明约 30 个通用工具，和我们希望减噪相反；它的 `definition` 还依赖 Wikimedia REST 某些语言站点的端点差异（[Wikimedia 官方文档](https://www.mediawiki.org/wiki/Wikimedia_REST_API/en) 指出结构化定义接口是**英语 Wiktionary 实验特性**），不适合未经中文数据实测直接定为优选。**先从 MediaWiki MCP 正式词条读取入手**，若需要独立解析词义再另评估专业词典适配器。

**IIIF MCP 暂缓**：项目特殊价值是影印页；但是先要确认识典/CTP/目标馆藏实际暴露 IIIF Manifest，再决定是否需要其社区封装。**Zotero MCP**虽有约 5.3k Stars 且维护活跃，但主要围绕私人 Zotero 文献库与本地附件，暂与匿名 Poeticus 公开知识源不同；保留在 #241，不占当前三席。Open Library、Internet Archive、Crossref、Semantic Scholar 等均存为长期候选，停止同类型重复对比。

**下一步只做一项**：#237/#234 共用 ProfessionalWiki MediaWiki MCP 的只读最小测试；能区分页面读取与中文古汉语义项后停止。后续再根据实际材料/需求选择 Docling 或 OpenAlex，不抢先安装，不在此阶段重写 #133/#149/#153。
