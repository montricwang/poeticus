## 2026-10-03 讨论决定：保持当前最小 Schema，先纠正字段归属

这次 #67 的重点是**已存在的非正文文字错误地进入 `body_segments`**，而不是为宋词研究建立更细的全部文献分类。当前 3,491 首候选词作尚未逐首校勘，现阶段**不因这批样本增加 `title_note` / `author_preface` / `editor_preface` 等字段**；这属于本次修复的范围约束，不代表这些文学概念永远无需区分。

**本轮对现有字段的暂行语义约定（未来遇到真实反例再复查）：**

| 字段 | 暂时承载的内容 | 边界 |
|---|---|---|
| `title` | 作品词题、简短题注（如写作时地、赠答对象等） | 短题注不必为了独立命名立即扩 Schema；也不能仅按长度机械分类 |
| `prefaces` | 相对独立的正文前叙述／序文，包括作者自序、小序等 | “自序”强调撰写者、“小序”强调文本形态，并非互斥的数据库类型；不能未经来源证明就标记作者身份 |
| `body_segments` | 词作正文的有序阅读片段 | 元素数不等于词的片数；词序、题注不应混入 |

**验收重点：** 纠正会影响阅读、选区、AI 解读的“非正文误入正文”，同时不把题注/词题、自序/小序的精细词学区分变成本轮阻塞项。用户明确接受语料存在后续待校问题；已知缺陷可追踪、可修订，但不得因追求 100% 精校暂停 React API 对接。

**升级判断：** 只有当实际数据分布、阅读展示、检索、引文来源或学术校勘流程确实需要更细类别，且来源证据能够可靠判断时，才在独立架构讨论中比较扩 Schema 的收益和误分类成本。任何更正要保留可重放的修改记录，避免下次重导覆盖人工更正。

这是一项**#67 的当前处理决策与停止线**；稳定、跨模块的数据契约若将来修改，再同步至 `docs/architecture/corpus-database.md`，不在尚未实现之前假称 Schema 已改变。

## 2026-10-03 补充实测：纳兰词集呈现成簇问题（更新本 Issue 范围）

用户在本机 PostgreSQL 对全库 3,491 首按 `body_segments` 元素数筛选，提供了**全部 30 条“3 段及以上”作品的查询结果**。其中 **13 条来自`纳兰词集`**，其余 17 条分布在柳永、欧阳修、苏轼、周邦彦、辛弃疾词集中。

4. 不因该问题重新导入 3,491 首、修改 UUID 或阻塞 React 分页 API 对接。本次只更新 Issue，**不改代码或数据库**。

## 现象（2026-10-03，本地真实 PostgreSQL / API 抽查）

用户查看纳兰性德《沁园春》时发现：一段明显属于**词前叙述（词序）**的文字被放入 `body_segments[0]`，而 `prefaces` 为空。作品仍有正文，因此此前的“非空正文／3491 行／无告警”检查无法发现此类**静默语义归类错误**。

**精确定位（不提交完整商业 EPUB 衍生正文）：**
- `id`: `14ddd68c-fca1-4b05-a4e6-45954e74b40f`
- `source_order`: `3399`
- `collection`: `纳兰词集`
- `author`: `纳兰性德`
- `cipai`: `沁园春`
- `text_version`: `1`
- 当前 `body_segments` 长度为 3；第 1 段以「丁巳重阳前三日，梦亡妇……」起，末尾「觉后感赋长调。」；实际词正文从第 2 段「瞬息浮生，薄命如斯……」开始。
- `prefaces: []`，`review_status: imported_unreviewed`。

## 已知事实与未知根因

- **已观察到：** 词序被归入正文、词序字段为空；这是具体记录的字段归类缺陷，**并非数据库数量或 FastAPI 传输失败**。
- **用户初步检查：** 原 EPUB 中词序和正文看起来字体／字号类似，甚至可能使用相同元素类型；目前**尚未核对原 XHTML、DOM 顺序、CSS、附近标题/段落**，不能据此断定“抽取脚本没有问题”或“必须重新设计抽取脚本”。
- 尚不清楚同样的排版规则是否影响同册其他作品，也不清楚错误最早出现在 EPUB 抽取、规范化还是入库适配环节。

## 以后处理时建议的最小步骤（本轮暂不实现）

1. 本地根据作品 ID / 原书顺序追溯私有 EPUB 对应 XHTML，核对词序与正文的标签、样式、相邻元素、标题与分段线索，并与原始中间 JSON、数据库记录逐级比对，定位首次误分层。
2. 对本册以及同一排版模板抽样调查是否存在一簇同类错误；也抽查程序无 warning 的作品。**不要因为一首词就全局规定“第一个 `body_segments` 元素是词序”。**
3. 若找到可复用且足够可靠的证据规则，做局部修复并添加不包含商业原文的合成回归测试；若原书没有机器可辨别的稳定线索，则考虑“标记为待核查／小范围人工校正”而不是扩大不可靠的启发式猜测。
4. 决定修复范围时同步考虑本地已有 3491 条作品的 UUID / `text_version` / 会话引用与选区偏移，避免为修复一首词直接重建数据库或静默覆盖已读版本。具体数据修订路线届时单独设计。

## 2026-10-05：新增贺铸自注案例（与纳兰词序同类）

用户在原 EPUB 中发现贺铸《□□□七娘子》存在**作者自注未被正确清洗/归类**的问题。

当前观察：
- 词正文使用楷体；
- 作者自注同样使用楷体；
- 自注字号比正文更小；
- 当前抽取结果未能把这段自注单独识别出来。

这与本 Issue 已记录的纳兰词集“自序/词序未正确从正文中分离”属于同一类问题：**EPUB 中存在语义上不同的非正文文本，但现有清洗规则没有可靠利用版式层级把它们分类出来。**

新增诊断重点：
1. 不再把“字体家族不同”视为必要条件；贺铸案例表明正文与自注可以使用同一字体，仅通过字号或其他 CSS 差异区分。
2. 回到原 XHTML/CSS 检查自注与正文的 `font-size`、class、父节点、缩进、行距、相邻结构等，而不是仅凭视觉字体类型。
3. 与纳兰词序案例一起评估：是否能形成“版式特征 + DOM 位置”的来源模板规则；若不能稳定泛化，则保留作品级可重放校正，而不是写全局启发式。
4. 语义上应区分至少“正文前序文/小序”和“正文内/后作者自注”，但是否立即扩展 Schema，仍按实际数据分布与产品需求决定，不在发现单个案例时先行设计。

本 Issue 因此从“纳兰词序单册问题”扩大为：**EPUB 清洗中序文、自序、自注等非正文结构的识别与归类问题**。纳兰词集仍是已知成簇案例，贺铸《□□□七娘子》作为第二类版式反例纳入同一诊断。
