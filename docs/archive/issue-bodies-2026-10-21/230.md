## 为什么做

Poeticus 的后端主要由 AI 辅助快速开发，功能持续增加，但项目负责人仍在学习 Python 与软件工程。当前不少函数缺少必要的职责说明，跨文件的调用关系也不容易追踪：即使程序能运行，读代码时仍很难判断「谁调用谁、每一步为什么存在、数据如何返回」。

**目标不是增加注释数量，而是让不依赖聊天记录、具备基础 Python 知识的读者，能够从真实入口一路读懂核心后端。** 这也是后续独立维护和求职展示的基础。

## 准备怎样做

- **先画清真实调用链**：确认入口函数、主要类／函数、上游调用者、下游依赖，区分 Agent、工具接口、业务 Service、Provider 与外部 API 的职责。
- **落实到关键函数**：优先给职责不直观的函数和类补简短 docstring，说明「做什么、输入输出、重要副作用或异常」；重要的设计取舍和容易误删的约束用局部注释解释「为什么」。
- **让代码本身更好读**：必要时改善命名、函数排列、冗余分支和跳转；只有查明实际职责问题并有回归保护时才做结构性重构。不机械地给每个一眼能懂的小函数写注释，也不把 Python 入门教程塞进源码。
- **保留一条简短阅读路线**：在现有开发／架构文档中标出核心入口与主调用链，告诉后来者先读哪些文件，不再建一套重复文档。

## 分批范围

**首批优先**：`backend/api/chat.py` → `backend/ai/graph.py` → `backend/evidence/` → `backend/mcp/server.py`。以「查询一个典故」为例，核对 LangGraph 原生工具调用和 MCP 入口如何进入同一套证据服务，并解释 `EvidenceService` 与 `CNKGraphProvider` 的分工。

后续再按实际阅读障碍选择其他 `backend/` 模块；一个 Issue 可以由多个短期分支／小 PR 完成，**不做一次性全后端大改**。Retrieval 内部已有 [#182](https://github.com/montricwang/poeticus/issues/182) 专项审计，优先复用其结论，不重复开工。

## 2026-10-13｜阅读 `graph.py` 后的节点内部重构候选

已通过本地 Serena 核对 `backend/ai/graph.py`：**保留 `agent_decide → route_agent → execute_tools` 的 ReAct 节点拓扑，不为拆分而增加 Graph 节点**。需要调整的是节点内部职责，而非更换 Agent 模式。

1. **优先整理 `execute_tools()`**：目前同时负责工具调用 ID / 预算检查、`_parse_tool_query` 参数解析、根据 `evidence_type` 在 Text Retrieval Client 与 `EvidenceService` 间分支、各自结果截断/规范化、异常降级、追加 tool 消息及更新 State。考虑提取“每种工具的调用与结果整理”为独立函数或明确的执行器接口；保留预算与消息回传的统一入口。先检查实际工具契约与扩展需要，不预先搭建通用插件框架。
2. **统一模型请求逻辑**：`agent_decide()` 的流式调用交给 `_stream_agent_decision()`，非流式分支直接调用模型并重复整理响应。此项由 [#246](https://github.com/montricwang/poeticus/issues/246) 专项负责；须保留评测/测试所需的 `graph.invoke()` 能力，不把非流式 HTTP 接口与内部同步 Graph 执行混淆。
3. **评估整理类型与工具定义**：`RouterState`、`RouterUpdate`、`ToolCall`、`TOOLS` 等目前集中在 `graph.py`；只有在实际提高阅读性、降低循环依赖时才移动到单独模块，不以文件行数为唯一理由。

**分批验证**：先用 Fake Tool / 现有回归覆盖 tool budget、重复 ID、参数错误、CNKGraph 命中/空结果、Retrieval 候选截断、失败消息和 Agent 循环，再小步调整；比较修改前后返回的 State 与 SSE 可观察行为。当前仅记为重构候选，**本轮不修改代码**。

## 2026-10-13｜下午候选：工具定义管理形态与 Provider 配置

**工具定义管理（本轮优先的独立小改动）**：目前 `graph.py` 的 `TOOLS`、`TEXT_RETRIEVAL_TOOL` 和 `_available_tools()` 同时包含面向模型的工具说明、参数 Schema 与启用条件。考虑提取到独立的 `backend/ai/tools.py` 模块，保留现有定义和可用性判断，对外提供简单查询函数。讨论是否需要 `ToolRegistry` 类，但**不预设必须用类**：只有动态注册、共享状态、实例生命周期或多套权限配置等确有需要才采用；否则模块常量 + 函数更易懂。区分面向模型的 Tool 定义与 `EvidenceService` 内注册的 Provider，不能互相替代。

**外部 API 配置与魔法数字（核查后再决定提取层级）**：`backend/evidence/providers/cnkgraph.py` 当前 `CNKGraphProvider.__init__()` 从环境变量读取 `CNKGRAPH_BASE_URL`（默认 `https://api.cnkgraph.com`），超时则固定为 `10.0` 秒；`_request_json()` 使用该配置发起 HTTP POST 并处理 404、HTTP/网络/JSON 错误。后续检查 Retrieval、MCP 等其他外部客户端已有的配置方式，判断应保留局部常量、引入配置变量还是统一集中配置。**不因只有一个魔法数字就新建配置类或文件，也不强迫各 Provider 使用相同超时**；需要配置时说明单位、默认值、环境变量及测试方式。

**建议施工与验收**：首先只移动 Tool 定义和筛选函数，验证启用/禁用 Retrieval 时模型收到的工具名称、参数 Schema、顺序完全不变；Provider 配置单列小步骤，核对超时与错误回传测试。工具执行器拆分仍按本 Issue 上节规划另行处理。无授权前不改运行逻辑、不增加第三方依赖。

**CNKGraph HTTP 404 语义待核查（2026-10-13）**：目前 `CNKGraphProvider._request_json()` 将两个端点的所有 HTTP 404 统一解释为“未命中”并返回 `None`，随后查询方法返回空列表。HTTP 404 也可能表示路径失效或服务端路由错误；施工前核对 CNKGraph 两个接口的实际响应约定，并使用模拟 HTTP 响应验证“无结果、路径错误、HTTP 故障”的不同语义。只有核实后才决定是否修改错误分类和降级，不凭 HTTP 状态码臆断业务含义。


## 2026-10-13｜下午施工范围补充：共用 Tool Executor

本轮讨论确认：内部 Agent 的 `execute_tools()` 与对外 `backend/mcp/server.py` 的 `_search()` 均承担一定的参数处理、EvidenceService 调用及结果整理职责。**下午将“共用工具执行器（Tool Executor）”列为明确的施工候选**，不只停留在泛泛评估；先逐条核对两条入口实际输入输出、预算、错误语义与返回数量限制，确定真正重复的业务步骤，再提取共用函数或小模块。

职责边界：Agent 负责模型工具调用消息、预算和 State；MCP 入口负责协议注册、外部参数限制和响应契约；共用执行器负责能够安全复用的业务查询/标准化步骤；EvidenceService 继续选择 Provider。**不把所有协议解析塞入一个 Parser，也不让 ToolRegistry 承担权限、限流、网段管理**。目前默认用模块和函数练手，不预先引入注册管理类或全局单例。

实施顺序建议：① 工具定义与可用性判断移出 graph；② 对照 Agent/MCP 的查询行为，提取一个最小共用 Tool Executor；③ 分别跑 Agent 与 MCP 路径的回归、校验现有输出契约；④ 外部 API 配置和 404 语义作为独立检查事项，不随手改行为。小步提交，必要时拆为多个 PR；不以 CI 通过替代真实交互验证。当前仅更新计划，未授权立即改动执行代码。


**状态类型命名（2026-10-13 下午）**：将 `backend/ai/graph.py` 中 `RouterState` / `RouterUpdate` 评估更名为 `AgentState` / `AgentUpdate`（优先此组，较 `State` 更清楚）。核对跨模块引用并只改类型名称，不更改 State 字段、LangGraph 合并语义或持久化行为。继续检查 `messages`、`tool_results`、`evidences` 的真实消费者，避免为了表面去重误删状态。
