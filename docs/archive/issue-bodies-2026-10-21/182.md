## 总体重构原则：把稳定能力从实验入口转正

本轮不仅逐项修复已发现的 P1/P2 问题，还应检查整个 Retrieval 的**依赖方向与能力归属**：

> **实验脚本可以调用稳定的正式模块；当正式模块、长期构建工具或多个实验入口反过来依赖某个临时实验脚本时，应审查其中是否已有值得转正的公共能力。**

- **共享的稳定能力**：辨认已被重复使用、语义基本确定的路径契约、Work/Chunk/Hit 数据结构、字符 n-gram 与 FTS5 规则、Artifact/Manifest 读取校验、哈希或纯算法。先确定真实调用方与一致性要求，再决定是否抽取；不能只凭“出现两次”就抽象。
- **归属与依赖方向**：将真正通用的能力放到职责明确、无需依赖实验 CLI 的模块；正式 Serving、离线构建和 Eval 按需调用它。不要让低层公共代码导入运行入口，也不要把重依赖或实验专属配置强加给所有消费者。
- **CLI 尽量薄，但不以行数为目标**：脚本优先负责参数解析、一次性流程编排与结果呈现；成熟的检索与数据处理能力由对应正式模块承担。真正独立的离线构建算法、诊断基线和报告逻辑可以继续存在于脚本或专门模块中，不强求所有东西进入 `backend/`。
- **保持契约与差异**：抽取之前列清输入、输出、错误/空结果、数据版本、资源加载和副作用。不同上下文有意不同的行为（例如诊断模式对空查询报错、Serving 返回空结果；严格历史朝代诊断与产品 recall-first 过滤）不可为“统一”而误合并。
- **克制抽象**：不为了凑“分层”新建笼统的 `utils.py`、`common/`、`helpers/`、Manager/Factory；仅当共享能力足够稳定且提炼后能降低实际维护成本时转正。

本轮交付应能回答：**哪个正式模块拥有这项能力？哪些 CLI 只是调用它？哪些历史实验仍提供不可替代的诊断价值？** 这样既降低新手阅读成本，也让未来退出实验脚本不再牵动正式构建或在线服务。

## 已观察到的结构与优先问题

### P1 — 入口与脚本身份不清（先做地图，不直接删）

`scripts/retrieval/` 同时存在 `exact_search.py`、`artifact_search.py`、`faiss_search.py`、`hybrid_eval.py`，它们分别保留了 Exact baseline、按 Artifact 自适应查询、FAISS 单通道诊断和 Hybrid Eval。正式在线主链却是：

```text
scripts/retrieval/run_serving.py
→ backend/retrieval/serving.py
→ backend/retrieval/service.py
→ query_strategy / fanout / fusion / eligibility
→ Server HTTP → Agent client
```

初学者无法仅凭文件名确认哪一套是正式路径。**待核对**每个入口的真正调用方、测试依赖、独有诊断能力、离线产物与重建成本，分类为：正式 Serving / 索引构建 / 长期诊断与 Benchmark / 历史探索。可以在现有 `docs/architecture/text-retrieval.md` 或开发指南增加一张最小入口导航，**不要创建新的平行文档体系**。

### P1 — 正式构建工具依赖历史实验脚本

`scripts/retrieval/build_metadata_store.py` 从 `scripts.retrieval.exact_search` 导入 `DEFAULT_DATA_ROOT`、`DEFAULT_WORKS`；`scripts/retrieval/lexical_bm25.py` 也从 `exact_search.py` 导入路径、`DEFAULT_TOP_K`、`sha256_file`。另有 `artifact_search.py` / `faiss_search.py` 借用其工具函数。

**问题**：`exact_search.py` 本是实验/诊断入口，却逐渐充当公共基础设施。未来退役它时容易意外破坏正式构建能力。

**最小候选改法**：路径常量由 `backend/data_paths.py` 的唯一目录契约直接提供；检查现有 SHA256 实现后，将确实共享的哈希/Artifact 基础能力放到有明确职责的公共位置，不为了几个函数堆叠 `utils/common/helpers`。保留 Exact Search 独立诊断能力，并用构建测试、CLI 默认路径及真实 Manifest 校验验证行为不变。

### P1 — 字符 n-gram / FTS5 查询规则重复实现

`scripts/retrieval/lexical_bm25.py` 中 `iter_character_runs` → `character_ngrams` → `unique_in_order` → `build_match_query`；`backend/retrieval/serving.py` 又有 `_character_ngrams` / `_build_match_query`。

**问题**：索引构建/单通道查询和正式 Serving 分别维护相似文本规则，未来修改一处可能导致 BM25 构建与查询词表达不一致。注意现有两者**空词项时行为不同**（诊断函数抛出错误，Serving 返回 `None`），不能直接机械替换。

**最小候选改法**：将共同的字符切分与词项/FTS5 表达式构造提取到适当的纯函数，保留不同调用场景的错误/空结果语义。用标点、中英文字符、短串、重复词项、引号与空 Query 的测试验证索引构建、诊断搜索、线上搜索一致性。

### P2 — `backend/retrieval/serving.py` 阅读跨度过大

约 775 行的 `serving.py` 同时包含 `QwenQueryEncoder`、`FaissDenseChannel`、`SentenceBm25Channel` 与 `RetrievalServingRuntime`。不是长度本身有罪：这些职责本身明确，且 `TextRetrievalService.search` 的 Query Plan → Fan-out → RRF → Eligibility 链条**已经相当清楚，应尽量保留**。

**待评估**：把通道具体实现（Dense/BM25 的模型、索引、数据库读取）与组装/请求编排分为最多少数几个职责清晰的模块，是否真的降低跳转成本？若没有实际收益则不拆，不为每个类单设文件。

### P2 — `scripts/retrieval/hybrid_eval.py` 可能保留了旧版在线链的重复组装

此脚本内部独立加载编码器、FAISS/BM25，并执行 `fuse_candidates_rrf` 和 `apply_candidate_eligibility`；正式 `RetrievalServingRuntime` 现在也有对应完整链路。

**风险与边界**：不是直接认定它过时；它可能保留真实的 probe 排名、per-list support、回查来源、离线输入诊断等独有能力。先比较其输出/用途与 `benchmark_serving.py`、`smoke_agent_retrieval.py`、生产 Runtime，再判断哪些可基于正式实现复用、哪些属于独立正确的 Baseline，哪些可以退役。

**验证**：明确比较同一 Query、同一 Artifact 下的候选身份/排名/过滤语义；如果两套实验有意使用不同策略，应明确命名和注释，不能为去重而抹掉独立基线。

### P3 — `backend/retrieval/metadata_store.py` 同时包含构建和在线读取

`build_metadata_store()` 管全量 JSONL→SQLite 构建；`MetadataStore` 管在线只读查询。二者生命周期不同，可能影响文件定位、依赖和后续维护。

**待评估而非立即重构**：观察是否真有编辑冲突、阅读成本或不必要的重依赖；没有证据就维持现状。若拆分，只做构建/只读职责分离，保持 Schema v2、Work/Chunk 行号/Hash 对应和公开接口不变。

## 不应误判为“AI 味儿”的内容

- **Manifest/Hash/数量一致性校验**：Serving 启动时校验 Embedding、FAISS、BM25、SQLite 的模型指纹、source hash、chunk 数量；它防止索引和来源行错配后**返回看似合理但归属错误的诗句**。不得为减少判断而删除。
- **输入、HTTP、数据库边界校验**：只有确认重复且上游不变量已经稳固时才移除；`try/except`、`.get()`、长函数都不自动构成问题。
- **诊断语义与正式产品语义有意不同**：例如 `chronology.candidate_prior_dynasties` 是早期严格前代诊断，而产品 `classify_dynasty_relation` 保留同朝/重叠/未知候选。不要为“统一”把它们混成一种规则。
- 不新增没有实际需求的 `Manager`/`Factory`/`Adapter` 层，不把少量代码拆成许多只转发的 helper。

### 停止线

**当前正式调用链对具备基础 Python 知识的人能够顺畅阅读；共享的稳定契约和算法拥有明确归属，正式模块不再无故依赖实验入口，且不存在影响维护的重复关键规则；相关测试与本地真实服务回归通过，即收口。** 不追求把整个仓库每行代码改得“像人写的”，也不要求一个新手立即理解 FAISS/IVFPQ 的全部内部数学原理。

## 2026-10-13｜本地源码复核：阶段性审计更新

- **仍存在的待审依赖**：`hybrid_eval.py`、`faiss_search.py`、`artifact_search.py` 仍从 `exact_search.py` 导入辅助能力。盘点每项导入的调用者、独有诊断行为，稳定共用能力才考虑转正；这属于本 Issue，不并入 #230。
- **正式检索主链目前职责清楚**：`TextRetrievalService.search` 依次处理 Query Plan、Fan-out、Work-level RRF 和 Eligibility；不要合并不同层面的查询去重、排名列表去重和 self-hit 排除。

## 2026-10-13｜新增候选：Retrieval 目录按职责归组（下午可做）

先评估最小目录分组：根目录保留 `client.py`（Agent HTTP client）、`server.py`（FastAPI）、`service.py`（检索编排）及 `serving.py`（Runtime）；`pipeline/` 考虑容纳 `query_strategy.py`、`fanout.py`、`fusion.py`、`eligibility.py`；`channels/` 容纳 `serving_channels.py`；`corpus/` 考虑容纳 `text_units.py`、`lexical_terms.py`、`chronology.py`、`metadata_store.py`；`artifacts/` 容纳 `artifact_files.py`、`embedding_artifact.py`、`serving_manifest.py`、`serving_paths.py`。**仅为候选，不机械按文件数拆包**，尤其核对 `metadata_store` 和 `chronology` 的职责归属是否合适。

施工前先列全仓 import/脚本/测试/CLI/文档引用，核对模块执行路径、相对 import、重依赖与循环依赖风险。分批移动并保持公开函数、Schema、算法、默认配置和检索结果不变，完成 Python 测试、静态检查、CLI import 及本地真实检索 canary 后再验收。必要时采用兼容重导出过渡，但不要永久制造两套入口。**本项可在下午作为与 #230 分开的、独立小 PR 实施；优先让用户先确认目录地图，不混入 Retrieval 行为变更。**
