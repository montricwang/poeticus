## 背景

Poeticus 现有作品库已经有 3491 首宋词；#119 也已经建立 Text Retrieval，可用 Dense / Lexical / Hybrid 从大规模诗词 Corpus 中发现文本候选。

但 Text Retrieval 回答的是：

> 哪些文本值得拿来比较？

它不能直接回答：

- 哪些作品在“清空 / 密丽 / 疏宕 / 沉郁”等诗学意义上接近？
- 同样写秋夜、离愁的两首词，为什么文学气质仍然很不同？
- 一首作品的风格判断究竟来自 AI 推断、人工判断，还是前人评论？

因此需要单独研究一层 **Poetics Profile / 作品诗学画像**，作为作品的可解释文学表征。

## 核心判断

> 不把“清空 / 骚雅 / 密丽 / 沉郁顿挫”简单做成 Boolean Tag，而优先视为可争论、程度性的文学判断。

例如：

~~~text
某作品
清空    0.82
密丽    0.18
疏宕    0.74
典雅    0.69
沉郁    0.41
~~~

这些分数不是文学史事实本身，而是某个分析者 / 模型在某套 taxonomy 下的判断。

## 需要区分的表征层

第一版可调查至少几组维度，但不预先冻结完整 ontology：

### 1. 题材 / 情感

- 羁旅
- 闺情
- 送别
- 悼亡
- 闲适
- 悲慨

### 2. 意象 / 语义场

- 酒
- 雨
- 梧桐
- 空城等

这类较适合离散标签 / 多标签。

### 3. 表现机制
- 用典
- 白描
- 比兴
- 对写
- 今昔对照

### 4. 诗学风格
- 清空

- 沉郁
- 豪健

这一层优先研究连续 score，而不是简单 true / false。

## 数据设计原则

不要直接向 `poems` 增加大量 Boolean 字段。

候选结构需要支持：

~~~text
poem_id
dimension / tag_id
score
confidence
evidence
assessor_type      # llm / human / classifier / historical_claim
assessor
model_version
taxonomy_version
created_at
review_status
~~~

需要保留：

- **score**：判断强度；
- **confidence**：我们对这次判断本身有多确信；
- **evidence**：为什么这样判断；
- **assessor / model_version**：谁做出的；
- **taxonomy_version**：概念定义改变后可重跑；
- **review_status**：candidate 与稳定结果分开。

## 最小实验

先选约 50～100 首有明显差异和边界性的宋词，不直接全量跑 3491 首。

样本应覆盖：

- 姜夔 / 吴文英：清空、密丽等典型对照；
- 苏轼 / 辛弃疾：同一作者内部风格差异；
- 周邦彦 / 柳永 / 李清照等；
- 名家非典型作品；
- 看似符合传统概括但实际可能形成反例的作品。

让强 LLM 按固定 taxonomy 输出结构化画像，再人工检查：

1. 同一作者内部是否被机械贴成同一风格；
2. 不同作者的典型作品能否拉开；
3. 模型是否把题材误当成风格；
4. 是否存在“看到月 / 秋 / 冷就自动判清空”的表面启发式；
5. score 是否具有相对排序意义，而不是伪精确数字。

## Eval 方向

优先做 pairwise / ranking，而不是追求绝对分数：

- A 与 B 谁更“密丽”？
- 同一维度下，A/B/C 的相对顺序是否稳定？
- 隐藏作者名后结果是否显著改变？
- 换一种用户 framing 是否被锚定？
- 同一首作品多次运行是否漂移过大？

可以与 #148 的 Critic Persona Eval 共用部分方法。

## 第一阶段不做

- 不立即 Fine-tune BERT / LoRA；
- 不因为有 3491 首词就立即全量批处理；
- 不把 AI score 当作 Ground Truth；
- 不要求每个古典诗学术语存在唯一稳定定义；
- 不预先建设庞大 ontology；
- 不把所有维度强行压成同一种数值类型。

## 停止线

第一阶段只回答：

> **作品诗学画像是否真的能形成稳定、可解释、对检索和推荐有价值的表征？**

如果 50～100 首样本都不能稳定拉开，就不扩大到全库。

## 2026-10-12｜并列候选：高维、稀疏、多标签的文学特征表示

**用户提供的技术路线**：不是只靠 Embedding 检索两首文字相近的诗词，而是让 LLM 批量阅读现有词作，产生**大量可解释的标签/特征**：题材、意象、情感、表达机制、语气、句法、写法、历史批评/审美感觉等。允许跨维度每首作品上百乃至上千条稀疏特征，先取得表示，再按问题需要组合、筛选、归纳/对齐。高维标签可以是离散命中、权重/程度、负向特征、从具体原文 span 导出的短释；**与 dense Embedding 并列，不要求先选择唯一一种**。



**不能提前把此法否掉**：对 3,491 首乃至几千/几万首作品做离线批处理，在工程规模上原则上可行；相较重建大规模 Dense Index，结构化标签能支持可解释的倒排/条件组合/人审。若 10,000 首平均 1,000 条关联是约千万条 `work↔tag` 关系，数据库并不天然承受不了；但**生成/审核/跨次一致性的 Token 与人工成本**需要测，不把 10,000×1,000 条 LLM 输出假定为瞬间/低成本。



**设计空间，不冻结 Schema**：①完全开放式 LLM 生成标签，表达丰富但同义词/粒度漂移较大；②固定大标签表，易精确检索但会损失微妙新概念；③**混合：开放候选 → 词汇规范化/层级合并（保留原始短释与锚点）→ 可查询特征**，可允许新概念逐步生成。可分层保存作品事实标签、文本机制标签、带强弱程度的审美判断；`model/prompt_version`、`source_span`、`confidence`、`review_status` 与人工/历史评价出处分开。



**与『降维』的精确关系**：把整首作品转换成较少的可解释特征，是一种表示/信息压缩，但如果特征维度达到几千，数学上**不保证**维度低于现有 1024-d dense 向量；本质是**从不可解释 dense 表示切换到可解释的 sparse semantic representation**。应通过查询性能和解释价值衡量，而不是仅凭标签数量。



**首轮试验**：50–100 首的历史 #156 pilot 保留，但增设『几十个固定标签 vs 开放细粒度标签 vs 两者混合』三组；观察同一首词多次标注同义项爆炸、作者刻板印象、短语/字句证据是否真实、标签增量是否给出新的跨题材近邻。确认收益后才考虑对 3491 首批量打标。
