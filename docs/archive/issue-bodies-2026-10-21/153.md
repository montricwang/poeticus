## 背景

Poeticus 现有证据链已经形成：

```text
Agent
→ lookup_allusion / lookup_reference / search_predecessor_texts
→ EvidenceService / Retrieval Service
→ CNKGraph / 自建诗词 Corpus
```

但这些来源都有明确边界：

- CNKGraph 适合典故、已收录出处；
- 自建 Text Retrieval 适合诗词 Corpus 内的互文候选；
- 后续 curated RAG 只覆盖主动选择的文献；
- 对作者生平、创作年代、版本信息、冷门文学事实、未纳入知识库的长尾问题，目前仍主要依赖模型参数知识。

因此需要增加一个**开放 Web Search Tool**，作为 curated corpus 之外的补充证据源。

核心原则：

> Web Search 是新的 Evidence Provider / Agent Tool，不另起一套独立 Search Agent。

## 第一版设计

优先沿用现有抽象：

```text
Agent
├── lookup_allusion
├── lookup_reference
├── search_predecessor_texts
└── search_web
        ↓
EvidenceService
        ↓
WebSearchProvider
        ↓
外部 Search API
```

第一版 Provider 可优先实验 Tavily；但业务层不得绑定具体供应商，后续允许替换为 Brave、Serper 或其他实现。

## 任务

- [ ] 新增 `WebSearchProvider`，接入现有 Evidence Layer，而不是在 Agent 外另建并行搜索流水线。
- [ ] 新增最小 Tool 契约，例如：
  ```text
  search_web(query)
  → title / url / snippet-or-content / provider metadata
  → EvidenceItem[]
  ```
- [ ] 将搜索结果统一适配到 Poeticus Evidence Schema，至少保留：
  - query / anchor；
  - title；
  - URL；
  - 可供模型阅读的摘要或正文片段；
  - provider；
  - candidate / error 状态；
  - 必要的 provider metadata。
- [ ] Web 结果默认视为 **candidate evidence**，不能因为搜索命中就自动晋升为 verified。
- [ ] 设置结果条数、单条文本长度、超时、请求次数和总 Tool budget，避免搜索材料无限进入 Context。
- [ ] 未配置 API Key / Provider 时不向 Agent 暴露该 Tool，保持现有部署可运行。
- [ ] 外部搜索失败、空结果、超时、格式异常时允许 Agent 基于已有证据降级回答，并明确未核实部分。
- [ ] 为 Provider adapter 和 Agent Tool 增加离线可重复测试，不依赖真实网络。

## 第一版刻意不做

- 不单独建立 Query Planner 服务；
- 不默认把一个问题拆成多个子查询；
- 不自行建设通用网页爬虫 / 浏览器自动化；
- 不默认抓取每个命中页面全文；
- 不同时接入多个 Search Provider；
- 不做复杂 rerank；
- 不把搜索摘要当权威文献。

这些复杂度只有在真实 Eval 暴露失败后再增加。

## 验收

至少覆盖几类真实问题：

1. **长尾事实**：模型自身不可靠、现有 CNKGraph / Corpus 不覆盖时，Agent 能主动调用 Web Search。
2. **已有专用 Tool 更合适**：明确典故或诗句前代来源问题，不因为新增 Web Search 就无脑改走开放搜索。
3. **无结果 / 网络错误**：系统不伪造“已经查到”的结论。
4. **来源保留**：最终回答所依据的 Web 结果可以追溯到具体 URL / title。
5. **部署降级**：没有 Web Search 配置时，Poeticus 现有功能与测试保持正常。

## 停止线

第一阶段只验证：

> **开放搜索是否给 Poeticus 带来真实、可追溯的长尾知识增量。**

不要把“接一个搜索能力”提前扩张成完整 Agentic Search Platform。

## 2026-10-12｜#235 技术选型试验交接（尚未产品接入）

#235 已关闭并记录 Tavily Search API/MCP、Tavily Extract MCP、Firecrawl Keyless Scrape MCP、DDGS Python Search 的 **WSL 真实只读成功测试**（全部 0 LLM）。DDGS 在《词源》长尾问题中比 Tavily 的一次搜索更贴题，但尚不能证明整体搜索质量/稳定性；Tavily 搜索及网页提取已有稳定接口基础，Firecrawl Keyless 在同一古籍页面提取成功但一次耗时显著较长。**现阶段不同时部署三个供应商或自动轮用免费额度**，先选单一主搜索来源做 MVP，保留可替换供应商的接口；是否 DDGS 免 Key 优先或 Tavily 有 Key 优先，需要结合线上环境与限流/可靠性确定。

下一次 PR 的最小验收：一个 `search_web(query)` 工具走现有 Evidence Layer；返回 title/url/snippet/provider/status=candidate；配置关闭或无 Key 时不破坏既有 Agent；限制搜索结果数、单条长度与总调用次数；超时/异常返回明确降级；测试直接 API/Provider adapter 与 Agent 流程，进行至少一次真实阅读场景交互验收。网页全文提取独立按需处理，不为第一版接入完整 Crawl/Planner；来源原文与参考文献校验另做。详见 #235。

### 2026-10-12｜实施顺序暂缓：先完成外部数字人文复用调查

#235 完成外部 Web Search/Extract 技术试验，不等于当前必须实现 `search_web`。用户明确目前的上位目标是调查已有的古籍平台、字词、人物图谱、词话全文和 EPUB/OCR 工具能替代多少本地语料/RAG/图谱建设。因此**本 Issue 保持 Open，暂缓写产品 PR**；先经 #184 评估 #237（词话古籍文本）、#238（人物/关系）、相关授权与证据锚点。待找到“现有本地 Evidence 的真实缺口 + Web 搜索确能弥补”再回来做最小 `search_web`；不否定现有 MVP 需求，不实施三服务额度轮换。

## 2026-10-19｜新增 DeepSeek Search/Fetch 作为候选（未接入）

DeepSeek 已公开 Search/Fetch 原生 HTTP API：
- [官方 Search & Fetch 指南](https://api-docs.deepseek.com/guides/search/)；Search 为 `POST /v1/tools/search`，Fetch 为 `POST /v1/tools/fetch`，共用 DeepSeek API Key。
- [官方收费](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)：Search、Fetch 各 **5 元 / 1,000 次成功请求**（即每次 0.005 元），模型推理 Token 费用另计；价格随官方政策变化。
- [Search Schema](https://api-docs.deepseek.com/api/search/)：一次可请求 1–50 条结果，具体响应字段和正文选项以 API 文档与实测为准。

**选型变化**：原文的「可优先实验 Tavily」仍是历史候选，不锁定。把 DeepSeek 与 #235 已实测的 Tavily/API、Firecrawl/Extract、DDGS 一同列入 #155 的离线选型对照。首轮仅比较 API 的**搜索/抓取质量与真实费用**，再由本 Issue 的 WebSearchProvider 选择一个生产实现；不能因价格低直接更换供应商，也不因同为 DeepSeek 就假定与现有模型自动集成。

**边界**：保持 #153 原有「先有长尾事实增量证据、再决定产品接入」停止线；DeepSeek Search/Fetch 属托管外部服务，不等同于本地部署 LLM。
