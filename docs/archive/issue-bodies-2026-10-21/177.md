## 背景

Poeticus 的私有数据已经从仓库内 `data/` 拆到与仓库并列的 `poeticus-data/`。计划统一工作区为：

```text
D:\Poeticus\
├── poeticus/         # Git 仓库
├── poeticus-data/    # 私有语料、模型、Embedding、检索索引、报告
├── Poetry/           # 第三方语料仓库
└── chinese-poetry/   # 第三方语料仓库
```

但目前 `poeticus-data/output/` 包含已验收作品快照、Werneror 中间语料、Embedding、FAISS/BM25/SQLite 等不同生命周期的数据；`reports/` 混有一次性审计、人工复核材料与正式评测记录。同时各脚本默认路径并未统一：例如 `scripts/retrieval/run_serving.py` 使用 `../poeticus-data/output/retrieval`，而 `scripts/corpus/werneror_import.py`、`werneror_chunk.py`、`db_import.py` 等仍使用仓库内 `data/output`。

**本 Issue 是整理/讨论与实施任务，不代表以下待定路径或删除方案已获确认；先审查、确定契约，再改动。**

## 待讨论的设计问题

1. **`output/` 的职责**：是否仅用于某次任务的暂存、调试、可随时清理的运行产物？小规模临时结果是否直接打印/使用临时目录，而不持久落盘？是否保留一个全局 `output/`？
2. **数据资产的持久位置**：正式/昂贵的产物不应只因为“由脚本生成”就归入 `output/`。候选结构：`poeticus-data/reading-corpus/{raw,normalized}/`、`poeticus-data/retrieval/{corpus,embeddings,faiss,lexical,serving}/`、`poeticus-data/models/`、`poeticus-data/reports/`。`all_manifest.json` 应与 `all_normalized.json` 同目录；Serving 所需 `manifest.json` 随各自 Artifact 保留。
3. **脚本去留**：正式导入/重建、检索 Serving、评测回归、可复用 diagnostics 与一次性历史 probe 分别怎样保留、精简或从活跃入口移出？“少用”不自动等于“废弃”。
4. **路径配置**：统一私有数据根（例如默认仓库相邻的 `poeticus-data/`，允许 CLI/env 覆盖），避免在不同脚本散落 `data/output`、`../poeticus-data/output` 等相互冲突的默认值；Windows/Linux 与部署环境均需适配。
5. **报告去留**：哪些是正式验收或决策证据、哪些含人工编辑、哪些纯可重建？要不要规范按次生成目录/时间戳和保留策略？
