## 当前判断（2026-10-21）

多来源工具已经接入：Poem Retrieval、Document RAG、CNKGraph、DeepSeek Search/Fetch、萌典和维基文库。**本地 14 工具的 Reader100 测试没有显示普遍的工具选择过载**，不应继续按旧方案「新建 Web Search / 为每类来源写死优先级 / 引入 Planner」施工。

[#357 的 100 题评测](https://github.com/montricwang/poeticus/issues/357#issuecomment-6284972557) 中 35 题实际使用工具，补充的预算实验只有 4 题超过两次调用；仍有少数应主动查证却没查的文学史、版本问题。它们必须先区分**检索数据缺失、接口失败、证据误用**和真正的工具路由问题。

## 只在下列条件出现后启动

- [ ] 找到多项可复现的读者问题：正确且可用的工具确实存在，但模型反复不调用、错调用、混淆不同来源，且简短 Tool description / Prompt 调整不能收敛。
- [ ] 固定题目和 Tool Trace，比对所需原始证据、实际调用顺序、no_hit/error 及回答质量。需要专用 Tool 的问题不应因 Web 结果容易取到就被误当已核实。
- [ ] **只修最窄的失效层**：工具描述、返回契约、路由提示或预算；新 Planner、动态 Tool Search 和统一评分体系都必须由真实对照收益触发。
- [ ] 给出「不增加额外路由层」或「最小改变已证明有效」的可复算结论；如阶段内没有触发条件，**可以按暂不计划实施结束这张单**，后续具体坏案例再复开或单列。

## 背景

[#153](https://github.com/montricwang/poeticus/issues/153) 计划新增开放 Web Search。Poeticus 到这一步会同时拥有多种性质不同的外部知识能力：

```text
lookup_allusion            → CNKGraph 典故
lookup_reference           → CNKGraph 成句 / 化用候选
search_predecessor_texts   → 自建诗词 Corpus Text Retrieval
search_web                 → 开放互联网
未来 commentary RAG       → curated 词话 / 诗话 / 评点
```

现有 #32 已解决 CNKGraph 内部“典故 vs 出处”工具选择；#119 / #144 又暴露了 textual provenance 问题可能被错误路由到 allusion Tool。

新增 Web Search 后，如果没有明确边界，很容易出现另一种退化：

> 所有不知道的问题都先搜 Web，专用 Corpus / 结构化证据源反而被绕过。

## 目标

形成一套**按问题性质选择证据域**的 Agent Routing 原则，而不是让多个 Tool 互相抢同一问题。

## 初始语义边界

### `lookup_allusion`

适合：

- 人物故事型典故；
- 典故性词语；
- 明确询问“这个典故是什么”。

不负责：

- 广义作者生平；
- 创作时间；
- 普通历史背景；
- 一句诗具体借了前人哪句文本。

### `lookup_reference`

适合：

- CNKGraph 已覆盖的成句 / 化用候选；
- 轻量、结构化的出处查证。

不应作为所有 textual provenance 问题的默认第一跳。

### `search_predecessor_texts`

适合：

- “借了谁哪一句”；
- “和哪首前代作品相似”；
- 诗词 Corpus 内的互文、成句、改写候选。

Retrieval hit 仍只是 candidate，不等于文学关系成立。

### `search_web`

适合：

- 作者生平、创作年代、历史背景；
- 版本、研究资料、机构页面；
- curated corpus 未覆盖的长尾事实；
- 需要外部来源而现有专用 Tool 明显无覆盖的问题。

不应因为“覆盖面最大”就成为所有问题的默认 Tool。

### curated commentary RAG（未来）

适合：

- 已主动选择、来源明确的词话 / 诗话 / 评点；
- 需要稳定 grounding 的文学评论。

## 需要设计的问题

- [ ] Tool description / Prompt 怎样表达上述边界，使模型能稳定选择。
- [ ] 当两个 Tool 都可能有价值时，第一跳如何决定：
  - 专用来源优先；
  - Web 作为 fallback；
  - 还是允许并行。
- [ ] 首轮 miss 后怎样使用剩余 Tool budget，不机械地切换到错误证据域。
- [ ] 哪些问题允许模型直接依赖参数知识，哪些问题需要主动查证。
- [ ] 多个 Tool 都有结果时，怎样保留来源差异，而不是合并成一个“搜索结果”。
- [ ] 是否需要在 Agent State 中记录：
  - evidence domain；
  - query；
  - tool result；
  - 最终回答实际使用了哪些 evidence。
- [ ] Tool budget 是统一计数还是不同证据域拥有独立上限。

## 回归样例

至少包含：

1. “前度刘郎是什么典故？”  
   → allusion 优先，不需要先 Web。

2. “片片轻鸥落晚沙借了前人哪一句？”  
   → Text Retrieval 优先，不先用 allusion / Web 试探。

3. “苏轼写《定风波》时是否已经在黄州？”  
   → Web / curated biography source 合理；诗词 Text Retrieval 不合适。

4. “张炎怎样评价姜夔？”  
   → 若未来已有 curated commentary RAG，应优先 curated corpus；没有时才考虑 Web。

5. “这个说法网上有人这么讲，但古籍依据是什么？”  
   → Web 命中不能替代专门文献证据；需要区分“发现线索”和“确认来源”。

6. 首选 Tool 无结果  
   → 可以补查，但补查方向必须由问题语义和已有结果决定，不能固定 `A miss → B`。

## 停止线

第一版不建立独立 Planner 服务，不要求模型预先生成复杂 DAG。

先用：

```text
清晰 Tool Contract
+ Prompt
+ Tool budget
+ 回归 Eval
```

验证是否足够。

只有真实失败表明单轮 Tool Calling 无法稳定路由时，再考虑更显式的 Query Plan / Planner Node。

## 2026-10-12｜检索两条正交分层：本地收录程度 × 外部来源范围

**讨论阶段原则，未实施/未冻结路由算法**：一是知识收录层（已校定的核心全文 / 仅保存准确书目与访问线索的外围文献 / 尚未知晓的长尾资料）；二是外部发现层（专门古籍/图书馆/学术来源 / 开放 Web 聚合搜索）。这两个维度**不应强制排序成一个全局权威等级**：专门网站可能不收录某本书，开放搜索可能先命中学术论文或某笺注书评；出现命中也不能自动将网页解释升格为底本。

**最小使用示例**：「苏轼《定风波》写作背景」若本地已有可信、带编年出处的注释→按作品 ID/书目及章节做精确检索；若本地只保存《东坡乐府笺》《苏轼词编年校注》等外围书目→先定向查图书馆/专门文献库，再以开放 Web 查该词的系年考证或相关论文；来源不足则说明尚未核实，不自动去抓取受限整理本全文。

**外部发现 ≠ 原始证据**：搜索结果区分原文/影印、编年注释、研究论文、二手转述；原始材料与学者编年推断（可能争议）在回答中分开。只有发现同类证据的真实缺口、稳定性/延迟问题时，才考虑不同来源的确定性优先级和 fallback；继续优先用现有 Tool Contract + Prompt + Eval，不先开发 planner / 全自动来源评分系统。

关联 #147（书目分层）、#133（核心 Document Corpus）、#237（跨站古籍版本与 API）、#153（仍暂缓的 Web Search MVP）。
