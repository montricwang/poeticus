## 背景

[#153](https://github.com/montricwang/poeticus/issues/153) 的第一目标不是证明“我们能调用搜索 API”，而是验证：

> **开放 Web Search 是否真的让 Poeticus 在长尾文学问题上得到新增能力，并且这种新增能力是否有可追溯证据。**

如果只看“模型最后答对没有”，很容易把模型参数知识误算成 Search 增量；#119 / #143 的 Text Retrieval 评测已经暴露过同类问题。

因此 Web Search 需要独立 Eval，且后续复杂度由失败类型购买。

## 对比组

至少比较：

```text
A. standalone LLM
B. Agent + 现有专用 Tools
C. Agent + 现有专用 Tools + Web Search
```

必要时再加入：

```text
D. Web Search + 某项升级策略
```

例如 multi-query、page fetch、rerank，但只有在前面已经观察到对应失败时才加入。

## Case 分类

优先收集 Poeticus 真实阅读场景，而不是通用搜索 benchmark。

### 1. 参数知识已经很强

例如著名作者、著名作品背景。

目的：检查 Search 是否只是重复消耗成本，甚至引入低质量网页干扰。

### 2. 长尾事实

例如冷门作品创作背景、作者生平细节、版本信息、较少见研究事实。

目的：观察 Search 是否带来真正新增答案。

### 3. 专用 Tool 明显更合适

典故 / 诗句来源 / Corpus 互文。

目的：验证新增 Web Search 不会破坏现有 Routing。

### 4. 搜索摘要不足

搜索结果能发现线索，但 snippet 不足以支持最终结论。

目的：判断是否真的需要 page fetch / content extraction。

### 5. 单 Query recall 不足

首次 query 没找到，但换写法、拆查询或加入关键实体后可以找到。

目的：判断是否需要 Query Planning / multi-query。

### 6. 噪声和来源冲突

多个网页互相转述、内容农场与较可靠来源并存、不同来源结论冲突。

目的：验证 Agent 是否会把“搜索排名高”误当成“证据强”。

## 记录字段

每个 Case 至少记录：

- 用户问题；
- 当前作品 / selection / history；
- 实际暴露给 Agent 的 Tools；
- Agent 调用了哪些 Tool；
- 每次 Search query；
- Search 返回的候选及顺序；
- 最终回答实际使用了哪些来源；
- 答案是否正确 / 是否过度断言；
- Search 是否带来新增事实；
- 新增事实是否被返回证据支持；
- 延迟、Tool call 数和大致成本；
- 失败类型。

关键指标需要区分：

```text
模型自己知道
≠ Search 找到了
≠ Search 证据真正支持最终回答
```

## Web Evidence 的语义

评测时明确区分：

- 搜索命中；
- 搜索摘要支持；
- 页面正文支持；
- 可靠来源明确支持；
- 模型基于多个线索作出的推断。

Web Search 返回默认仍是 **candidate evidence**。

不能因为：

- 排名靠前；
- 多个网页重复同一句；
- 模型觉得“看起来合理”；

就标记为 verified。

## 用 Eval 决定下一层复杂度

### 什么时候引入 multi-query / Query Planner

只有当多条真实 Case 显示：

> 单一合理 query 经常漏掉答案，而简单改写 / 拆查询可以稳定补回 recall。

### 什么时候增加网页全文抓取

只有当：

> Search 已经找到正确页面，但摘要 / snippet 经常不足以支持回答。

### 什么时候增加 rerank

只有当：

> 有价值结果已进入候选，但 distractor 过多导致模型稳定选错 / 漏用。

### 什么时候增加多 Provider fallback

只有当：

> 单 Provider 在覆盖、稳定性、地区结果或成本上形成明确瓶颈。

不要把“理论上更健壮”当成提前同时接 Tavily + Brave + Serper 的理由。

### 什么时候需要独立 Planner Node

只有当：

> 单轮 Tool Calling + 清晰 Tool Contract 仍然无法稳定完成多步搜索，而且这种失败已有重复 Case。

## 停止线

不追求一次建立“最佳搜索系统”。

第一轮只需要回答：

1. Web Search 有没有真实产品增量？
2. Agent 会不会在不需要时乱搜？
3. 搜到的材料能不能真正支撑回答？
4. 当前最主要的失败到底发生在：
   - Query；
   - Search Provider；
   - snippet；
   - source quality；
   - routing；
   - 还是最终 synthesis？

先定位失败层，再增加对应机制。
